# v2 Execution Subsystem — Control Panel & UX

> **Status:** Requirements (forward-looking). Builds on `00`–`03`. Defines the Electron
> control surface: the Trading Desk, the approval flow, the rules-config screen, the
> paper→live promotion, and notifications. The UI is a **control panel over the headless
> core** (§1) — it is for visibility and approvals, **never** for safety (§0.35).

---

## 4.1 Where it lives

A new sidebar section **🤝 Execution** (kept distinct from 💼 Portfolio, which mirrors
your *manual* E\*Trade positions — see `00` §0.2c):

- **🎛️ Trading Desk** — the live control + monitoring view (§4.2).
- **⚙️ Execution Settings** — the rules-config editor (§4.4).

The panel connects to the core's control API (`127.0.0.1:7433`) + SSE (§1.6). If the core
isn't running, the Desk shows **"Engine offline"** with a **Start Engine** action (launches
the core process); all live data is fed by the core, never read from `exec_*` directly.

## 4.2 Trading Desk view

**(a) Master control header** — always visible:

- **PAPER / LIVE badge** — large, color-coded (paper = blue/neutral, **live = red**),
  unmissable. The single most important on-screen fact.
- **Engine state** — `Running / Stopped / Paused / Kill-tripped` badge.
- **Master switch** — **Stop** is the prominent control (hard stop, §0.37); Start; Pause
  is a smaller secondary. Stop with open positions → guarded confirm + **Flatten & Stop**.
- **Broker health** — connected/authenticated/heartbeat indicator (watchdog, §1.8).
- **Kill switch** — status, manual **Trip**, and manual **Clear** (clear is itself
  confirmed; §2.6).
- **Capital gauges** — *deployed vs ceiling* and *day P&L vs daily-loss-trip* (the 10%
  line marked), so headroom is visible at a glance.

**(b) Proposals queue** (SSE-live) — each pending proposal as a card:

- ticker · strategy · structure (e.g. *bull-put vertical*) · legs/strikes · **net credit**
  · **max loss** · contracts · **capital used**;
- the brief **rationale** + **critic verdict** (with the verdict tooltip);
- a **risk-gate summary** (which checks passed; §2.5);
- a **shelf-life countdown**; **Approve** / **Reject** buttons.

**(c) Open positions** — bot-managed (`exec_positions`):

- ticker · structure · entry credit · **current mark / P&L** · days held / DTE ·
  **nearest exit rule** (e.g. "profit target 50% — 38% there") · status
  (`open / closing / needs_attention`);
- a manual **Close** action; `needs_attention` rows are highlighted.

**(d) Activity log** (SSE-live) — the human-readable `exec_audit_log` stream: proposals,
approvals, fills, exits (with reason), limit hits, kill trips, reconciliation events.

## 4.3 Approval flow (semi-auto)

1. Core creates a proposal → SSE updates the queue **and** a notification fires (§4.6).
2. User reviews the card → **Approve** → a confirm step shows the **final IBKR price + max
   loss** (re-price guard, §3.2) → core re-runs the risk gate (§2.5) → submits. Or
   **Reject** (optional reason).
3. **Live vs paper friction is different by design:**
   - **Paper:** single-click approve (it's practice).
   - **Live:** an explicit **"LIVE — real money"** confirmation modal (account id, ceiling,
     max loss spelled out; a type-to-confirm or hold-to-confirm gesture). No accidental
     live fills.
4. **Notifications deep-link to the panel; approval happens in-app.** In **live** mode,
   approval is **never** one-tap from a notification. (Paper may allow quick-approve from
   the notification — configurable.)
5. Discretionary **exit** proposals (profit target / planned exit, §3.3) flow through the
   same queue/approval path; **protective exits never appear here** — they fire
   automatically and only *report* into the activity log + a notification.

## 4.4 Execution Settings (rules-config)

A config screen modeled on the existing scoring-engine config (familiar pattern), editing
`exec_config`:

- **Risk limits** (§2.3): capital ceiling, max-risk-per-trade %, max concurrent, daily-loss
  trip %, per-ticker cap, optional per-strategy cap.
- **Entry policy** (§3.2/3.6): eligible strategies, min composite (global) **plus per-strategy
  composite-floor overrides** (one editable floor per eligible strategy; blank inherits the global
  floor — composites aren't comparable across strategies), per-day/per-week caps, entry window,
  avoid-earnings, proposal shelf-life, re-price tolerance, risk-budget width, liquidity gate.
- **Exit policy** (§3.3/3.6): stop multiple, defensive DTE, profit-target %, hold-days /
  time-exit DTE, and each **discretionary** rule's `propose | auto` toggle. **Protective
  rules expose thresholds but no `propose` option** (§0.3 invariant — enforced in the UI).
- **Execution mode** (paper / live) — the guarded toggle (§4.5).

Edits take effect on the next evaluation cycle. **Loosening a live limit** (e.g. raising
the ceiling or per-trade %) requires a confirm; tightening is immediate.

## 4.5 Paper → Live promotion (the most guarded action)

Switching `execution_mode` from paper to live is the single most consequential control:

- Allowed **only when the engine is `Stopped`** (no in-flight activity during the switch).
- Presents a **promotion checklist + summary**: live account id, capital ceiling, the full
  active limit set, broker connected-to-live + reconciled, and an acknowledgement that real
  capital is now at risk — behind a **type-to-confirm**.
- After switching, the engine starts in live via the normal Start path (reconcile-before-
  act, §1.8). The **red LIVE badge** is then persistent across the app.
- Reverting live→paper is unguarded (it only *reduces* real-money exposure).

## 4.6 Notifications

Because the core runs headless (the window may be closed), notifications are the primary
way the user learns of events needing attention.

- **Channels:** desktop (Electron native, when the app is open) **and** core-sent
  **email / push** for critical events (the core has its own notification path so alerts
  arrive even with no window open — reuses the v1 email/notification services).
- **Events:** new proposal (needs approval), fill, **protective exit fired**, discretionary
  exit proposed, **kill-switch trip**, broker disconnect / degraded health (watchdog),
  reconciliation mismatch, and a **daily summary** (positions, P&L, day's actions).
- **Severity:** approval-needed and safety events (kill trip, mismatch, protective exit,
  health) are high-priority; informational fills/summaries are normal.

## 4.7 Safety cues (always-on visual language)

- **PAPER vs LIVE** is never ambiguous — persistent, color-coded, on every Execution
  screen.
- **Kill-switch state** and **broker health** are always visible on the Desk header.
- **`needs_attention`** positions and **degraded health** use a distinct alert style.
- Protective (auto) vs discretionary (approve) actions are visually distinguished in the
  activity log so it's always clear what the engine did on its own vs what you authorized.

## 4.8 Open points

- **Quick-approve from notification (paper only)** — convenience vs discipline; default
  **off**, configurable. Never available in live.
- **Mobile push transport** — reuse the existing email path for v2.0; a dedicated push
  channel (e.g. Pushover/Telegram) is a possible later add for faster mobile alerts.
- **Daily-summary timing** — default post-close; configurable.
