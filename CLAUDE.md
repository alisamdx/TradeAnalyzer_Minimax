## Project

> **Rebuild in progress (2026-09):** a new, data-first application is being designed under `NewApp/` (start at `NewApp/README.md`). That folder is separate from everything below, which describes the **existing** app. The existing app stays untouched and running; the new one is paper-only until its requirements are done.

TradeAnalyzer is an Electron + React + TypeScript desktop app for a retail options/swing trader. Watchlists, screener, five-mode analysis engine (buy/options/wheel/bullish/bearish), configurable scoring engine, daily AI intelligence brief, validation dashboards, multi-leg payoff modeling, portfolio tracking synced from E*Trade, LEAPS+CSP and collared-LEAPS screeners, earnings calendar, News & Research, backtesting. The app is feature-complete against the v1 spec; the gate to v1.0.0 is real-world usage validation.

### Code style
- TypeScript strict mode. No `any` unless unavoidable.
- Functional React components with hooks. No class components.
- Service classes in `src/main/services/`. IPC handlers in `src/main/ipc/`.
- DB access goes through `withTransaction(db, fn)` — never raw `db.transaction()`.
- All market data flows through `DataProvider` / `OptionsProvider` interfaces — never ad-hoc `fetch` to Polygon.
- Formula comments must reference `docs/formulas.md#anchor`.

### Never
- Bypass the rate limiter for Polygon API calls
- Invent or synthesize market data — surface missing fields as null
- Log secrets — API keys live in OS keychain or `.env`
- Commit `.env`, credentials, or `backups/`
- Use `any` type — prefer `unknown` with type guards
- Reach for `db.transaction(fn)()` directly — use `withTransaction(db, fn)`

### Financial data conventions
- IV is stored and displayed as a **percentage** (38.82, not 0.3882). E*Trade returns IV as a decimal fraction (0.3882) — always multiply by 100 when ingesting.
- All monetary values in USD. Prices per share, not per contract.
- DTE is calendar days (not trading days).
- `// see docs/formulas.md#anchor` comment on every derived metric.

### E*Trade integration
- OAuth 1.0a flow implemented in `src/main/services/etrade-auth.ts`
- **The E*Trade OAuth renew endpoint is `/oauth/renew_access_token`, NOT `/v1/oauth/...`** (the `/v1/` prefix is only for market/accounts APIs). It was wrong until v1.1.99, so `renewAccessToken()` silently failed and dormant tokens **never auto-revived** — every dormancy forced a manual re-auth, masquerading as the recurring evening-batch "token expired" failure. Renew errors are swallowed in the renew-and-retry paths, and the renewal tests **mock** `renewAccessToken`, so the bad URL was invisible; `tests/etrade-renew-endpoint.test.ts` now asserts the real fetch URL. A dormant token returns `oauth_problem=token_rejected` (not `token_expired`). `checkConnection()` was a **date-stamp check only** (fast, no live call) and so could not tell a working token from a dead one — as of v1.1.166 it probes whenever the stamp isn't today's (see the midnight-ET quirk below). v1.1.100 adds a **live** `probeETradeConnection`/`etrade:test-connection` (real SPY quote + renew-and-retry → `ok|renewed|expired|error`) used by the Settings "Test Connection" button and a **~90-min keep-alive heartbeat** (`index.ts`) that pings E*Trade inside the 2h window so the token never goes dormant during a running session.
- Tokens expire at midnight ET. After 2h inactivity they go dormant — call `renewAccessToken()`. The nightly jobs **and** the on-demand `ETradeDataProvider.getOptionsChain`/`getOptionsExpirations` (via `withRenew`, v1.1.48) auto-renew-and-retry on a dormant-token 401; a token expired past midnight still needs a manual re-auth. A dormant token used to silently yield an empty chain on evening agent/lab runs.
- **A dormant token does NOT reliably fail as a 401** — it can kill/hang the response stream (undici `terminated`). Never gate a renewal attempt on an auth-shaped error message; renew-and-retry on ANY E*Trade failure (renewing an active token errors harmlessly). This bit **two** paths with the same auth-message heuristic: the daily-iv-update connectivity check (halted the evening orchestrator chain 8 of 10 trading days, fixed v1.1.92) **and** `ETradeDataProvider.withRenew` (the on-demand options path used by the API server, Strategy Lab, agent, and v2 execution re-pricing — silently returned empty chains > 2 h after last activity, fixed v1.1.94). Both now renew on any error. **The one exemption is the inverse test, and it must stay that way:** `withRenew` rethrows an HTTP 400 carrying an E*Trade application `<code>` (v1.1.355). Only a POSITIVELY identified answer is exempt, never something "not auth-shaped". E*Trade can only send a code after accepting the token. Renewing and retrying those answers had tripled every 10032 "no options" / 10033 "invalid symbol" call (136 failed calls + 89 renews on 2026-10-13).
- E*Trade credentials stored encrypted in settings via `secure-settings.ts`
- All E*Trade API calls go through `etradeGet()` which handles signing — never construct auth headers manually.

## Known quirks

- **better-sqlite3 ABI flips** between Node and Electron. `predev`/`prebuild`/`prepackage` swap the Electron binary; `pretest` swaps the Node binary. `NODE_MODULE_VERSION 128 vs 137` = wrong binary; run the matching `rebuild:*` script. Don't revert to `electron-builder install-app-deps` (reports success without swapping the ABI).
- **`package.json` must never be written by PowerShell `Set-Content -Encoding utf8`** — writes a UTF-8 BOM electron-vite rejects. Use the Edit tool or Node.
- **The root `npm run package` builds TradeAnalyzer ONLY — TradeAnalyzer 2 is a separate exe with its own build, and nothing in the root chain calls it.** Found 2026-09-17: v1.1.263 changed `packages/next/src/main/exceptions.ts`, the root package succeeded, the exe reported 1.1.263 — and `packages/next/release/win-unpacked/TradeAnalyzer2.exe` was still **0.4.8 built five days earlier**, so the change was in no binary. Build it with `npm run package --prefix packages/next` (both apps closed). Two corollaries: TA2 bundles `@tradeanalyzer/core` **as of its own build**, so a stale TA2 also runs stale core — `meta_open_handle` showed it opening the generation on `dictionary_version 15` while TA1 was on 18; and **`packages/next` has its own version** which the root bump does not touch, so a changed TA2 keeps calling itself the old version and `meta_open_handle.app_version` then names the wrong build in the forensic record. Same shape as v1.1.250's `dist/` gap: a workspace package compiled separately, and the version stamped on the main exe says nothing about it.
- **The root `npm test` does NOT run the workspace suites** — `npm run test:all` does. `packages/next`'s `workspace-versions.test.ts` sat red for weeks with `package-lock.json` recording core at 0.6.9 and the root at 1.1.245, and nothing surfaced it. Refresh with `npm install --package-lock-only`.
- **`npm run package` needs Windows Developer Mode ON** — winCodeSign archive has macOS symlinks; non-admin symlink creation is otherwise blocked. One-time setup.
- **`node:fetch` does not exist** in Node 24. Use global `fetch`.
- **`window.api` declaration** lives only in `src/renderer/src/global.d.ts`. Never redeclare per-file (TS2717).
- **`ELECTRON_RUN_AS_NODE`** guard in `dev` script prevents CJS/ESM mismatch crashes.
- **Options provider is switchable** (`optionsProvider` setting), read at startup; **E*Trade is the active default** (Polygon Options Starter cancelled). `DataProvider` is always Polygon.
- **IV rank/percentile** are null from Polygon snapshot — computed from `iv_history`, which needs the MarketData.app/IVolatility backfill populated.
- **Earnings** come from E*Trade (no Polygon public endpoint). **E*Trade dates are UTC** → Thursday-evening ET reports show as Saturday UTC; `earnings-service.ts` shifts Saturday→Friday, marks unconfirmed.
- **E*Trade IV** is a decimal fraction (0.3882 = 38.82%). `* 100` when ingesting into percentage storage; pass directly to Black-Scholes as sigma.
- **`iv_history.atm_iv` is a PERCENTAGE.** `migrations/016_iv_history.sql` created it as a decimal ("0.285 = 28.5%"), and `017_fix_iv_atm_pct.sql` converted every row to a percentage the next day. 016's column comment said "decimal" until 2026-10-10, so reading the CREATE TABLE alone gave the wrong unit; a column's unit can be changed by a later migration that its CREATE TABLE never mentions. Checked 2026-10-09 on SPY, AAPL, NVDA, TSLA, KO and MRNA, 343 rows each from 2025-05-29 to 2026-10-09, on both sides of the IVolatility → E*Trade splice: every value is a percentage (SPY ~12.7, MRNA ~102), with none below 1.5. Divide by 100 before Black-Scholes. A reader who trusts the comment and skips that gets vols 100× too large; a reader who divides a value that really is decimal gets them 100× too small. Either way nothing throws. NewApp's `derived_iv30_daily` and IVolatility's `iv30` are decimals, so check the unit per table, never per habit.
- **VIX comes from E*Trade, not Polygon** — Polygon's *stocks* snapshot can't serve VIX (it's an index, `I:VIX`). The brief job's `refreshVixQuote()` fetches it via E*Trade `/v1/market/quote/VIX`, sane-range-validates (`[5,150]`), and upserts into `quote_cache` for the critic. **The E*Trade index symbol `'VIX'` is unverified** — check `runMeta.vix` against the real VIX after a brief run; if wrong, the value is ignored (fail-safe) and the symbol needs fixing. Both the critic (`getMarketContext`) and the Morning Briefing dashboard (`BriefingService.getMarketRegime`) read this one cached value.
- **Critic LLM gets only the data in its context** — it has no live feed. It was told to compute a "1-sigma move (annualized vol …)" with **no** vol field provided, so it fabricated IV numbers. Anything the critic should reason about numerically (IV, realized vol, …) must be in the context object; the prompt now forbids citing vol figures not present in `volatility`.
- **Fake-timer tests** use `flushTimersUntil()`, not `vi.runAllTimers()`.
- **The batch runs twice a trading day** (≈10:15 ET intraday scan + ≈16:30+ ET after close) and the after-close slot re-runs every job. **Every job must refresh + overwrite what the morning slot wrote** — the morning run stores a *partial* same-day daily bar (first ~50 min of volume, intraday close), and breakout/`volume_surge` scoring reads it. Don't gate a job on `MAX(date) < date('now')` (that made the evening price refresh skip a ticker that already had a partial morning bar — fixed v1.1.49; price-gap-fill now always re-fetches + `INSERT OR REPLACE`s the recent window). The after-close daily bar must be **final** when fetched — Polygon keeps settling it past 16:00 ET, so ≈17:00 ET is safer than 16:30. See spec §20.5.
- **Weekly-expiration date math must stay in one time base.** Helpers that guess upcoming **Friday** expirations (e.g. `routes-options.ts` `nextFridays`) must compute the weekday *and* serialize in the **same** time base — all UTC (`getUTCDay`/`Date.UTC`/`setUTCDate`/`toISOString`) or all local. Mixing local weekday math with `toISOString()` shifts every date to **Saturday** on evening runs (local clock past UTC midnight), and E\*Trade lists Fridays only → the chain lookup silently returns an empty array. This starved the TraderAgent of option contracts for ~10 days (fixed v1.1.47). The canonical UTC pattern lives in `analysis-service.ts` / `filter-templates-service.ts`.
- **IBKR (TWS API via `@stoqey/ib`) gotchas** (v2 execution, validated live on paper 2026-06-18): (1) **No market data for BAG combos** — `reqMktData` on a smart-routed combo returns nothing even with an options subscription; single-leg option data works, so `IbkrExecutionBroker.priceCombo` prices **from the individual legs** (`comboQuoteFromLegs`), never the BAG. (2) **Orders need `eTradeOnly:false, firmQuoteOnly:false`** or newer TWS silently drops them (no status, no error). The engine's own placement path was missing these until v1.1.62 — the armed paper engine logged `order_submitted` but no fill ever came back and nothing reached the account (the diagnostic scripts always had the flags, so the gotcha was known but the production `IbkrExecutionBroker` path was never exercised end-to-end). Both the live order and the whatIf preflight now build through the shared `buildComboOrder()` which always sets them. (3) **Options pricing needs an OPRA market-data subscription**; order placement/fills do **not** (execution ≠ data). (4) **Paper account permissions** can't be toggled independently in Client Portal (the UI mirrors live). Do **not** assume paper has full options permissions — verify empirically: the paper account (`DUQ795672`) was found on 2026-06-23 to **lack options spread (multi-leg) permission**, so IBKR rejected/cancelled every 2-leg combo the engine sent. The engine now runs the spread-permission preflight in **paper as well as live** (v1.1.66) and refuses to start with `spread_permission:<code>` rather than arming into silent rejections; fix is operator-side (Client Portal → Trading Permissions → Options → spread level). (5) A **combo is one BAG order with N legs** (TWS "show legs" expands it), filled as a package — never N independent leg orders. (6) **An order's reject reason comes on the `error` event keyed by order id, NOT on `orderStatus`** — a rejected/cancelled order's `orderStatus` is just `Cancelled`/`Inactive` with no reason. The broker must match an order-id error to its tracked order and surface the reason, else orders end `cancelled` with `reject_reason=NULL` and you're blind (fixed v1.1.65). Diagnostics: `scripts/ibkr-*.mjs`.
- **`historical_prices` can hold UNADJUSTED SPLITS — `adjusted=true` on the fetch is not enough.** Polygon returns a series adjusted *as of that fetch*, but bars are stored incrementally and price-gap-fill only re-fetches a ~3-day window, so a split that happens later leaves pre-split bars next to post-split ones — a permanent step mid-series. Measured 2026-08-28: **153 discontinuities across 126 tickers**, incl. CRWD −74% in one day (4:1 split), DD +203%, MRNA +177%, against SPY's largest genuine daily move of 2.58%. This silently corrupts SMA/RSI/ADX, `volume_surge`, breakouts, relative strength, the backtest engine, and **Brief Replay** — the tool FR-SEY-5 depends on. `split-repair.ts` (v1.1.139) detects the step and re-fetches the whole range; repair is idempotent, so a false positive costs one API call while a false negative corrupts every indicator spanning the date. **Any incrementally-stored price series has this bug class — freshness of the tail does not imply consistency of the history.**
- **Two data sources spliced with NO overlapping days cannot be compared, ever — and the comparison is only purchasable before the splice, not after.** The existing app's `iv_history` joins IVolatility (to 2026-05-29) to E*Trade-computed values (from 2026-06-01) with **zero overlapping ticker-days** across 1,055 shared tickers. Measured on equal 67-day windows the E*Trade era carries **1.30x the IV range and 1.24x the day-to-day noise** — which would matter a great deal to IV rank, since range is exactly what IVR is computed from, and today's 252-day window is ~186 IVolatility days + ~66 E*Trade days with the *current* reading always E*Trade. But the two windows are different calendar quarters, so **source character and market regime are not separable**, and no further analysis of the stored data will separate them. Note what is NOT evidence: the level step across the join is +2.9 %, against +1.0 %, +3.4 % and +5.2 % on comparable weekends *inside* the IVolatility era — a step with no baseline beside it is not a finding, and reading one as a source bias was my first mistake here. **Two transferable rules:** (1) before splicing any two sources, buy or capture an **overlap window** (NewApp fixes this at 20 trading days past the stitch) — it is cheap beforehand and impossible afterwards; (2) an overlap check written as *"for every day both series exist, compare them"* **passes silently on zero such days**. Make the paired-day count a thresholded quantity in its own right, so "no overlap" and "clean overlap" cannot look alike. Same shape as the conviction band that could never fire and the liquidity gate that always did.

- **A UNIQUE index turns a finding into an insert failure, and the two are not interchangeable.** `raw_executed_order` was drafted unique on `order_id` with the rule "a re-pull that returns a stored order writes nothing". The behaviour is right; the index is the wrong mechanism, because the check that matters (QC-803, "an order arrived again with different leg data") can only fire if the second version can be *stored*. With a unique index it instead throws inside the capture transaction, lands as a generic parse failure, and the operator sees "the parser broke" with no way to see what differed — the evidence the finding is made of is exactly what the constraint destroys. Fixed by keying `(order_id, observed_at)` like every other supersession in the schema and putting the idempotence a level up: a fingerprint column, compared before insert, so an unchanged re-pull is a genuine no-op. **General shape: a constraint enforces an invariant; a check reports a violation. If violating the invariant is a thing you want to SEE rather than prevent, the constraint is in the way — and it fails in the one place where you have the least information.**

- **A price discontinuity has THREE possible causes and only one is repairable (v1.1.139-141).** (1) *Unadjusted split* -> re-fetch the whole range. (2) *Genuine violent move* -> data is correct; mark it, but the verdict must EXPIRE (30d TTL) since providers backfill corporate actions late. (3) *Ticker reuse* — the symbol was reassigned to a different company, so the series splices two entities and **no re-fetch can ever fix it** (the provider keys by ticker too); truncate `historical_prices` + `iv_history` before the splice. **Discriminate with VOLUME, not price**: reuse shifts the volume regime >=15x permanently (BNY 76x, SPCX 53,592x) while genuine moves stay <=5x (MRNA 5.0x). A split day's intraday range is *normal* (~2-5%) because OHLC are all already in the new scale — so a wide range means a real move. **"Steps and stays" does NOT imply a split**: a permanent repricing on news looks identical on price alone (I called MRNA a reverse split on that basis and was wrong).
- **A split repair fixes `historical_prices` but NOT the option legs frozen in `daily_briefs.picks`.** The two then sit on *different price scales*, and any replay/backtest that settles a stored strike against a stored close manufactures enormous fake losses. Measured 2026-09-02: 4 CRWD picks (4:1 split, strike/spot **4.12x**) contributed **-$168,516** of fiction to a lizard-vs-spread backtest whose reported total was **-$70,955** — the real figure was **+$97,561**, so four rows out of 164 *inverted the sign of the headline*. `split-repair` cannot fix this: rewriting historical option legs would falsify what was actually recommended at the time. Any harness reading stored legs must carry a **scale guard** — compare the short strike to the underlying's close on the pick date and exclude (don't settle) rows that disagree. `scripts/backtest-lizard-vs-spread.mjs` has one (`SCALE_TOLERANCE = 0.35`); it prints excluded rows rather than dropping them silently. **This bug class outlives the repair that causes it — a fixed price series makes stored legs MORE wrong, not less.**
- **A provider "boolean" may be a STRING, and the naive cast fails in the worst available direction.** E*Trade's option chain sends `inTheMoney` as `"y"` or `"n"` — measured 2026-09-07 on a live SPY chain. The obvious implementation for a flag column is a cast, and **`Boolean("n") === true`**, so every contract would have read as in-the-money: nothing throws, no check fires, and a moneyness filter silently selects the whole chain. The same session found `timeStamp` is epoch **seconds** (as milliseconds it lands in January 1970 — that one at least fails loudly), `expiryType` has an undocumented fourth value `MONTHEND`, and `volume` really is sent as `0` sometimes, so "absent" must be a **presence** test and never a truthiness one. **General shape: a field's TYPE is part of its contract and is not inferable from its name.** `isX`/`hasX`/`inX` naming invites a cast; one live response settles it, and the ones that fail silently are exactly the ones nobody thinks to check.
- **A source-scanning test must strip comments and string literals, or it fires on its own documentation.** Hit four times now while building NewApp: `core`'s purity guard matched `safeStorage` inside a *column description*, `next`'s AC-13 scan matched `meta_dictionary` and the word `OFFSET` inside its **own doc comment**, and the collector-host test matched `toISOString` inside a comment explaining why `toISOString` must not be used. Every one is a true positive for the regex and a false one in substance. The cost is not the failing test — it is what a developer learns from it, which is *"stop writing the comment"* or *"work around the guard"*, and both are worse than the bug the guard exists to catch. The fourth was **JSX text**: the AC-13 scan read a `<button>close</button>` link as a reference to the bar `close` column, and the only lesson available from that failure is *reword the button*. Text nodes are page copy, not code — strip them too (`/>[^<>{}]*</g`, which leaves `{row.strike}` in scope). **Rule: any assertion that greps source strips comments first; a rule about code reaching a global or an identifier also strips string contents, while a rule about a module path must keep them** (the path IS a string). Give each rule fixtures both ways — `fires` and `clean` — so the stripping itself cannot silently over-reach and make the guard vacuous.
- **A range walk with stride `N+1` emits a degenerate one-day tail whenever the range length is an exact multiple of `N+1` — and a test that builds its range from `today` can only ever see one configuration.** `syncClosedPositions` slices Jan 1 → today into 30-day transactions windows, stepping 31 days. On a range length divisible by 31 the walk lands with `cur === endMs` and emits a final window with `from === to`: one wasted round trip to an endpoint that is intermittently unresponsive for ~120 s. From a Jan 1 start that is **about twelve dates a year** (2026: Feb 1, Mar 4, Apr 4, May 5, Jun 5, Jul 6, Aug 6, Sep 6, Oct 7, Nov 7, Dec 8). The test that should have caught it asserted exactly the right invariant — every window has `span > 0` — but drove the real service, whose range comes from the clock, **so the suite was red on ~12 days a year and green on the other ~353, and on those twelve it failed for reasons unrelated to whatever had just changed.** That is worse than no test: a suite that goes red on a calendar teaches people to ignore it. Fixed v1.1.193 by extracting `buildDateSlices()` as an exported function — **that extraction is most of the fix**, because inline it was only reachable through `today` — and folding the tail into its predecessor (never dropping it; that would leave a one-day hole). **General shape: date arithmetic reached only through `new Date()` is tested on one sample per day. - **A provider's HTML page is a data contract nobody wrote down — read it before parsing it, and record what you saw.** Four phase-8 sources were fetched live before a line of parser existed (NewApp B7a, 2026-09-07), and every one of them differed from the obvious implementation in a way that **fails silently**: (1) the **FOMC** calendar names *both* months when a meeting straddles the boundary (`Apr/May 30-1`) and the decision day is in the **second** — the natural reading yields 2024-04-01, a real date wrong by a month; it also carries a non-range entry (`August 22 (notation vote)`) that a `d-d` regex drops, and its year panels are **not in chronological order**, so a flat sweep dates every meeting to whichever year parsed last. (2) The **Treasury** par-yield CSV spells one tenor `1.5 Month` where the other thirteen abbreviate (`1 Mo`, `1 Yr`) — so map by header **name**: a positional reader survives a rename and silently shifts an entire curve one column, while a name reader drops the column and the tenor-count check reports it. (3) **BLS** release pages serialise their own navigation into a `<tr>`, so select rows by a *positive* shape test (three cells, middle one date-shaped), never by "skip the first row". (4) `federalreserve.gov/json/ne-calendar.json` returns **HTTP 404 with a full HTML body** — a body is not evidence of success. **The general rule: for any source that is a page rather than a feed, one fetch converts an assumption into a measurement, and the measurement belongs in the spec next to the parser.**

- **A shared status column asserts that its fields arrive TOGETHER, and that assertion has to be earned per group.** NewApp's `raw_index_quote` gave `last, open, high, low, prev_close` one `quote_status`, and the generated CHECK constraint reads that as strictly all-or-nothing. So a response missing only `open` would have had to null `last` too — and the range check on `last` treats absence as **blocking**, meaning one missing *context* field would have taken out the whole market-regime read. Fixed at B7a by giving `last` its own status and letting the four session fields share theirs. The tell is asking **who consumes each column**: `last` is read by the check, the critic and the dashboard; open/high/low/prev_close are context, and losing them as a group is one honest fact. Note the failure mode if you get it wrong and write the row anyway — the constraint throws *inside the capture transaction*, so it surfaces as a generic parse failure rather than as the missing field it is, which is the same evidence-destroying shape as the `order_id` unique index.

- **A provider "cap" that is harmless today is still a cap, and the time to detect it is before a window grows.** EDGAR's `submissions/CIK*.json` returns at most **1,000** entries in `filings.recent` with the remainder in a `filings.files` overflow — the same truncation shape as Finnhub's 1,500-row earnings calendar, which put an earnings date a quarter late. EDGAR's truncates from the *older* end, so it happens to be harmless for a job that wants new filings, and that is exactly why it would go unflagged. It is now flagged like any other. Also: `filings.recent` is **parallel arrays**, so zipping by index makes a short companion array a *silent misalignment* rather than an error — take the row count from the natural key (`accessionNumber`, which cannot be blank) and store missing companions as null instead of shifting them into line. And map EDGAR's empty `reportDate` to null, because an empty date string sorts before every real date and quietly wins any `MIN()`.

- **An Electron startup that neither shows nor exits leaves a headless survivor — and the missing window is what disables the mechanism that would have killed it.** NewApp's new exe threw inside `app.whenReady().then(...)` with no `.catch()`, so the error became an *unhandled rejection warning* on a stderr nobody reads. `createWindow()` never ran, and `window-all-closed` **only fires once a window has been created and closed** — so `app.quit()` was never called and the process lived indefinitely. Symptom: three `TradeAnalyzer2.exe` processes, no window, no error, no exit, found only because the build's not-running guard kept refusing to package. **Two diagnostic traps in reading it:** (1) a perfectly healthy Electron main process also reports an **empty `MainWindowTitle` and `MainWindowHandle = 0`** in `Get-Process`, so "no window title" is not evidence of anything — I read it as orphaned children of a closed app and was wrong; (2) the real tell is the **process count and the `--type=` split** (`Get-CimInstance Win32_Process` + `CommandLine`): healthy is main + gpu + **renderer** + utility, and a startup that died before `createWindow()` has **no renderer**. Fix is two lines and both are needed — `.catch()` that calls `dialog.showErrorBox` then `app.exit(1)` (not `quit`, which is cooperative and has no window to close), plus `process.on('unhandledRejection'|'uncaughtException')` routed to the same handler.

- **A schema-evolution rule protects WRITTEN ROWS, so an empty table is a different case — and the rule has two halves, of which only one is usually checked.** NewApp's `applyDictionary` refuses anything but nullable-column/new-table/new-index growth inside a generation, which is right, and it bricked the new exe when a status-column split added a NOT NULL column to a table holding **zero rows**: correct by the letter, pointless in substance, since nothing can be reinterpreted that was never recorded. An empty table is now rebuilt from the dictionary; one holding even a single row keeps the refusal, and the error names the count. **The more dangerous half was silent:** the guard compared only columns the dictionary had *gained*, never ones it had **lost** — so a dropped column stayed behind, still NOT NULL with its CHECK, leaving a table that accepts **no inserts at all** and fails much later inside an ingestion transaction, where it reads as a parser fault rather than as schema drift. **Whenever a migration guard compares a declaration against a live schema, check the comparison in both directions; a reshape is an add and a remove, and catching one of them is not catching the reshape.**

- **A reference table that fails OPEN must seed itself, or the fail-open default becomes the bug.** NewApp's `ref_trading_day` sat in the dictionary from B2, was read by preflight, the watchdog and several QC checks, and **nothing ever wrote it**. Preflight treats an unknown date as a trading day on purpose — a needless run costs calls, a skipped one costs a day that cannot be recovered — but with the table empty that means *every weekend and holiday reads as a session*: the collector writes weekend-dated snapshots of Friday's data, and the watchdog emails "no daily run exists for today" every Saturday and Sunday until nobody reads it. Fixed by seeding it **inside preflight**, idempotently, before it is read: a reference table that exists only if somebody remembered to seed it is one that will be missing on the day it matters. **General shape: whenever a check is deliberately permissive about missing reference data, the same commit must guarantee the data is there — otherwise the permissiveness silently becomes the normal path.**

- **Generate an exchange calendar from rules and validate it against an independent list, in BOTH directions.** A hardcoded holiday table works until the year it runs out and then fails *silently* (the existing app's covers 2023–2027, so a 2028 run reads every weekday as a session and expects bars on Christmas). NewApp generates NYSE closures from rules and the tests compare them against the existing app's separately maintained list both ways — nothing missing, nothing extra. Fifty dates agreed by two independently built sources is far better evidence than either alone, and the single disagreement is the finding: **2025-01-09 (National Day of Mourning) is an unscheduled closure no rule can generate**, so it is listed by hand with `source = 'manual'` and the generator never overwrites it. Three rules are quietly easy to get wrong: the NYSE does **not** observe New Year's Day when it falls on a Saturday (unlike every other fixed-date holiday — December 31 stays a session); **Good Friday** has no fixed date and no n-th-weekday rule, so it needs an Easter computation; and **Juneteenth starts in 2022**. Monthly expiration is the third Friday **or the preceding session when that Friday is a holiday** — and picking a test month for that needs care, since Good Friday is usually *not* a third Friday (2019-04-19 is; 2015-04-03 is only the first).

- **A decryption failure that returns an empty string turns "unreadable" into "unset", and the app then runs with NO credentials at all.** `secure-settings.decrypt()` caught a `safeStorage` error and returned `''`, so a start where the OS credential store was not ready blanked **every** sensitive key at once — Polygon, E*Trade, Anthropic — and every provider call failed as unauthorised, looking exactly like a revoked key or a provider outage. Measured 2026-09-07: **32 keyless Polygon 401s in one afternoon against 38 successes from healthy starts of the same binary with the same stored key.** The operator had long since found the workaround (close the app and start it again) without ever learning the cause. **The tell is in `logs/api/`: a healthy call logs `"apiKey": "[REDACTED]"` in `requestParams`, a credential-less one logs `requestParams: {}`** — so the log always held the answer and nothing was reading it. Fixed v1.1.200: `undecryptableKeys()` records the failures and startup reports them in a dialog. **General shape: whenever a `catch` returns the same value as "absent", it has destroyed the distinction that names the fault — and it does so at exactly the moment the system is least able to explain itself.** Also note the launch-method sensitivity: launching the exe from `Start-Process` reproduced the credential-less boot, while a normal double-click did not, so a diagnostic launch is not a neutral observation of the app.

- **A containerised (MSIX) shell has `%APPDATA%` REDIRECTED, and the redirect is invisible from the inside — writes succeed, read back perfectly, and the other process never sees them.** Cost most of an afternoon on 2026-09-07. Queueing a `meta_job_request` row for the NewApp collector appeared to work every time (insert committed, a fresh connection read it back, row `state=queued`) while the running app reported `No queued jobs.` through a dozen two-minute ticks. Cause: the tooling ran inside a packaged host, so `C:\Users\<u>\AppData\Roaming\...` was silently served from `C:\Users\<u>\AppData\Local\Packages\<pkg>\LocalCache\Roaming\...`. Windows uses **copy-on-write** there, which is exactly why every read *before* the first write agreed with the app and every read *after* it did not — the divergence begins at your first write, not at process start. **Nothing announces it**: `%APPDATA%` still reads as the real path, and `process.execPath` / `cwd()` / `import.meta.url` are not rewritten, so a first guard that pattern-matched those did not fire. The only honest test is to **write a marker file into `%APPDATA%` and then look for it under `AppData\Local\Packages\*\LocalCache\Roaming\`** — `packages/core/scripts/queue-job.mjs` does that and refuses to run. **The same redirect also gives a child-launched Electron app a different `Electron\Local State`, so safeStorage/OSCrypt resolves a different master key and every stored credential fails to decrypt** — which is why an app launched from such a shell comes up with no keys and 401s everywhere while the same binary double-clicked is fine. The credential symptom and the queue symptom are one cause. **General rule: before trusting that two processes share a file, make BOTH of them report what they see. A write that reads back correctly proves nothing about what anyone else can read.**

- **A list endpoint with no filter and no paging returns a plausible, complete-looking, WRONG universe — every call HTTP 200.** NewApp's `universe_seed` shipped with Polygon sources `market=stocks&type=CS` and `type=ETF`, `limit=1000`, named `sp500` and `etf_list`. Polygon has **no index-membership endpoint on this plan**, so the names were aspirational and nothing contradicted them; and `limit=1000` returns one page (`next_url` pages the rest) which the parser ignored. The first live run made **2,096 calls, all 200**, reported success, and captured **2,000 tickers in alphabetical order A–DBND** — `AAAA`, `AACI` and every microcap in between — with **MSFT, NVDA, TSLA, SPY, GOOGL, META, JPM, XOM and WMT absent.** The correct lists were sitting in the host app's own `constituents` table the whole time (503 + 1,024 + 60 = **1,089 distinct**). **Two rules: (1) a list source must be validated on its CONTENT, not its status code — assert that a few names you know must be there are there, because "1,000 rows, HTTP 200" is what both the right and the wrong answer look like; (2) when a provider cannot express the filter you need, the missing filter does not announce itself — it returns the unfiltered set.** Recovery was free because `reconcileMembership` closes members absent from an incoming list, so a corrected seed self-heals.

- **`enumOf` bakes its values into a CHECK at CREATE TABLE time, so widening an enum changes no column name and a column-comparison migration guard sees NOTHING.** Third gap found in NewApp's `applyDictionary` in one day (after "added NOT NULL" and "removed column"): adding a `host_app` provider would have passed the guard silently and then failed on the constraint at the first insert using it, inside an unrelated transaction, long after the change. It now compares the whole stored DDL (`sqlite_master.sql`) against the generated one — but because that comparison is **textual**, it may only ever **rebuild an EMPTY table and never refuse a populated one**: a normalisation false positive then costs one harmless recreate instead of making the app unopenable. Drift on a populated table is *reported*, not thrown. **The normalisation was wrong on its first run** — the generator terminates its statement and `sqlite_master.sql` does not, so all 50 tables read as drifted; the idempotence test caught it, which is what that test is for. **General shape: a migration guard that compares declarations to a live schema must compare the WHOLE definition, and a textual comparison must only ever be allowed to take the safe action.**

- **TWO SQLITE LIBRARIES ON ONE WAL DATABASE CORRUPTS IT — and "a built-in has no ABI to be wrong" is reasoning about the wrong risk.** NewApp's dev scripts used `node:sqlite` (bundling SQLite **3.51.3**) while both applications use `better-sqlite3` (**3.53.1**), and the wal-index (`-shm`) format carries no cross-version compatibility guarantee. Running `diagnose-generation.mjs` / `queue-job.mjs` against a generation the collector was writing corrupted `meta_response` **twice**, and also silently lost writes — `queue-job` reported "request 1" on two successive runs because the first insert never reached the file. **The identification that mattered: `sqlite_master.rootpage` on a freshly built schema.** The two events reported `Tree 5` and `Tree 7`, which look like different objects and are the same table — adding one table to the dictionary shifted every later root page, so a tree number is only meaningful against the schema version that produced it. **The diagnosis this replaces was wrong**: the MSIX redirect was real, was worth fixing, and was NOT the cause — the second corruption happened after the redirect guard shipped, on a verified-clean shell. A directory holding two `data.sqlite` files is strong evidence of *a* fault and no evidence at all about *which* fault. Fixed v1.1.204: `packages/core/scripts/lib/generation-access.mjs` refuses while a `-shm` exists and opens with `better-sqlite3` only, **never falling back** (the ABI swap is the price, and it names the command). **General shape: a diagnostic that damages what it inspects is worse than none — and this one was the instrument being used to decide whether the damage was happening.**
- **A rule pinned by a test attached to ONE implementation does not constrain the second one.** `tests/collector-host.test.ts` has asserted "builds ET timestamps from parts, not from `toISOString`" since the day it was written — and `packages/next` stamped `meta_open_handle.opened_at` with `new Date().toISOString()` anyway, because the rule lived in a test about the collector host rather than in a function both applications call. The two stamps sat side by side in the forensic record of a corruption: `TradeAnalyzer 2 2026-09-08T03:02:53.252Z` (really **2026-09-07 23:02 ET**) beside `TradeAnalyzer 2026-09-08T23:54:19-04:00`, one of them a day out, in the two rows being compared. Fixed v1.1.208 — `etTimestamp()` is in `@tradeanalyzer/core`, both call it, and the host's test now asserts the *delegation* while `packages/core/test/time.test.ts` tests the behaviour. **When you pin a rule with a source-scanning test, ask what else in the repo the rule applies to; a scan proves only that the file it reads obeys it.**

- **An upsert keyed on "who has this now" cannot answer "was there ever".** `meta_open_handle` exists solely so a split file set is *readable* rather than inferred, and it was keyed on `app_name` alone — so each application's row held only its LATEST open and a redirected open was overwritten by the next healthy one. Measured 2026-09-09 on the real corrupt generation: both apps reported the same `db_path`, which was true of their last opens, evidence of nothing, and was read at first as "no split". Re-keyed to `(app_name, db_path)` in v1.1.208 so a path an application ever resolved is permanent. **General shape: before trusting a negative from a table, check whether the table's own key could have destroyed the positive.** (Implementation note: use a UNIQUE INDEX — the dictionary's DDL generator emits `PRIMARY KEY` inline per column, so two key columns yields `table "X" has more than one primary key`.)

- **Under a redirect, EVERY read through `%APPDATA%` answers about the container's shadow copy — including the ones a diagnostic prints before it refuses.** `diagnose-generation.mjs` probed the redirect, said so, and then reported the pointer contents, the database size, its mtime, its `-wal`/`-shm` state and the generation list, refusing only later at the open. Measured 2026-09-09: it reported `data.sqlite` at **1,789,952 bytes modified 2026-09-07 23:05 with no sidecars**, which is byte-for-byte the container's copy, while the collector had run against the real file the following evening. Every number was true and every one answered a different question. Fixed v1.1.207 — it refuses **at the probe** and prints the container's copy only under a heading saying that is what it is. **"We refuse before opening" is not enough: the reading is already wrong long before the open.** And the shadow copy is evidence in its own right — Windows creates it the moment a redirected process first *writes* to a path, so its creation and modification times bound the window in which redirected writing happened.

- **A guard whose input cannot contain what it looks for is not a guard.** `scripts/rebuild-better-sqlite3.mjs` matched `/EBUSY|resource busy or locked|EPERM/` against `err.message` to explain a locked `better_sqlite3.node`. The call uses `stdio: 'inherit'`, so `prebuild-install`'s output goes straight to the console and `err.message` is only ever `Command failed: npx prebuild-install …` — the errno was on screen and never in the string being tested, so the friendly message had never once fired since the day it was written. Fixed v1.1.207 by asking the **file** (`openSync(binary, 'r+')`; Windows maps a loaded `.node` as an executable image and refuses write access), before `prebuild-install` runs. **Whenever a handler parses an error string, check that the string can actually carry it — `stdio: 'inherit'`, a wrapped error, or a rethrow all silently empty it.** Note the third culprit the message now names: a *harness left running in the background* locks the binary exactly like a running app, and `pretest` swaps the ABI, so `npm test` dies with a stack trace pointing at `execSync`.

- **`Atomics.wait` on the Electron main thread stalls the process rather than pacing it.** The seed replay's inter-write delay used it deliberately, so the block would be synchronous — an `await` was thought to "hand the loop back and change what is being tested". Both halves were wrong: the live collector waits on a real HTTP response, so **yielding is the faithful model and blocking is the artificial one**; and parking the main thread stops libuv running its callbacks, so the seed's own async continuations never resume — measured 2026-09-09 at **1.9 s of CPU in 17 minutes with no output at all**. The comment guarded against the opposite failure ("runs at full speed while reporting a pace") and the real one was worse and in the other direction. Use `await new Promise(r => setTimeout(r, ms))`.

- **A retry loop over work that cannot record its own outcome does not converge — and the operator's mailbox is where it surfaces.** The NewApp collector's 2-minute claim loop re-claimed the same `meta_job_request` every tick because `gen-001` was malformed and `finishJob` could not write a terminal state, so the row never left `queued`. Each attempt ran the job and emailed a RED gate report: **70 runs and an inbox full of identical alarms before the first one could be acted on.** No attempt cap, no backoff, no "this already failed" check. Removed in v1.1.206; a queued job is now claimed by running `collector-oneshot` by hand. **Before any automatic retry goes back, it needs two things this one never had: a terminal state whose write cannot fail, and a cap on attempts per unit of work.** The general shape: whenever the *record* of an outcome lives in the same store as the work, a store failure makes the retry unbounded, and the alarm channel amplifies rather than reports it.

- **`batch_jobs.enabled` was ignored by the orchestrator chain — the one trigger that actually runs jobs (fixed v1.1.206).** `runStartupJobs` filtered `enabled && run_on_startup` and the daily tick filtered `enabled && daily_schedule_enabled`, but `getSubJobs` — feeding the chain that runs twice a trading day — did not look at the column, so **switching a job off in the Batch view did not stop it** and no single control did. Two defaults compounded: a job *absent* from the orchestrator's `config_json.jobs` defaults to **enabled** (still true, deliberately), so a newly registered job joins the after-close chain with nobody opting it in — which is how three collector jobs started running against a generation that was still being stabilised. Note what `enabled = 0` does and does not mean: `runJob` has never consulted it, so a disabled job is still runnable by hand. **General shape: when several triggers share a flag, check every one of them honours it — the one that is missed will be the one carrying the load.**

- **Electron 32 will not run a `.mjs` entry point, and says nothing at all.** Passed one on the command line it produces **no output, no error and no exit** — a headless main process that has to be killed, with no gpu or renderer child (the `--type=` split from the startup-survivor quirk below is the tell). The byte-identical script as `.cjs` runs and prints normally. Measured 2026-09-08 while building `packages/core/scripts/replay-seed-in-electron.cjs`. The failure mode is a **silent hang**, which is indistinguishable from the bug that harness exists to investigate — so any Electron entry launched by a script stays CommonJS, and reaches ESM through `import()`. Two more things that harness has to get right for the same reason: `ELECTRON_RUN_AS_NODE` must be **deleted** from the child's environment or Electron runs as plain Node and the arm silently becomes a duplicate of the control (assert `process.type === 'browser'` inside), and every exit path must call `app.exit()` explicitly, because a main process that never created a window never fires `window-all-closed`.

- **A dev script that opens the shared database is a THIRD application, and the guards written for the other two do not apply to it.** NewApp's `packages/core/scripts/` held three scripts that open a generation. `queue-job.mjs` and `diagnose-generation.mjs` each carried their **own copy** of the redirect check; the `-shm` in-use check lived in the shared helper; the refusal to create a missing file lived in `queue-job.mjs` alone. **`exception.mjs` — written later, for B5's ticker-reuse rulings — had none of the four**: it resolved the pointer from `homedir()` (a third spelling of a path the other two each spelled differently), called `new Database(dbPath)` on the live generation, ran `applyDictionary` against it from any shell while both apps were running, and closed without a checkpoint. Every one of those four failures had already cost this project a day, and each was already prevented somewhere else **in the same directory**. This is the fourth write-up of one shape — *a capability that must apply to every caller belongs in the function they all call* — and the previous write-up was **about these very scripts**, describing the applications as the gap. A copy in each caller is not a safeguard; it is a list of the callers somebody remembered, and the next script is written after the list. Fixed v1.1.205 by putting all four refusals in `openGenerationExclusively` / `resolveGenerationPointer` and adding a source scan that fails any script resolving the shared pointer without them.

- **Claude Code's own shell in the desktop app is MSIX-containerised, so every script it runs is a redirected process.** Verified 2026-09-08: `detectRedirect(process.env.APPDATA)` reports `%APPDATA%` served from `AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming`, and full Electron profiles for **both** applications sit under that path — `trade-analyzer-next` with its own `data\gen-001\data.sqlite` and archive files. So the redirect quirks below are not about some hypothetical packaged terminal: **they are about the session you are reading this in.** Practical consequences: a directory listing through `%APPDATA%` is a *merge* of two views and cannot be trusted to say what exists; never open a project SQLite file from here (query the API server instead, or run `packages/core/scripts/diagnose-generation.mjs`, which now refuses); and "I verified the shell was clean" is a claim that needs the probe, not an impression — `assertNotRedirected` is exported from `@tradeanalyzer/core` and costs one call.

- **A guard on the pointer is not a guard on the thing it points at — and `new Database(path)` CREATES.** NewApp's `readSharedPointer` carefully refuses to invent the shared pointer, because a wrong path would make a second empty generation indistinguishable from the real one having lost its data. One level down, `openGenerationDb` opened `data.sqlite` with better-sqlite3's default, which creates a missing file — so minutes after the corrupt gen-001 was deleted the collector's 2-minute claim tick **rebuilt it**: 52 tables, `integrity_check: ok`, every row count zero. The tell is **`meta_generation` = 0**, because only the new exe writes that row. **And that symptom was already on the corruption report** ("meta_generation reads 0 afterwards"), filed as evidence of the damage — so once the two causes were known to share it, neither could be read from it alone. Fixed v1.1.203: the refusal sits *before* the `mkdirSync` and the open, and `generationExists()` is checked by all four callers so the operator gets `skipped` with a reason instead of a two-minute stack trace. **General shape: when creation is one component's job, every other component needs an explicit refusal at the exact call that could do it accidentally — a default that creates is not a neutral default.**
- **Two applications on one logical path is TWO FILES if either was launched from a redirected shell — and the shared WAL then corrupts both.** The MSIX redirect is **per file**, so by the time NewApp's `universe_seed` ran, `data.sqlite` had been copy-on-written into the container while `-wal` and `-shm` still fell through to the real ones: the two processes coordinated through **one lock and one write-ahead log while writing two different base files**, and frames written against one base were checkpointed against the other. `PRAGMA integrity_check` reported `btreeInitPage() returns error code 11` descending through one btree at an **identical 2,318,336 bytes on two independent runs** — deterministic because the *interleaving* is deterministic, which reads exactly like a deterministic code path and sent the first session hunting three innocent hypotheses (`applyDictionary` per tick, FK behaviour in the rebuild paths, archive ordering). **Two diagnostic moves settled it in minutes and both are cheap:** (1) `sqlite_master.rootpage` on a *freshly built* database names the damaged tree — `Tree 5` was `meta_response`, i.e. the table being written, not "an early table" as inferred; (2) **a directory listing through a redirected path is a MERGE of the two views, while listing the container path directly is not** — `gen-001-corrupt-20260907` appeared in one and not the other, which proves two files behind one path without opening either. Fixed v1.1.202: `assertNotRedirected` (in `@tradeanalyzer/core`) runs in **both** exes before any SQLite handle exists, and `meta_open_handle` records which app resolved which `db_path` so a future split is read rather than inferred. **The guard had lived only in the two dev scripts — the places that could not destroy anything — while the applications that could had none.**
- **Opening a WAL database from a redirected shell MOVES it. This is not a read.** The worst finding of 2026-09-07, and it destroyed a generation while I was inspecting it to find out why it looked empty. Mechanism: under an MSIX redirect, `data.sqlite` had already been copy-on-written into the container, but `-wal` and `-shm` had not, so reads of the sidecars still fell through to the **real** ones. On close SQLite checkpoints — and the checkpoint is written into whichever `data.sqlite` that process can see, i.e. **the private copy** — after which the shared WAL is deleted. Net effect: the schema moved out of the real generation into a copy nobody would ever open again, and the original was left as a bare 4,096-byte header page reporting **0 tables**. It looks exactly like "the app never created it", which is the wrong diagnosis and leads straight to deleting things. **Rules: (1) never open a SQLite database from a process whose filesystem view you have not verified — `packages/core/scripts/diagnose-generation.mjs` now *refuses* rather than warns; (2) `data.sqlite` size alone is meaningless in WAL mode, since a complete schema can live entirely in `-wal` with the main file at one page, so always report the sidecars; (3) a present `-shm` means some process has it open right now, which is usually the question you were actually asking; (4) a tool written to stop you guessing can hand you a confident wrong answer — this one reported only the main file's size on its first real use and I nearly told the operator to delete a healthy database on the strength of it.**

- **A success predicate built from an equality can be satisfied by two zeros, and then "it worked" and "there was nothing to do" are the same line.** `wal_checkpoint(TRUNCATE)` returns `{busy, log, checkpointed}`, and the natural verdict — `busy === 0 && log === checkpointed` — is also true of `0 === 0`. Measured on the two clean `universe_seed` runs of 2026-09-09: **`walBytes ≈ 4.15 MB` with `log = 0, checkpointed = 0`**, both times. `wal_autocheckpoint` (every 1000 pages by default) had already flushed everything long before `close()`, so v1.1.209's explicit checkpoint — the leading suspect for the generation corruption, and the thing the whole next test was designed around — **moved no frames on either run**. It was struck off as the cause only because v1.1.210 logged the result *unconditionally and beside the WAL size*; one version earlier both runs printed nothing at all and it would have entered the record as the fix. **Two rules: (1) when a check reports success, make "nothing to check" a distinct outcome from "checked and passed" — an equality between two counters collapses them; (2) log the magnitude the operation acted on next to the verdict, or the verdict cannot be sized.** Same shape as the conviction band that could never fire and the liquidity gate that always did.
- **A script's closing instructions are documentation and go stale exactly like the rest of it — and they are read at the moment the operator is least able to check them.** `queue-job.mjs` ended with "the collector-oneshot handler claims one every ~2 minutes; it must be running" for the three versions after that loop was **removed** (v1.1.206), so the advice told the operator to wait for something that no longer existed. In the same evening `diagnose-generation.mjs` suggested `Rename-Item … "gen-001-corrupt-<date>"` — a date-only stamp, so the second corruption in one day collides and the tool whose job is to stop you guessing hands you `Cannot create a file when that file already exists` — and built that stamp from `toISOString()`, so **any diagnosis after 20:00 ET would file the evidence under tomorrow's date, permanently, in the directory name that IS the evidence**. All three were found by *using* the tools, not by reading them. Grep dev scripts' console output for claims about behaviour whenever that behaviour changes.

- **A walk over the dates that HAVE rows cannot find a date that has none.** NewApp's `cleanDayStreak` counted consecutive clean days by iterating `SELECT DISTINCT trading_date FROM qa_domain_day_status` — so a trading day on which the host app never ran (no 17:05 run *and* no 19:30 watchdog, the one day nothing can write `not_run`) was simply not in the walk, and the streak counted straight across it: **a missing day read as a clean one**, in the number that decides pilot exit. The `not_run` marker only protects against a dead scheduler while the process that writes it is alive. Fixed v1.1.221 by walking `ref_trading_day` and treating a session with no rows as a break. **General shape: any "consecutive" or "since" count must iterate the calendar it is counting over, never the rows that happen to exist** — the same absence-reads-as-pass family as QC-907's zero paired days.

- **A queue whose head wakes "the next" waiter by SHIFTING will shift itself, and the resource is then spent twice.** `TokenBucketRateLimiter.processNextInQueue()` did exactly this: the callback that had just succeeded was still at the head of `resolveQueue`, so `shift()` returned *it*, `setImmediate` re-ran it, and it took a second token. **Every `acquire()` spent two — the limiter ran at half its configured rate for as long as the class existed** (a burst of 10 granted 5, measured 2026-09-09), so a "100 rpm" setting was really 50 and Settings displayed a number the app never used. The fix is that the succeeding callback removes *itself* and the waker **peeks** — a waiter that still cannot get its tokens re-arms on a timer, and a shifted one would be re-armed while out of the queue, losing its FIFO place and becoming invisible to `drain()`. **Two things about why twelve tests missed it, and they generalise further than the bug: (1) every assertion was "did it resolve" with slack in the budget, and none asked "how much did that COST" — a resource-accounting bug is invisible to a liveness test; (2) the re-entry path does not execute under fake timers at all, because `setImmediate` is faked and the deferred callback never fires, so a regression test written with `vi.useFakeTimers()` passes identically before and after the fix.** My first attempt at one did. **Any test of deferred work must either use real timers or prove it can fail** — and prefer counting the resource (`expected 5 to be 10`) over awaiting it, because a hang tells you something is wrong while a count tells you what.

- **A converter that computes `invalid` and a writer that ignores it is `?? 0` with extra steps — and it re-appeared one layer down in the rebuild built to prevent it.** NewApp's bar parser called `toIntegerStrict(v)`, which returned `{ value: null, invalid: true }` for a fractional volume, and then wrote `volume: volume.value ?? 0`. **Polygon's daily `v` is fractional routinely** (it counts fractional-share trades), so gen-001 stored a plausible zero on most bars with no status column to mark it — AAPL read `volume 0` beside `transactions 1,225,501`. Two consumers failed silently in opposite-looking ways: **QC-205 skipped every zero median and reported Evaluated 0 on all three backfills** (a blocking check that had never measured one step), and **the chain subset computed dollar volume as `close × 0` and admitted nobody** — which had been attributed to "not enough bars yet" and to the empty legacy hand-off, both real and neither the main cause. No test saw it because **every fixture used a whole-number volume**: the dictionary's own premise ("a fractional volume means the field is not what we think it is") was a drafted claim never checked against one live response. Fixed v1.1.236 (`core` 0.6.6, dictionary v15): volume is a nullable REAL in a new `share_quantity` unit, stored as sent. The same audit found QC-205 measured the wrong thing even with good data — the last 40 ROWS per ticker, so stacked backfills made it ~13 days and a reuse anywhere but the tail was invisible; it now measures 20 sessions either side of each QC-204-sized step, on the latest version of each day. **General shape: when a check reports `Evaluated 0`, that is the finding — before tuning its threshold, find out what made its input empty.**
- **`console.log` / `console.warn` in the main process of a packaged app is not a log — it is nowhere.** The brief job reported both of its emails only to the console. On 2026-09-11 the after-close brief emailed 17 picks and the Roll the Dice email a few seconds later never arrived; reconstructing even *which step* failed took the batch history, the operator's inbox, a minute-by-minute histogram of 7 MB of API log and an in-app reproduction — and the actual SMTP error was still unrecoverable. Fixed v1.1.241: every email outcome goes to `logs/errors` (INFO when sent, ERROR with the provider message when not, each naming its step). **Rule: any path whose failure is "something the operator expected did not arrive" must write its outcome — success included — to a file. A log that records only failures cannot tell "sent" from "never tried".** The same block also sat inside `totalPicks > 0`, contradicting its own comment "a no-pick day still sends" — a comment is a claim, and this one was false for every zero-pick brief.
- **"The next N rows" is a time window only on a series with no holes.** NewApp's QC-205 compared median volume over the 20 stored bars either side of a price step. SOLS was a $0.0001 shell printing once every few weeks until Solstice Advanced Materials listed on 2025-10-30, so the shell's 20 bars spanned two years and three of its internal sub-penny steps "saw" Solstice's volume — all three reported the identical post-step median, 4,222,115, which is the tell: **identical window statistics on events far apart mean the windows overlap.** Measured on the calendar instead (20 exchange sessions, ≥ 15 bars), the real splice then has an EMPTY before-window and becomes unmeasurable — fixing the window hid the case the check exists for. So the dormant form got its own check (QC-209: a step after ≥ 20 bar-less sessions, followed by bars on ≥ 15 of the next 20), and its density condition is what stops the shell's own steps firing. That splice was also QC-204's unexplained maximum (48.74 / 0.0001 = 487,400×) — **a table's worst value is usually the most interesting single row in it, so read that row before assuming it is noise.** Fixed v1.1.238.
- **A job that treats "source table absent" as a normal outcome cannot tell a fresh install from being handed the wrong database.** NewApp's `legacy_import` logs a missing table as a rejection and carries on, which is right for an install that never had screen presets. `collector-oneshot` passed it the NEW generation (`legacyDb: db as never`), so every one of eight tables was "absent" and the job reported `0 config rows, 0 decisions` — success, 0 s — from its first day. **The `as never` is the second cast in a week to hide a wrong value** (v1.1.232's `as` hid the brief-mode enum). Behind it sat a query against `constituents.universe`, a column that never existed, unreachable until the first bug was fixed. Core's test missed that because its fake legacy tables were written from the importer's assumptions and had no `constituents` at all. Fixed v1.1.237; the regression builds the legacy DB from the real `migrations/`. **Rules: (1) a cast to `never`/`unknown` at a call site is a claim nobody checked — prefer a typed dependency; (2) when "nothing there" is an acceptable result, assert on at least one thing that must be there; (3) test a reader against the schema it reads, never a fixture written from the reader.**
- **A refused query rendered beneath its refusal as "no rows" is indistinguishable from a query that ran and matched nothing.** TA2's Data view shows a notice when a filter on a large table lacks an indexed column — and still drew the empty grid underneath. The operator read `raw_daily_bar WHERE volume = 0` as zero rows, which would have exonerated the bug above. Fixed v1.1.236 (`next` 0.4.5): no grid under a refusal. Same family as QC-907's zero paired days and `cleanDayStreak` walking only dates with rows.

- **An idempotence key that omits the DATE silently deletes a day's facts whenever a body is naturally stable — and "a fresh call returns a different body" is a premise about QUOTES that was applied to LISTS.** NewApp's `dedup_hash` was `sha256(provider + endpoint + params_json + body)`, with the dictionary itself asserting that re-running a day is safe because the bytes differ. A ticker's **expiration dates are the same bytes every day** until one rolls off. So on the second daily run (2026-09-15) 496 of 541 expiration responses hashed equal to the previous day's, `captureResponse` short-circuited, and **no `raw_option_expiration` row was written for the new date** — QC-401 then correctly reported 91.68 % of the chain subset "returned no expirations" while every one of those calls had been made, answered 200 and paid for. Measured in the collector window: etrade **4,867 called / 4,365 captured**, and the whole 502 gap is that one endpoint (polygon 1090/1090, edgar 31/31, finnhub 9/9, treasury 1/1 — nothing else deduped, because their bodies move). Independent confirmation without touching the DB: per-symbol E*Trade `responseSizeBytes` against the previous night gave **499 identical / 20 changed / 18 new**. It was invisible on day one because there was nothing to dedupe against — **the first run of any such mechanism cannot exhibit it**. Fixed v1.1.248 by putting `as_of_date` in the key. **Two transferable rules: (1) whenever a cache/dedup/"unchanged" test spans a time bucket, the bucket must be IN the key, or the mechanism will eventually be asked to distinguish "same answer" from "same day"; (2) both existing dedup tests pinned `asOfDate` to one constant, so neither could ever see it — the same one-sample shape as date arithmetic reached only through `new Date()`.**
- **A constructed identifier that must equal a received one is a measurement, not a format — and `padEnd(6, ' ')` matched nothing for two weeks.** `ref_sticky_contract.osi_symbol` is joined by equality to `raw_option_contract_snapshot.osi_symbol`, which is E*Trade's `osiKey` stored verbatim. `osi.ts` built the root space-padded, under a docstring claiming the shape came from a live response; the **OCC specification** pads with spaces and **E*Trade sends dashes**. Captured bytes settle it: `ACGL--260918C00095000` and `BMNR--270115P00095000` from the provider, `AIZ   261016C00280000` from the builder. So the join could not match for any root shorter than six characters: **every pin was unhonoured** (QC-409 at 267 then 415 findings, growing by one per new recommendation and never resolving) and `sticky_reason` was never stamped on a captured contract. The file's own header names this exact failure as "the worst available" — the guard was written, the risk was understood, and the constant was wrong. **Nothing caught it because every fixture in the repo spelt `osiKey` the way the builder did** (`SPY   260918C…` in four test files) — a reader tested against a fixture written from the reader, third instance in this project. **Rule: any identifier you BUILD that must equal one you RECEIVE gets its test anchored on a value copied out of stored provider bytes, never one typed by hand — and the anchor names the table and date it came from.** Fixed v1.1.248; `repairStickyOsiPadding` closes the mispadded ranges and opens corrected ones rather than rewriting in place, because the old symbol is the evidence for the findings it caused.
- **`nodemailer.sendMail` resolving is not delivery, and it is not even full acceptance — it rejects only when EVERY recipient is refused.** The collector's `sendEmail` awaited it and logged `collector-email:sent`, discarding `info.accepted`, `info.rejected`, `info.response` and `info.messageId`. Two RED gate emails (2026-09-14, 2026-09-15) were logged sent, with no error, and did not arrive — and from the log a relay failure, a partial rejection, a spam-folder landing and a clipped body were all indistinguishable. **A second, compounding fault: the email listed every finding one per line — 773 blocking rows**, past the ~102 KB where Gmail clips a body and unreadable long before that, with 415 identical QC-409 lines burying the eight other checks that each needed a different decision. **An alert that cannot be read has already failed, whatever the delivery log says.** Fixed v1.1.248: the relay's verdict and the body size are logged (partial rejection is an ERROR), and each section collapses to one line per check with up to three real rows and `… and N more`, the total never dropped. **General shape: when a notification is the only thing standing between a silent failure and the operator, its OWN outcome needs the same evidence standard as the thing it reports — and its size is a property to assert in a test, not a consequence to hope about.**

- **A VERDICT THAT HAS NEVER CHANGED IS NOT A SIGNAL — report the DELTA, and make "no baseline" a third outcome.** Every daily gate run of NewApp's gen-002 came back RED, so on 2026-09-15 a check firing for the first time at 92 % (QC-401) was rendered identically to 151 price discontinuities weeks old: same verdict, same section, same formatting, 773 rows. The only way to extract the news was to read all of it and remember the previous night, so the operator stopped reading the alert and asked for a manual review each evening instead — **the alert existed, fired correctly, and still produced a human in the loop.** Fixed v1.1.249 (`qa/delta.ts`): per check, what this run *added*, what *stopped*, what merely persists, derived from `first_seen_run_id`/`last_seen_run_id`/`still_firing` — **no new stored state, because a snapshot table is a second source of truth to keep honest.** Four things that turned out to matter: (1) the delta belongs in the **subject**, since that is what is read on a phone and what decides whether the mail is opened (`RED (572 blocking) · 1 NEW` vs `RED (572 blocking) · no change`); (2) the baseline is the previous **run**, not the previous **day**, or a same-day re-run compares against itself; (3) `churned` has to exist — a check that swaps one ticker for another has an identical count on both runs, and calling that unchanged hides a moving population behind a stable number; (4) **"no baseline" must be a distinct outcome from "no change"** — a generation's first run has nothing to compare against, and rendering that as a quiet night would make the summariser the newest member of the family it summarises (QC-907's zero paired days, `cleanDayStreak` walking only dates with rows, the overlap check that passed on zero overlaps). **Third instance of one shape after the conviction band that could never fire and the liquidity gate that always did: a threshold is informative only where it can go both ways, and so is a verdict.**

- **`packages/core` IS CONSUMED FROM `dist/`, AND NOTHING IN THE BUILD BUILT IT — v1.1.248 and v1.1.249 shipped with none of their changes in them (fixed v1.1.250).** `main: ./dist/index.js` and every subpath export points into `dist/`, while `prepackage` ran only `check-not-running` → the better-sqlite3 ABI swap → `electron-vite build`. So `dist/` held whatever the last person to type `tsc` had left: core 0.6.9 from v1.1.245. Two releases were committed, tested (529 core tests), typechecked, linted, packaged and **version-verified off the binary's `ProductVersion`** — and the dedup fix, the OSI fix, the email cap and the run delta were all absent from the artefact. **The four green checks all read `packages/core/src` or the root `package.json`; not one of them touched `dist/`.** It surfaced only because `meta_run.collector_version` recorded `0.6.9` on a run made by an app calling itself 1.1.249 — the only field in the system that names the *built* collector, written into the generation rather than displayed, so it was found one run late and by luck. **General shape: a test suite that runs against source is not evidence about an artefact built from something else, and "the version on the exe is right" says nothing about a workspace package compiled separately.** Fixed in two halves, both needed: `build:core` runs in `prepackage`/`prebuild`/`predev` before `electron-vite build`, and `scripts/check-core-built.mjs` then fails the build if `dist/version.js`'s `COLLECTOR_VERSION` disagrees with `packages/core/package.json` **or** if any `src/` file is newer than every `dist/` file — because a build step that silently does not run looks exactly like one that ran, and a version comparison alone cannot catch a source edit made without a bump. Verify a guard like this by running it against the broken tree *first*; this one printed `built 0.6.9, source declares 0.6.11` before the build and passed after.
- **The gate email was 1.25 MB, and that is why two RED alerts never arrived.** `accepted=1 bytes=1254650 CLIPPED(>102KB) relay="250 …"` — accepted by Resend with an SMTP `250`, twelve times over Gmail's ~102 KB clip threshold, on a body that listed every one of 2,835 blocking findings. **The relay accepting a message is not evidence that anybody can read it**, and until v1.1.248 logged the byte count the failure was indistinguishable from a relay fault, a spam landing or a partial rejection. Two days were spent inferring; the first run with the size in the log settled it. **Rule: log the SIZE of anything you hand to a delivery system, next to its verdict — the verdict alone cannot be sized.** Same shape as the WAL checkpoint that reported success on `0 === 0`.

- **E*Trade's option PRICES and its GREEKS can disagree about where the stock is — trust the prices (v1.1.252).** Measured 2026-09-15/16 with `packages/core/scripts/qc410-study.mjs`: put-call parity on E*Trade's quoted mids recovers the session close to a median −0.03 % across ~500 tickers, while on 50–70 tickers a day the deltas imply a different underlying — PCTY **113.6 on a 147.3 close on both days**, AMG 405 on 343, WSM 235 on 218. The Greeks are recomputed per request (the same AIZ quote, one timestamp, returned delta −0.995 on one run and −0.782 on the next) and are not stale by any fixed lag. **Any strike chosen "by delta" on such a chain is the wrong contract**, and the old app's Strategy Lab guard (8 %, reading the strike nearest put delta −0.50) cannot see the 3–8 % cases because it resolves no finer than strike spacing. How it was found is the transferable part: QC-410 had been firing at 8 % of ATM contracts, which read as "the model's tolerance is too tight near expiry" — and the first explanation offered (after-hours drift in `nearPrice`) was **wrong**, disproved when `nearPrice` matched the bar close on all 547 tickers. The decisive split was **per ticker**, not per contract: breach rate went from 1.4 % to 94 % as the delta-implied spot moved away from the close, and parity separated "Greeks wrong" from "prices wrong" without using any Greek. **General shape: when an aggregate breach rate is modest, split it by the unit the fault would live in before tuning the threshold — a feed-wide 8 % can be 90 % of contracts on a few dozen tickers and 1 % everywhere else.**

- **SEC's companyfacts API can omit a filing for weeks even when the filing carries XBRL (v1.1.271).** IQV's and JCI's July 10-Qs (`isXBRL=1, isInlineXBRL=1`) were still absent from companyfacts on 2026-09-18, seven weeks after filing, and JBS N.V.'s August 10-Q likewise; the other ~470 filers' July reports were present. So "we fetched companyfacts after the filing" is not "we have the filing's facts", and a queue that re-asks "the N newest pending filers" with no memory of having asked will spend its budget on the filers SEC never updates — JBS took a slot on four of six runs. Retry lagging filers on a cadence (`factsQueue`, weekly) and let the finding name SEC as the cause rather than the pipeline. **By 2026-10-14 it was 35 filings, 70+ days out (Citi had no 2026 10-Q in the aggregate at all), and no retry was ever going to fix it.** Since v1.1.360 the collector reads an omitted filing's own extracted instance (`…/{accession}/{primary}_htm.xml`) instead. It matched companyfacts row for row on three filings both have. **SEC's archive host (`www.sec.gov`) refuses a User-Agent without a contact address**, answering HTTP 200 with an "Undeclared Automated Tool" HTML page, so any ad-hoc fetch from a shell needs the app's `edgarContact` setting. `data.sec.gov` is more lenient, which is why companyfacts calls never showed it.
- **A gate check that throws is recorded as ONE blocking finding, so a broken check looks like a small, stable problem forever.** QC-604 queried `ref_trading_day.trade_date` (the column is `date`) and had never evaluated a report date (fixed v1.1.251). QC-407 did not throw — it joined on `raw_eod_quote.last`, which Polygon never sends on this plan, and evaluated zero tickers every run with no finding at all (fixed v1.1.252). Both were in the gate's own output the whole time: one as `check threw`, the other as `evaluated_count = 0`. **Read `qa_check_result.evaluated_count` for zeros and the exceptions list for `check_error` before reading anything else in a RED report.**

- **A consecutive-runs escalation counts EVALUATIONS, so a check that re-reads one old observation every night escalates on repetition, not evidence (v1.1.317).** QC-602 compared each ticker's *latest* E*Trade earnings row, which the rotating overlap sample fetches about once in eleven weeks, against fresh Finnhub data nightly. One observation of AAPL, ABT, ACN and ABBV each became four "consecutive" firings and was promoted to blocking, and could not clear until E*Trade was asked again. Compare a sampled source only in the run that fetched it. **When a check joins a slowly refreshed source to a fast one, ask how often the slow side is actually re-observed — the finding's age, severity and "still firing" all inherit the answer.**

- **A rotation computed as `(day × N) mod list length` loses filers in two ways (v1.1.325).** NewApp's EDGAR submissions sweep did this with a calendar day, but the collector runs on trading days, so the weekend slices were never asked. And any change to the list length moves the pointer: v1.1.275's fund exclusion took the list from 1,083 to 1,012 and sent it from L back to H. After two weeks it had asked 135 of 1,012 filers, and `events_filings` read 20 / 0 / 1 while re-reading filers seen nine days earlier. **Order by "asked longest ago", read from the record of the asks.** That has no pointer to move and cannot skip anything. Better still, look for one bulk source that answers for everyone: here, the daily form index the insider sweep already fetched lists every report filing.

- **A shared SQL fragment interpolated into other queries must use aliases no caller could pick (v1.1.332).** `effectiveCikSql` named its inner tables `s` and `r`. QC-701 passed it `r.ticker` from its own `raw_ticker_reference r`, so inside the subquery `r.ticker = r.ticker` bound both sides to the inner table. That is always true, so every stock got the CIK of the newest reference row in the table. QC-701 then evaluated **0 of 69**, which reads exactly like "nothing to check". It shipped in v1.1.331 with green tests, because the test's fixture held one ticker, and for one ticker "the newest row" is the right one. It was caught only by rehearsing on real data (`rehearse-gate.mjs`, 7/69 → 0/0). **Two rules:** give interpolated fragments distinctive aliases (`cik__sec`, `cik__ref`), and test any per-row lookup with **at least two rows that must get different answers**.

- **A per-structure field stamped onto every leg is wrong for exactly the structures that have more than one (v1.1.347).** The legacy hand-off built each leg's OSI symbol from `setup.expiration`, but calendars, diagonals and PMCCs take their long leg from the lab's far chain, and `SetupLeg.expiration` says so. The far leg was pinned at the near expiry: CRWD 237.5 on the 10-30 weekly, a strike E\*Trade lists only on monthlies. QC-409 fired on it nightly, and the stored bid/ask/IV beside it were another contract's. The same builder passed the lab's **percentage** IV into a fraction column, under a comment saying the lab held fractions. 04 §8 claimed "a hand-off test asserts it" and no such test existed. **A spec sentence saying a test exists is a claim. Find the test.** Separately, a check whose subject the provider has stopped serving (QC-409 on pins whose underlying E\*Trade answers 204/400) must report that once per ticker (QC-415), not once per contract forever.

- **A run that did nothing must not close with the status of a run that did its job (v1.1.350).** NewApp's `runDaily` opened a run before preflight, and when preflight refused (a weekend, a closed generation) it closed the run `complete`. Seven weekends left seven empty "completed daily runs". Two readers trusted the status: the replay job's "latest completed daily run" replayed Sunday's and reported 0/0, and the watchdog's "any complete run for the date = done" would have swallowed the NO RUN email had preflight ever stopped on a trading day. **When a status is read as evidence that work happened, a refusal needs a different status. And a reader that needs captured data should ask for captured data (`EXISTS meta_response`), not for a label.**

## Standing instructions for AI sessions

- **No phased delivery anymore** — the app is feature-complete. Implement the requested change end-to-end: tests green, changelog + `.ai/AI_CONTEXT.md` + affected `Requirements/spec/` section updated, single Conventional Commit, then `npm run package`.
- Prefer the simplest implementation that satisfies the request. Don't add features outside scope; if one seems needed, surface it and add to `Open decisions` in `.ai/AI_CONTEXT.md`.
- Keep `.ai/AI_CONTEXT.md` accurate and lean (target < 1,500 lines). It describes current state, not history — history goes in `changelogs/`.
- When you hit a non-obvious gotcha, add it to `Known quirks` here and/or `.ai/AI_CONTEXT.md §10`.
- Announce when `npm run package` starts and finishes.
- **Validate-before-ship for trade-logic changes (FR-SEY-5).** Any change to a scoring weight/signal, an entry/exit policy parameter, or a risk-gate rule that affects *which trades the engine takes or how it sizes/exits them* must be backed by a **Brief Replay and/or Backtest delta** showing it is at worst neutral on the historical sample before it ships on the live path. A rule that can't be shown to help on the data doesn't ship enabled — it may ship **disabled** (configurable, default off) with the null/negative finding recorded. Precedent: the SPY-regime gate and overbought guard were both tested and rejected on full-year replay. See `Requirements/v2-execution/06-seykota-risk-extensions.md`.
