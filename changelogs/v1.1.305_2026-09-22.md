# v1.1.305 — 2026-09-22

## QC-906 was measuring a normal option grant

### The finding, and why it was not what it said

The 2026-09-21 gate carried `11 of 94 fetched Form 4 filings parsed to no rows`.
QC-906 reads that as the signature of a schema change — a parser that has
quietly stopped understanding its source, which shows up nowhere else because
the domain simply gets quieter.

All 11 were pulled back from EDGAR. Every one is a correct, well-formed Form 4
carrying **only derivative transactions**:

| accession | issuer | nonDerivTx | derivTx |
|---|---|---|---|
| 0002012362-26-000006 | Amcor (AMCR) | 0 | 2 |
| 0000950103-26-014137 | Aura Minerals (AUGO) | 0 | 3 |
| 0001795497-26-000006 | BILL Holdings (BILL) | 0 | 1 |
| 0000950103-26-014124 | Cintas (CTAS) | 0 | 1 |

`makeForm4Ingest` dropped derivative transactions on purpose, and the reason was
good: `raw_insider_transaction` had no column to tell an option grant's notional
share count from an open-market purchase, so storing both would have made every
insider-buying signal computed from the table wrong in a way nothing could
detect afterwards. The parser was right. The check was measuring the wrong
quantity — the dominant cause of "no rows" was an ordinary option grant, not a
schema change.

Measured over every run that ever had Form 4 data:

| run | empty / fetched | fired |
|---|---|---|
| 19 | 18 / 94 = 19.1 % | yes |
| 27 | 11 / 94 = 11.7 % | yes |

**Two of two, against a 10 % threshold. It has never once passed.** Same family
as the liquidity gate that always fires and the conviction band that never
could: a threshold is informative only where the quantity it tests can go both
ways.

### The fix

Dictionary **v20** adds `raw_insider_transaction.security_class`
(`non_derivative` / `derivative`, nullable), and both classes are now stored.
Zero rows once again means what the check says it means: a readable filing that
yielded nothing. A Form 4 reporting only *holdings* still parses to none — rare,
and a finding worth having.

`security_class` **must be read before `shares` is summed.** The original
concern has not gone away; it has been given a column.

### The part that took the thinking: replay

A parser that produces more rows than are already stored breaks replay equality
(AC-4 / QC-951) for **every response captured before it** — 487 insider rows
across runs 19 and 27 would have become unrebuildable, and QC-951 is blocking.
`replay.ts` narrows the comparison to columns the old dictionary had, but it
cannot narrow *rows*, and changing a parser's behaviour does not change its
recipe digest, so a replay re-runs today's code under yesterday's recipe id.

So the widening is an **argument**, carried in the recipe:
`recipes.form4({ derivatives: true })`. A pre-v20 response's stored recipe has
no `derivatives` key, `parseStoredRecipe` rebuilds the parser without it, and
its replay reproduces exactly the rows it produced then. That is what
`meta_ingest_recipe` exists for — the dictionary's own words: *"what makes a
replay a re-run of the SAME parse rather than a reconstruction of it."*

Two details that had to be right and only one is obvious:

- The key is **omitted** when false, not written as `derivatives: false`. Adding
  it unconditionally would change `recipeDigest` for every already-captured
  Form 4 and give it a new recipe id.
- The legacy path writes `security_class` as **null**, not `'non_derivative'`.
  A replay compares values, not intent, and the column did not exist then.
- `line_no` numbers non-derivative transactions first and continues into the
  derivative ones, so no row already stored is renumbered and
  `(accession_no, line_no)` stays unique.
- A present-but-non-boolean `derivatives` throws rather than reading as truthy.
  `Boolean("false") === true`, and a stored recipe saying a parse was narrow
  must never be able to widen it — the same shape as E*Trade's `inTheMoney`
  arriving as `"n"`.

### Verified, not assumed

The new dictionary was applied to a **real copy of the live generation**
(`VACUUM INTO` snapshot, 1.73 GB, `raw_insider_transaction` holding 487 rows).
`ALTER TABLE … ADD COLUMN "security_class" TEXT` landed, `meta_dictionary`
recorded v20, the gate ran its 54 checks, and no drift was reported. The column
is a plain `TEXT` rather than an `enumOf` for exactly that reason: a populated
table grows by a bare `ALTER`, so a declared CHECK would sit in the generated
DDL and never in the stored one, and the table would read as drifted on every
open — the same trap that keeps `meta_response.ingest_recipe_id` free of a
`references` clause.
