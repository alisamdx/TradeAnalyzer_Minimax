# v1.1.250 — 2026-09-15

## The build now builds `packages/core`, and refuses to ship if it didn't

**v1.1.248 and v1.1.249 shipped with none of their changes in them.**

`@tradeanalyzer/core` is consumed through `dist/` — `packages/core/package.json`
sets `main: ./dist/index.js` and every subpath export points into `dist/`. The
root build never compiled it: `prepackage` ran `check-not-running`, then the
better-sqlite3 ABI swap, then `electron-vite build`. So `dist/` was whatever the
last person to type `tsc` had left there — in this case 2026-09-15 01:13 ET,
core 0.6.9, from v1.1.245.

Both of tonight's releases were committed, tested, typechecked, linted, packaged
and version-verified off the binary, and the cross-day dedup fix, the OSI padding
fix, the gate-email cap and the run delta were **all still absent from the
artefact**.

### How it surfaced, and how nearly it didn't

A manual `data-collector` run at 21:04 ET recorded
`meta_run.collector_version = 0.6.9` — made by an application reporting itself as
1.1.249. That field is the only place in the system that names the *built*
collector, and it is written into the generation rather than displayed anywhere,
so it was found one run too late and by luck.

Nothing else could have caught it:

| Check | What it reads | What it proves about the build |
|---|---|---|
| `vitest run` (529 core tests) | `packages/core/src` | nothing |
| `tsc --noEmit` | `packages/core/src` | nothing |
| the version test | `src/version.ts` vs `packages/core/package.json` | nothing |
| `ProductVersion` on the exe | root `package.json` | nothing about core |

Four green checks that agree with each other and say nothing about what shipped.
**A suite that runs against source is not evidence about an artefact built from
something else.**

### The fix, in two halves

- `build:core` (`tsc -p packages/core/tsconfig.json`) runs in `prepackage`,
  `prebuild` and `predev`, before `electron-vite build`.
- `scripts/check-core-built.mjs` runs after it and fails the build if
  `dist/version.js`'s `COLLECTOR_VERSION` disagrees with
  `packages/core/package.json`, or if any file under `src/` is newer than every
  file under `dist/`. A build step that silently does not run looks exactly like
  one that ran, so the result is verified rather than assumed.

The timestamp half matters on its own: the version only moves when somebody
remembers to bump it, so a version comparison cannot catch a source edit made
without one. A false positive costs one `tsc` run.

Verified by running the guard against the stale tree before building — it
reported `built 0.6.9, source declares 0.6.11` and exited 1 — then against the
built tree, where it passes.

## The gate email was 1.25 MB, and now we know

v1.1.248's send-outcome logging is **app**-side, so unlike the core changes it
did reach the binary. Its first real run produced the number the last two days of
guessing lacked:

```
[collector] email sent: [TA-Data] 2026-09-15 after_close — RED (2835 blocking)
  — accepted=1 bytes=1254650 CLIPPED(>102KB)
    relay="250 cdbe82d8-…" id=<9e108b99-…@resend.dev>
```

**1,254,650 bytes.** Accepted by the relay with an SMTP `250`, twelve times over
Gmail's ~102 KB clip threshold. The message left the building every time and was
never readable when it landed.

The cap that reduces this to a few KB is core-side (v1.1.248), so it was in the
`dist/` that never got built. It is in this one.

## Run 13 is not a valid test of anything from v1.1.248/249

It ran collector 0.6.9. It also made the backlog look worse in a way that is the
escalation rule working correctly: a third consecutive firing promotes an
exception one severity level, so ~1,533 QC-410 and 415 QC-404 warnings became
blocking, taking the count from 753 to 4,502. Re-running an already-collected day
ages every open exception. Worth knowing before re-running a day for any reason
other than data recovery.
