# v1.1.26 — 2026-06-16

**Brief `valid_until` date correctness** (surfaced reviewing past-midnight / overnight brief runs).

`nextTradingDayOpen()` computes the `valid_until` timestamp persisted on every `daily_briefs` row ("next trading day 9:30am ET"). It had two date-handling bugs:

1. **UTC-date base skipped a trading day on evening-ET runs.** It seeded the search from the **UTC** date of `generated_at` and incremented at least one day. An evening-ET run is already "tomorrow" in UTC — a Monday 8:57pm EDT brief is `2026-06-16T00:57Z` — so the search started from the 16th and rolled to the 17th, marking a Monday-evening brief valid until **Wednesday** instead of **Tuesday**.

2. **Hardcoded EDT offset was an hour early all winter.** It set 9:30 ET as `13:30Z`, true only under EDT (UTC−4). Under EST (UTC−5) 9:30 ET is `14:30Z`, so every winter brief's `valid_until` was an hour early.

## Fix

`nextTradingDayOpen()` now:
- Keys the search off the **ET calendar date** of `generated_at` (`toLocaleDateString('en-CA', { timeZone: 'America/New_York' })`), advancing the ET date to the next trading day (noon-UTC anchor keeps the date arithmetic DST-safe).
- Builds the 9:30-ET instant **DST-aware** via `etUtcOffsetMinutes(target)` (EDT −240 → 13:30Z, EST −300 → 14:30Z).

Impact is cosmetic: `valid_until` drives the "valid until" label and the same-ET-day auto-supersede timing only — it never touches pick data. No other behavior changes.

## Tests
`tests/next-trading-day-open.test.ts` (+6): evening-ET run does not skip a day; daytime run rolls forward; winter (EST) instant is `14:30Z`; weekend (Fri→Mon) and holiday+weekend (Thu before Juneteenth → Mon) skips; host-timezone independence. Full suite: 504 passing.

## Context

Came up answering "will the daily brief have data issues running past midnight?" Conclusion: the brief's date logic is otherwise sound — it computes "today" in ET, June 16 is a normal trading day, and it uses prior-session data by design. The real overnight gotcha is unrelated to dates: **E\*Trade tokens hard-expire at midnight ET**, so a post-midnight run fail-safe skips Stage 4 with a "reconnect" message rather than producing bad data. This release just removes the one genuine (cosmetic) date bug found in passing.
