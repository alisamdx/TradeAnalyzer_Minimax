## QC-008 and QC-601 re-judge their stale findings under today's rules

### Problem

Both checks judge only the current run. QC-008 reads the capped responses this run received, and QC-601 compares the latest two earnings sweeps. A finding raised by an earlier run is therefore never evaluated again. It stays open by design (P9), and nothing could close it. On the 2026-09-18 snapshot that was 18 QC-008 and 9 QC-601 findings, all raised under rules since corrected.

### Fix — QC-601 (`rejudgeSlipFindings`)

For each open finding not evaluated today, the current rule is applied to every consecutive sweep pair whose later run falls between the finding's first and last seen runs. The rule compares the nearest future date per run and excuses a roll after the issuer reported. If no pair would fire, the finding came from the first rule, which read two windows of one sweep as successive observations, and it closes `rule_changed` with the runs and pair count in the note. If any pair fires, it is a real slip and stays open, whatever the latest sweep says.

The nine on gen-002, with the nearest date per sweep:

| finding | nearest date across runs 8, 12, 13, 16, 19, 22 |
|---|---|
| AZO, FERG, THO | 2026-09-22 throughout |
| COST | 2026-09-24 throughout |
| MTN | 2026-09-28 throughout |
| JBL, MU | 2026-09-30 throughout |
| LEN | 2026-09-16, then 2026-12-14 from run 19 (reported 09-16: a roll) |
| GIS | 2026-09-15, then 2026-12-15 from run 19 (reported 09-15: a roll) |

### Fix — QC-008 (`rejudgeCapFindings`)

For each open finding from an earlier run (its key is a `source_response_id`):

- a capped `from`/`to` window is judged by the v1.1.252 rule against **its own run's** uncapped responses; re-covered day by day → `rule_changed`;
- a submissions response whose ticker's current reference is a fund type → `rule_changed`, since the EDGAR sweep has not asked for funds since v1.1.275.

What the database cannot settle stays open. A stock's submissions list is "capped" when EDGAR's `recent` block does not reach back to the lookback date, and that is the oldest `filingDate` in the response body. The body lives only in the encrypted archive, which a check cannot read. JEF and JPM were read complete by hand in v1.1.275 and need the operator's `false_positive` ruling.

`coveredBySubdivision` is the same coverage test as before, extracted so it can be applied to any run.
