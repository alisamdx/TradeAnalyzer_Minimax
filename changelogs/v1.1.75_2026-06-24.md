# v1.1.75 — 2026-06-24

## Earnings calendar: keep the *nearest* future earnings date (real-money risk fix)

### Symptom
During the iterative Daily Brief accuracy deep-dive (round 9), several actively-reporting
names in the latest brief showed a **November** "next earnings" date while clearly skipping
their **August** quarter:

| Ticker | Finnhub returns | DB stored (wrong) | True next |
|--------|-----------------|-------------------|-----------|
| NVDA   | 2026-08-25, 2026-11-17 | 2026-11-17 | 2026-08-25 |
| MRVL   | 2026-08-26, 2026-11-30 | 2026-11-30 | 2026-08-26 |
| AMAT   | 2026-08-13, 2026-11-12 | 2026-11-12 | 2026-08-13 |
| ADI    | 2026-08-18, 2026-11-23 | 2026-11-23 | 2026-08-18 |

(Confirmed by querying Finnhub directly with the configured key — both dates exist; the DB
kept the later one.)

### Root cause
`EarningsRefreshJob` Phase 1 (bulk pre-fill) fetches Finnhub in two ordered windows —
`today→+90d`, then `+90d→+180d` — and `EarningsService.upsert` overwrites the single
per-ticker row unconditionally (`ON CONFLICT(ticker) DO UPDATE SET report_date = excluded.report_date`).
A quarterly reporter appears in **both** windows (the next report in 0–90d, the one after in
90–180d), so **window 2's later date overwrites window 1's nearer date**. The calendar ended
up storing the *following* quarter and silently dropping the *next* earnings.

### Why it matters (blast radius)
`earnings_calendar` is keyed by ticker (one row each), and three consumers all read that one
row for the nearest future date:
- **v2 execution entry gate** — `brief-entry-source` `earningsBeforeExpiry` (the engine's
  earnings risk gate for inflection / wheel / income short-premium structures).
- **Critic** — `getEarningsBeforeExpiry` / `earnings_in_window` flag.
- **Brief Stage-3 scoring** — `loadEarningsPenalty` (−20 composite for earnings within 45d on
  income/wheel/bearish).

With the nearer date dropped, all three could conclude "no earnings before expiry" when an
earnings report actually falls inside the option's life — exactly the catastrophic event the
premium-selling book must avoid (sell a credit spread / iron condor straight through earnings).
Today's brief was unharmed only by luck: all picks' July expiries clear even the true August
dates, so the bug was latent, not biting.

### Fix
`src/main/services/jobs/earnings-refresh-job.ts` — Phase 1 now keeps the **nearest** future
date: it ignores past/today candidates and skips a candidate whose date is on/after an
already-stored future date, so window 2 can no longer push out window 1. This matches the
per-ticker Phase-2 path, which already sorted ascending and kept `entries[0]`. The existing
poisoned rows self-heal on the next Earnings Refresh run (runs on startup + after-close),
since window 1 will now (re)write the nearer date and window 2 will skip it.
