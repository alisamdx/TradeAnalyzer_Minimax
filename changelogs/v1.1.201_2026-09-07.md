# v1.1.201 — 2026-09-07

## The NewApp collector's universe came from the wrong place

### What happened

The first live `universe_seed` succeeded mechanically — queue → claim → run,
**2,096 Polygon calls, every one a 200**, membership reconciled, archive
written. It captured **the wrong 2,000 tickers**.

`NEW_APP_UNIVERSE_SOURCES` asked Polygon for `market=stocks&type=CS` and
`type=ETF` with `limit=1000`, under the list names `sp500` and `etf_list`. Two
faults, compounding:

1. **No index filter.** Polygon has no index-membership endpoint on this plan,
   so the query returned *every* US common stock. The list names were
   aspirational, and neither the code nor the response contradicted them.
2. **No paging.** `limit=1000` returns one page; Polygon pages with `next_url`,
   and `parseTickers` read a single `results[]`.

Measured on the live run: **2,000 tickers in alphabetical order, A through
DBND** — `AAAA`, `AACI` and every microcap in between — while **MSFT, NVDA,
TSLA, SPY, GOOGL, META, JPM, XOM and WMT were all absent**.

This is the Finnhub cap trap in a second place: a response at the cap is not a
complete answer. Here nothing looked at the cap at all.

### The fix

**The correct lists were never remote.** They are in this application's own
`constituents` table — 503 sp500, 1,024 russell1000, 60 etf, **1,089 distinct
across 1,587 rows**, exactly the figure NewApp 04 §4.1 records — and the
`constituents-refresh` job already maintains them (Vanguard-first, CSV import as
the manual override).

`newAppUniverseSources(db)` reads those lists and serialises each as its own
response, archived and digested through the same capture contract as any
provider call (P2, AC-1). The archive records *what we were given*, and the
host's curated list as of that moment is a legitimate answer to that. A new
`host_app` provider value carries the attribution, because calling it Polygon
would be a lie in the one column that says where a row came from.

A single empty list is refused rather than returned: `universe_seed` reconciles
membership against what it is given, so an empty set would read as "every member
of this list has left".

### Recovery

No reset needed. `reconcileMembership` closes members absent from an incoming
list, so a corrected seed closes the 2,000 wrong memberships and opens the right
ones. The stray `raw_ticker_reference` rows stay — that is what append-only
means, and they are true observations of tickers that were briefly in the
universe.

### The validation rule this leaves behind

A list source must be validated on its **content**, not its status code.
"1,000 rows, HTTP 200" is what both the right and the wrong answer look like.
