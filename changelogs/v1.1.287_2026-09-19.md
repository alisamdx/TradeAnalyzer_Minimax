### QC-203: a check that could not pass

Spec 02 (`is_final`: "0 if fetched before Polygon's settlement window closed for that date (before ~17:00 ET)") and spec 04 ("`is_final` is set from `respondedAt ≥ 17:00 ET`") agree. `runBarsPhase` instead passed `provisionalDate: run.tradingDate` unconditionally, so every same-day bar was stored `is_final = 0`, whatever time it arrived. QC-203 then fired on 100 % of bars on every run: run 8 fetched at 17:59 ET, run 22 at 18:23. The final version of a bar arrived only with the next day's five-day fetch. It was invisible as a defect because the check reported a fraction that never moved, one warning among dozens.

**Fix.** `barSettled(tradingDate, respondedAt)` in `collector/bar-settlement.ts` returns true when the response arrived on a later ET date, or on the trading date at or after `BAR_SETTLED_AT_ET` = 17:00. The ET wall clock comes from `etTimestamp`, so the boundary holds under EDT and EST alike; a null or unparseable time returns false. `runBarsPhase` sets `provisionalDate` only when the response is not settled. The recipe records the decision, so a replay of the response parses it identically.

**Stale findings.** QC-203 findings are keyed by trading date, and the check evaluates only the current date. `rejudgeNonFinalFindings` looks at every bar response (`/v2/aggs/ticker/…/range/1/day/…`) in the runs that raised a finding for an earlier date. If every one arrived settled, the current rule would have stored the bars final, so the finding closes `rule_changed` with the arrival window in the note. Any pre-17:00 arrival (a morning run) keeps it open.

`barSettled` lives in its own module so the QA check need not import the bars phase.

**Not built:** R3, re-fetching a genuinely provisional bar before run end. A run before 17:00 ET still leaves its same-day bar provisional until the next day's fetch, and QC-203 says so.
