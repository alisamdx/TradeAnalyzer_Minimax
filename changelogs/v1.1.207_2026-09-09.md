# v1.1.207 — 2026-09-09

## fix — the generation diagnostic was describing the wrong file

`diagnose-generation.mjs` probed for the `%APPDATA%` redirect, printed the
verdict, and then printed the pointer contents, the derived database path, its
size, its modification time, its `-wal`/`-shm` state and the list of generations.
**Every one of those is read through `%APPDATA%`, and under a redirect
`%APPDATA%` is served from the container.** Once the container holds a
copy-on-written shadow of a file, those lines describe the shadow.

Measured 2026-09-09: the tool reported `data.sqlite` at **1,789,952 bytes,
modified 2026-09-07 23:05, no sidecars**. The container's own copy is
byte-for-byte that size and timestamp — while the collector had been running
against the real file the following evening. Every number was true and every one
answered a different question.

It now refuses **at the probe**, before a single line about the generation, names
the two commands that produce a real answer, and then prints the container's own
copy under a heading saying that is what it is.

**"We refuse before opening" sounded sufficient and was not.** The reading was
already wrong long before the open. A diagnostic that cannot see its subject must
say so and stop; what it must never do is describe something else in the same
format and leave the reader to notice. This is the second confident wrong answer
from this tool — the first is already in CLAUDE.md.

## fix — and then it died on the input it exists to describe

Run against a genuinely damaged file, the diagnostic threw a raw `better-sqlite3`
stack out of the `sqlite_master` read — **before any of its report existed**.
That reads as *the script broke*, not *the database is damaged*. Its own header
warns about precisely that failure, and the query sat outside the guard anyway.

Everything is guarded now and integrity comes first. Three further things it was
getting wrong, each found by running it against a corrupted fixture rather than
by reading it:

- **An unreadable schema was reported as zero tables**, which fell into the
  "NO SCHEMA — something created the file without applying the dictionary"
  branch, whose advice ends in `Remove-Item -Recurse -Force`. So a badly damaged
  generation would have been described as an empty one and recommended for
  deletion. Same shape as `decrypt()` returning `''` for "could not decrypt"
  (v1.1.200): **a catch that returns the same value as "absent" destroys the
  distinction that names the fault** — and here it does so pointing at a delete.
- **Recovery is `Rename-Item`, never `Remove-Item`.** A generation is cheap to
  rebuild by re-running the jobs; the corrupt file is the only record of how it
  broke and is not reproducible at all. The rename keeps the directory's own name
  instead of hardcoding `gen-001`.
- **`meta_open_handle` and the row counts are read even when the file is
  corrupt**, each guarded on its own, because damage in one btree says nothing
  about whether another is readable. They were skipped in exactly the case they
  exist for.

Two additions that came out of the same session:

- **`Tree N` is resolved to an object name** via `sqlite_master.rootpage` in the
  file being examined. A tree number is only meaningful against the schema
  version that produced it — `Tree 5` and `Tree 7` were the same table across a
  dictionary bump, and reading them as two kept the 2026-09-07 diagnosis pointing
  the wrong way for an evening. Verified on a fixture: `Tree 291: table
  bulk_payload`.
- **An explicit generation path** (`diagnose-generation.mjs "<dir>"`), so a
  *retired* generation can be examined at all. The whole point of renaming a
  corrupt one aside is to keep it, and the only tool that can read it could open
  nothing but the one the pointer named. The redirect probe correspondingly
  measures **the directory being examined** rather than `%APPDATA%` globally —
  the redirect is per file, and a target under `C:	emp` is not redirected by
  anything. That is the same correction already made in
  `lib/generation-access.mjs`.

When more than one `db_path` appears in `meta_open_handle`, the report now says
so in as many words: that is a split file set, and it is the one mechanism anyone
has shown can corrupt this database.

## fix — the ABI-swap lock guard could never fire

`rebuild-better-sqlite3.mjs` has carried a friendly EBUSY message since the day a
running app first broke `npm test`. It has never been reachable.

It matched `/EBUSY|resource busy or locked|EPERM/` against `err.message` — but
the call uses `stdio: 'inherit'`, so `prebuild-install`'s output goes straight to
the console and `err.message` is only ever `Command failed: npx prebuild-install
--runtime node --force`. **The word EBUSY was on the screen and never in the
string being tested.** Found by hitting exactly the case it was written for: a
background replay harness held the binary loaded, `pretest` tried to swap it, and
the raw `execSync` stack came out.

Now it asks the **file** — `openSync(binary, 'r+')`, since Windows maps a loaded
`.node` as an executable image and refuses to open it for writing — and it asks
*before* `prebuild-install` downloads anything. The message names the third
culprit too, which is the one that bit: a harness left running in the background,
not just the apps or `npm run dev`. The regex is kept as a second path but is no
longer the only one. **A guard whose input cannot contain what it looks for is
not a guard.**

## fix — the replay's paced arm did not pace, it stalled

The inter-write delay used `Atomics.wait`, chosen deliberately so the block would
be synchronous: an `await` would "hand the loop back and change the shape of what
is being tested". Wrong twice.

- **Fidelity.** The live collector waits on a real HTTP response, which is
  asynchronous. Yielding the loop between writes is the faithful model; blocking
  it is the artificial one.
- **Function.** Parking the *Electron main thread* in `Atomics.wait` stops libuv
  running its callbacks, so the seed's own async continuations never resume. The
  paced arm used **1.9 seconds of CPU in 17 minutes** and produced no output.

The comment guarded against the opposite failure — an arm that "ran at full speed
while reporting a pace". The real one was worse and in the other direction.

With `await new Promise(r => setTimeout(r, ms))` the arm runs: **1,089 responses
at 250 ms = 285.5 s, integrity ok**, identical row counts and WAL size to the
unpaced run. That closes the last removable difference between the replay and a
live seed.

## docs — the redirect is back on the corruption suspect list

**A copy-on-write shadow of `gen-001/data.sqlite` exists in the tooling
container** — 1,789,952 bytes, **created 2026-09-06 17:47 ET, modified 2026-09-07
23:05 ET**. Windows creates that copy at the moment a redirected process first
*writes* to the path, so those two timestamps bound a ~30-hour window of
redirected writing that spans every corruption event and continues **after** the
redirect guard shipped in both applications.

That removes the basis for eliminating the redirect, which rested entirely on
*"the corruption recurred on a shell verified clean"*. The shell was never probed
and is not clean — it is this session's own, and it is MSIX-containerised.

**It does not establish a cause.** Which process wrote the copy is unknown:
`exception.mjs` (unguarded until 2026-09-08), the earlier unguarded versions of
`queue-job.mjs` / `diagnose-generation.mjs`, or either application launched from
inside the container — both have full Electron profiles there. Recorded as
evidence, not as a verdict. Promoting a corroborating detail to a premise is how
the last two diagnoses went wrong, and this file already says so.

### Where the investigation stands

Everything reproducible offline is clean — the collector code path, the Electron
runtime and ABI, real `safeStorage`, the real schema at the real pace, and the
environment. **The next step is not another elimination.** It is to read what the
real `gen-001` says from a shell that can see it: `PRAGMA integrity_check`, and
`meta_open_handle`, which records every application that opened the generation
and the `db_path` each resolved. Two different `db_path` values would show the
split directly instead of by inference. That table was added for this question
and has never been read.
