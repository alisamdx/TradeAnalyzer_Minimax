# v1.1.269 — 2026-09-18

`core` 0.6.24, `next` 0.4.12 (TradeAnalyzer 2 has no code change; rebuilt to bundle the new core).

## BRK.B pins could never be honoured

**What QC-409 said on 2026-09-18:** `BRK.B-261016P00495000 is pinned (recommended_by_legacy) but has no snapshot for 2026-09-18` — and the same for the 510 put. Both blocking.

**What actually happened.** The Oct 16 BRK.B chain was fetched (HTTP 200, 84 KB) and stored. E\*Trade roots every BRK.B contract `BRKB--` — all **8,850** BRK.B rows in `raw_option_contract_snapshot` — while `osiSymbol()` kept the class-share dot and built `BRK.B-…`. A pin is matched to a snapshot by equality on `osi_symbol`, so the pin could never match. Same failure the v1.1.248 padding fix described: a constructed identifier that must equal a received one.

**Fix.** `osiRoot(ticker)` — alphanumerics only, dash-padded to six — used by `osiSymbol()`. BRK.B is the only dotted ticker in the chain subset, so the dot is the measured case; stripping every non-alphanumeric follows the OCC specification, whose roots are alphanumeric. The existing `repairStickyOsiPadding` now compares every open pin's root with `osiRoot(ticker)` instead of looking for a space, so it re-roots the two open BRK.B pins on the next run (close + reopen, provenance kept) and covers the old space padding too.

## Two faults found beside it

**Held pins were written space-padded every run.** `deriveHeldStickyContracts` copied `raw_account_position_snapshot.osi_symbol`, which the account parser builds in OCC's *space*-padded form (`AMD   261016P00520000`). The chain phase's repair then closed it the same day. Visible in gen-002: every `held_in_book` pin opened and closed on one date. The pin is now built with `osiSymbol()` from the position's ticker, expiration, right and strike. **The raw column is deliberately unchanged**: it is parser output, and changing the parser would make every replay of an earlier day read `different` (QC-951, blocking).

**The repair dropped a held pin's reason.** It skipped reopening when the corrected symbol was open under *any* reason. AMD's held 520 put was also recommended on 2026-09-18, so the held pin was closed and not reopened. The contract was still captured, but the record that it was held was lost. The repair now keys per `(osi_symbol, reason)`, as `deriveHeldStickyContracts` does.

## Expected on the next run (2026-09-21)

QC-409's two BRK.B findings stop firing. `stickyRepadded` is 2 (the BRK.B pins) plus any held pin still open in the space form. No new space-padded `held_in_book` pins.
