# v1.1.368 — 2026-10-15

## fix: Daily IV Update asks E*Trade for dotted share-class tickers

**Symptom.** TA1's `iv_history` had exactly five readings (2026-06-01..06-05) for BRK.B, BF.A, BF.B and HEI.A, and none ever for LEN.B or UHAL.B. GOOGL, the control, had 347 through 2026-10-15. Daily bars for all six were current. IV rank and IV percentile for these names were computed on a series that stopped in June.

**Root cause.** v0.23.9 (commit 33423e7, 2026-06-05 18:11 ET) added a pre-filter to `daily-iv-capture.ts` that skipped every ticker containing a dot, before any E*Trade call, with the message "Class share — no listed options". Its premise was wrong. On 2026-10-14, other paths (Strategy Lab, collector) asked E*Trade for these chains, and `logs/api` shows option expirations and option chains answered **HTTP 200** for BRK.B (93 KB chain), BF.A, BF.B, HEI.A and UHAL.B. Only LEN.B really has no options (`optionexpiredate` → 204, `optionchains` → 400 `10032`). The five June readings are the runs before the filter shipped. The write path (`IvHistoryService.captureFromEtradeChain` / `storeReading`) handles a dotted ticker correctly. Nothing needed changing there.

**Fix.**
- Removed the pre-filter. A dotted ticker is asked like any other. One with no options (LEN.B) is still skipped, through the existing no-options error path, now also matched on E*Trade's `10032` code.
- **Skip reasons are logged.** Every skip records its ticker and reason (`no listed options`, `no expirations`, `could not compute ATM IV from chain`). The list is appended to the job's result notes, up to 40 names and then "… and N more". The `batch-run:daily-iv-update` line in `logs/errors` carries it. Before this, the "11 skipped" in each run's notes named nothing.

**Not backfilled.** The June 8 – October 15 gap stays. A new reading appears from the next run. IV rank for these five names stays thin until history builds up again, or until the IVolatility bootstrap covers them.

**Test.** `tests/daily-iv-capture-dotted-tickers.test.ts` runs the job over BRK.B and LEN.B with the real `IvHistoryService`. It asserts that BRK.B is asked and stored under the dotted ticker, and that LEN.B's skip reason appears in the notes. It fails on the old code at `expected "spy" to be called with arguments: [ 'BRK.B' ]`.
