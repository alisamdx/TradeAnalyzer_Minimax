## What T7 measured

`scripts/fr-spread-pool-selection-study.mjs`, 6,221 settled rows over 54 dates, top-15,
episode-collapsed, against **a random draw of the same size on the same dates** — the null T5 and T6 both
lacked. "Beats the universe mean" is the wrong test for a top-N rule, because a small N carries sampling
noise a whole-universe mean does not.

| rule | mean | median | trimmed | assigned |
|---|---|---|---|---|
| random band (5th–95th) | −1.29 … −0.52 | 1.14 … 1.34 | −0.34 … 0.30 | 29.3 … 34.7 |
| **premium richness** | **+0.54** | **2.86** | **1.48** | 31.0 |
| composite-70 (the live cut) | −0.12 | 2.02 | 0.79 | 30.3 |
| income-72 | −0.56 | 1.67 | 0.46 | 32.7 |
| ivRank + premiumYield (41 pts) | −0.17 | 2.40 | 0.99 | 30.6 |
| **ivRank only** | **−1.01** | 1.79 | 0.06 | 31.6 |
| the 29 price-derived points | −1.32 | 0.86 | −0.39 | 34.4 |
| inverted composite-70 | −1.50 | 1.14 | −0.66 | 33.4 |

**Three findings.**

1. **The cut earns something and is dominated.** composite-70 clears the null on all three return
   measures, so it is not decoration — but premium richness beats it by 0.66pp mean and 0.84pp median.
   Exactly the shape F8/T5/T6 predicted: 19 of 91 points carry it, the rest dilute.
2. **`ivRank` — the composite's largest weight at 22 — is inside the random band**, and adding it to
   `premiumYield` made the pair *worse* than `premiumYield` alone (−0.17 vs +0.54). T5 read it as weakly
   positive against "no selection"; against a same-size random draw it is chance. **Unresolvable from
   stored data:** `iv_history` is the IVolatility→E\*Trade splice with zero overlapping ticker-days, so
   this may be a broken input rather than a broken signal, and no further analysis separates the two.
3. **No rule moves the assigned rate.** Every one sits inside 29.3–34.7%. That confirms the parked
   "the composite is disconnected from the win condition" thread on 6,221 rows rather than a quintile
   sketch, and it is the finding that matters here: **selection changes how much credit you collect, not
   how often you are breached.** What premium richness buys is more credit at unchanged breach risk — a
   real VRP edge, and not circular precisely because assignment stayed flat while return rose.

**income-72 was the surprise.** BPS-1's structural argument — that income carries no ownership weight and
so should suit a defined-risk trade better — was right about the weights and wrong about the outcome: it
is worse than the incumbent on all four measures and its mean falls back inside the random band. The
direction was predicted before the run (ivRank is 42% of income-72 against wheel's 31%), but **that is not
claimed as the mechanism** — a plausible story read off a weight table is what v1.1.173 did and v1.1.176
refuted. The income arm keeps running anyway: this is a CSP proxy on one regime, and it costs nothing.

## The third arm

`premium` is now a pool alongside `wheel` and `income` (08 S12). It is **not a brief strategy**: it has no
`brief_candidates` rows and no critic brief of its own. Its tickers are the whole universe ranked by
annualized premium return out of `analysis_snapshots`, gated on liquidity ≥ 5/10 and price ≤ $750 so all
three pools face the same universe, top 15 to match the others' size.

`DailyOptionsSnapshotJob` already fetches a live E\*Trade chain for ~1,100 tickers nightly to fill that
table, so **the pool costs no new market data** — only the spread chain capture for its names, which is
the ~60 extra calls per run the operator accepted.

Two asymmetries, both stated rather than hidden, because they bias the very comparison the arm exists to
make:

- **Critic coverage.** With no brief of its own, `premium` takes verdicts from every strategy's latest
  brief; a ticker no brief covers carries no verdict, so the critic gate cannot bind on it.
- **T7's advantage is a CSP's return on CAPITAL**, which is not a spread's return on MAX LOSS. The
  assignment finding transfers; the return finding does not transfer automatically. That is what this arm
  is for.

## One resolver, two callers

`spread-pools.ts` `resolvePoolTickers()` is the single choke point. `spread-chain-capture.ts` decides whose
chains get fetched and `spread-mode.ts` decides whose spreads get built, and if those two disagreed the
premium arm would produce nothing and read as **a screen with no candidates rather than a plumbing gap**.
Fifth write-up of one shape in this project — a capability that must apply to every caller belongs in the
function they all call, not copied into each one.

Two small decisions inside it worth keeping: a row with no annualized return is **skipped, not sorted as
zero** (absent is not the same as worst, and a fabricated zero would quietly fill the pool with names
carrying no premium data), and ties break by ticker rather than by the snapshot's storage order, which is
not a documented property and would let a rank drift with no signal changing.

## Migration 087 — the enum trap, one day later

086 wrote `CHECK (pool IN ('wheel','income'))` yesterday. SQLite bakes a CHECK in at CREATE TABLE time and
there is no ALTER that widens it, so admitting a third value takes a full table rebuild. That is exactly
the `enumOf` trap in CLAUDE.md — **widening an enum changes no column name**, so a column-comparison guard
sees nothing and the failure would surface as a constraint violation inside an unrelated transaction long
afterwards.

Verified against the real 084+086 schema before shipping: rows preserved byte-identically, `premium`
accepted, an unknown pool still refused, and both indexes rebuilt. `spread_mode_picks` has no foreign-key
children, so the cascade trap (a `PRAGMA foreign_keys=OFF` that is a no-op inside a migration's
transaction) does not apply — a table with children would have needed the child copied aside first. Every
existing row already satisfies the wider constraint, so the copy cannot fail; a rebuild that can fail on
its own copy means the app does not boot.

## Note on the paired window

`pools.pairedFrom` requires **every** arm to have run on a date, so adding a third arm would normally reset
the comparison. It costs nothing here: `income` shipped in v1.1.301 and has not run yet either, so all
three arms start together on the next brief.
