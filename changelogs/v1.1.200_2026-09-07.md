# v1.1.200 — 2026-09-07

## A boot that cannot read its credentials now says so

### The bug

`secure-settings.decrypt()` swallowed a `safeStorage` failure and returned an
empty string:

```ts
catch {
  // Decryption failed (e.g. different OS user, corrupted value) — return empty
  return '';
}
```

So a start where the OS credential store was not ready came up with **every**
secret silently blank — Polygon, E*Trade, Anthropic — and the app ran
credential-less. Every provider call failed as unauthorised, which looks exactly
like a revoked key or a provider outage.

**Measured 2026-09-07:** 32 keyless Polygon 401s in one afternoon, against 38
successes from healthy starts of the same binary with the same stored key. The
API log distinguishes them perfectly and only in hindsight: a successful call
logs `"apiKey": "[REDACTED]"` in `requestParams`, a failing one logs
`requestParams: {}`. The operator already knew the workaround — close the app
and start it again — without knowing the cause.

**An absent setting and an unreadable one are different facts**, and collapsing
them removed the only evidence that would have named this in minutes.

### The fix

- `decrypt()` records the key in an `undecryptableKeys()` set instead of
  discarding the failure. The read still returns `''`, so no call site changes
  behaviour.
- Startup checks that set after `migratePlaintextSecrets` and, if it is
  non-empty, writes an `ERROR` to `logs/errors/` **and shows a dialog** naming
  the affected keys and telling the operator to restart.
- Unavailable-store and failed-decrypt are recorded alike but described
  differently: the remedy for one is a restart, for the other re-entering a key.

`tests/secure-settings-undecryptable.test.ts` — 7 cases, including the two that
must **not** record (a genuinely unset key, and a legacy plain-text value).

## Startup failures are no longer silent

`app.whenReady().then(...)` had **no `.catch()`** — the same shape found and
fixed in the new exe earlier today. A throw anywhere in startup became an
unhandled rejection warning on a stderr nobody reads, and everything registered
after the throw simply did not exist, with no error and a window that looked
fine. It now logs and shows a dialog.

The NewApp collector block is additionally wrapped in its own `try`/`catch`,
because it is registered **last** on purpose (`sequence_order` is frozen from
registration order), which makes it the first casualty of any earlier throw —
and its absence is indistinguishable from it never having been written.

## The collector claim loop reports what it sees

A queued `meta_job_request` row sat unclaimed through a dozen two-minute ticks
while the handler reported `No queued jobs.`, with no way to tell whether it was
reading the wrong database, holding a stale snapshot, or genuinely seeing an
empty table. Those want three different fixes and the note distinguished none of
them.

- Every tick now writes an `INFO` line to `logs/errors/` with the resolved
  `dataRoot`, generation number, and the total/queued/max-id of
  `meta_job_request`.
- The `batch_runs` note carries the same counts, so the batch history alone is
  diagnostic.
- The interval body is wrapped: `readSharedPointer()` **throws** on a malformed
  pointer, and an uncaught throw there produced no `batch_runs` row at all — a
  loop that looks stopped rather than failing, every two minutes, silently.

`ErrorLevel` gains `INFO` so the log can record that something **did** happen.
A file that only holds problems cannot answer "did the collector start?" —
absence there means both "fine" and "never ran".
