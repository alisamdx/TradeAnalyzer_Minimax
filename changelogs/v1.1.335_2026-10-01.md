# v1.1.335 — 2026-10-01

## Every way the app can end now leaves a record

**What happened.** On 2026-09-28 TradeAnalyzer went silent at **10:41:54 ET**, partway through the
morning brief (its last call was DDS's `optionexpiredate`, an ordinary HTTP 204), and was next
started at **07:52 ET on 09-29**. The 17:05 data-collector, the 19:30 watchdog and the after-close
batch all need the app running, so none ran — which is why `derived_iv30_daily` has no 09-28 row
and the stale-greek shadow log has no 09-28 after-close picks. The operator did not close it.

**Why it could not be diagnosed.** Nothing distinguished a quit, a crash and a freeze:
- a normal quit wrote nothing to `logs/errors`;
- the main process had no `uncaughtException` / `unhandledRejection` handler;
- the ~90-minute E*Trade keep-alive also stopped, so the main event loop was not running — but a
  frozen main thread cannot log its own freeze;
- Windows recorded no crash (WER), hang, sleep or shutdown in that window.

**Change.**
- **Session sentinel** (`services/session-sentinel.ts`): `logs/session.json` holds
  `{ pid, appVersion, startedAt, lastAliveAt, cleanExit }`, refreshed every 60 s. At boot, a previous
  record without `cleanExit` logs `app:previous-session` (WARNING) naming the pid, version and **last
  alive time** — so a freeze or kill is reported by the next session, bounded to one heartbeat.
- **Lifecycle lines in `logs/errors`**, written **synchronously** (`logErrorSync`) because the process
  may not outlive them: `app:start`, `app:quit`, `app:session-end` (Windows logoff/shutdown, which
  skips `before-quit`), `main:uncaught-exception` (FATAL, with stack; Electron's error dialog is
  still shown), `main:unhandled-rejection` (ERROR, still non-fatal), `app:render-process-gone`,
  `app:child-process-gone`, `app:window-unresponsive` / `app:window-responsive`.
- A second instance (which quits at once) does not touch the running session's record.
- `logErrorFromException` stamped every entry `appVersion: '0.1.2'`; it now uses the real version.

**Reading it next time.** `node scripts/day-report.mjs --date <next day>` shows the
`app:previous-session` line. A freeze reads as "last alive" shortly before the API log stops; a clean
quit as `app:quit`; a crash usually also leaves `main:uncaught-exception` or a WER event.

Tests: `tests/session-sentinel.test.ts` (7), including the 09-28 shape — alive until 14:41:54Z,
no clean exit, next boot reports it with that last-alive time.
