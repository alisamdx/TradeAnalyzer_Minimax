## Fix: a run preflight stops closes `cancelled`; the replay's default source must have captured something

**What happened.** Replay request 7 (2026-10-12 01:43) reported `NOTHING_REPLAYABLE — 0/0 responses replayed`. Its default source, "the latest completed daily run", was run 70: a `daily` run dated **Sunday 2026-10-11**, started and finished at 22:52:21 with zero responses. When the app came back at 22:52 Sunday the scheduler ran its missed slots, and preflight correctly stopped `data-collector` ("2026-10-11 is not a trading day"). But `runDaily` created the run before preflight and closed it **`complete`**. Every weekend of the pilot has left one of these: runs 3, 23, 24, 40, 41, 54 and 70.

**The worse half.** The watchdog (`collector-daily.ts`) reads any `complete` daily run for a date as "collection done". Preflight also stops on a closed generation, and a run stopped that way on a *trading* day would have closed `complete` and suppressed the NO RUN email.

**Changes**

1. `runDaily` closes a preflight-stopped run as **`cancelled`**. On a trading day the watchdog then reports "Runs exist but none completed (cancelled)" and emails.
2. `runReplayJob`'s default source is the latest completed daily run **with at least one `meta_response`**. That covers the seven historical rows, which are left as they are.
3. TA2's replay queue refuses an explicit run id that captured nothing, and the job description says so.
4. The reset confirmation's data-day count (`reset.ts`) counts only runs that captured something. The weekend rows had inflated it by seven.
