# v1.1.212 — 2026-09-09

`@tradeanalyzer/core` 0.3.5, dictionary version **8** (unchanged). Migration **081**.

The rate-limiter bypass, deferred since v1.1.196 because it changes the
collector's write pace and the pace was an experimental variable in the
generation-corruption investigation. Three clean seeds later, it is safe to move.

## fix — `polygonGet` called `fetch` directly

`ElectronCollectorHost.polygonGet` made every Polygon call with a bare `fetch`,
against spec 06 §5 change #3 and CLAUDE.md's standing rule. It now takes a token
from **the application's own limiter instance**.

The instance, not a copy. Polygon rate-limits per API key and the collector
shares this app's key, so two buckets would be two independent budgets spending
one allowance — and avoiding exactly that is *why* Q4 chose to host the collector
in this process: one token holder, one limiter.

`acquire(1)` runs **before** the latency clock starts. A queue wait folded into
`responseLatencyMs` would make Polygon look slow precisely when the limiter is
working hardest, in the log that gets read first when a provider path misbehaves.

## fix — the stored rate limit never survived a restart

Found while wiring the above, and the more consequential of the two.

`rateLimiter.setRate()` was called from **one** place: the settings *save*
handler. Nothing read `rateLimitRpm` at startup. So a configured rate applied
until the next restart and then silently reverted to the hardcoded default — the
app ran at a rate its own Settings screen did not show, indefinitely, with no
symptom.

Harmless while every caller was a person clicking. Not harmless now that a
nightly collection budgets itself against a pace.

The limiter is now constructed from the stored value, falling back to the default
when the row is missing or unparseable — never throwing, because it sits on the
path of every provider call and must not be what stops the app booting.

## change — the default Polygon rate is 500 rpm (was 100)

| | calls | at 100 rpm | at 500 rpm |
|---|---|---|---|
| `universe_seed` | ~1,092 | ~11 min | ~2.2 min |
| daily Polygon phases (bars + misc) | ~1,440 | ~14 min | ~3 min |

Both fit the 19:15 ET deadline; only one leaves the headroom NewApp 04 §3 is
relying on. 500 is the limiter's own maximum and roughly **a quarter** of the
~1,900 rpm the collector was measured sustaining, unthrottled, without a single
429.

**Migration 081** moves a stored `rateLimitRpm` of `100` to `500`. That rewrite
is safe *because 100 was the old default*, so a stored 100 is indistinguishable
from never having chosen — every other value, including 50 and 250, is left
exactly as it is. To run at 100 deliberately, set it in Settings; it now
survives a restart, which it did not before.

Settings gains a **500** preset, since a default the presets could not express
would have shown as no preset selected.

## The spec's 600/min was never expressible

NewApp 04 §3 planned Polygon at "600/min (⅓ of observed peak)".
`TokenBucketRateLimiter` clamps to 500 in both its constructor and `setRate`, so
600 would have been silently reduced and the budget was planning against a rate
the code cannot produce. §3 now says 500 and records why.

Its "observed peak" was also measured on an **unthrottled** collector — the
bypass above — so it was never a pace the budget could assume in the first place.
Another drafted number replaced by a measured one, which is the third in this
section alone.
