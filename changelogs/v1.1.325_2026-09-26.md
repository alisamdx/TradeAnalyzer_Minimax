# v1.1.325 — 2026-09-26

`core` 0.6.58 · `next` 0.4.44

## EDGAR report filings come from the daily form index

### What was wrong

The collector's `events_filings` domain read **20 / 0 / 1** stored on
2026-09-23, 09-24 and 09-25 against 20 expected. The rows themselves were
right. What was wrong was **which filers** got asked.

Report filings (10-K, 10-Q, 20-F, 40-F) came from one place only: the
submissions sweep. It asked 20 filers per run, taken at
`(calendar day × 20) mod filers`. That rule had two faults, both measured on
gen-002:

- **Weekends were never asked.** The day number is a calendar day, but the
  collector runs on trading days, so each weekend's two slices (40 filers a
  week), plus every holiday's, were skipped. In any ~51-day cycle about 29 % of
  filers were missed, and a filer could miss two cycles running.
- **The pointer jumped whenever the filer count changed.** v1.1.275 excluded
  funds and duplicate CIKs, which took the list from 1,083 to 1,012 entries.
  That sent the pointer back from L to H, so 2026-09-23..25 re-asked filers
  already read on 09-14..17:

  | run | asked | already asked on | new filings stored |
  | --- | --- | --- | --- |
  | 09-23 | INTU…JAZZ | 15 of 20 on 09-14 | 20, all from the five first-time filers |
  | 09-24 | JBHT…KKR | all 20 on 09-15/16 | 0 |
  | 09-25 | KLAC…LEA | all 20 on 09-16/17 | 1 (KR's 10-Q, filed 09-18) |

After two weeks, only **135 of 1,012** filers had ever been asked. The fact pull
(companyfacts) is triggered by a stored report filing, so a filer the sweep had
not reached had no path to fresh fundamentals.

### The fix

- **The daily form index stores the report filings.** The insider sweep already
  fetches EDGAR's `form.YYYYMMDD.idx` for every session since the last one that
  parsed. That index lists every filing of the day. The same response now
  carries a recipe (`edgar_form_index_filings`) that writes every universe
  operating filer's report filings to `raw_edgar_filing`, a session after
  filing, at no extra call.
  - The recipe holds only that index's candidates and the ones already stored.
  - The index has no period or primary document, so `report_date` and
    `primary_doc` are null on these rows. Nothing reads either column.
  - Each accession is stored once, even when it is listed twice or under a
    co-registrant's CIK. `accession_no` is unique and the capture transaction
    is the whole index, so a repeat would have failed the index and that day's
    insider sweep with it.
- **The insider sweep now runs before the filings and facts sub-phases**, so the
  fact pull sees the same run's new filings.
- **The submissions sweep is now a backstop that asks the filers asked longest
  ago** (`submissionsSlice`, read from `meta_response`, never-asked first).
  There is no pointer to move, it cannot skip a filer, and a second run on the
  same date asks the next twenty.
- `events_filings.stored` counts report filings from both sources.
- QC-701's "no newer filing seen" wording no longer blames the submissions
  slice.

### Checked on real data

Against the live `form.20260924.idx` (3,699 filings, 19 of them report forms)
and the gen-002 filer list, the new parser picks exactly **CPB's 10-K and PAYX's
10-Q**. Neither had been stored by the old sweep.
