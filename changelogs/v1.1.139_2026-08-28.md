# v1.1.139 — 2026-08-28

## fix: `historical_prices` carried unadjusted stock splits

### The bug

Polygon aggregates are fetched with `adjusted=true`, so every response is a correctly
split-adjusted series **as of that fetch**. The corruption came from incremental storage:
`price-gap-fill` re-fetches only a ~3-day window, and older bars are never revisited. When
a split happens later, the bars written before it keep their PRE-split prices while new
bars arrive POST-split — leaving a permanent step change in the middle of the series.

Found 2026-08-28 while marking a quarter of brief picks to market. CRWD fell **74% in one
day** (2026-06-29, a 4:1 split) and manufactured a fake $43k loss in the analysis. A scan of
1,136 tickers over 400 days found **153 discontinuities across 126 tickers**, 35 of them at
a simple split ratio:

```
DD   +203% (1:3)    MRNA +177% (1:3)    HON  +95% (1:2)
CRWD  −74% (4:1)    IESC  −53% (2:1)    MNST −52% (2:1)
```

SPY's largest genuine daily move over the same quarter was **2.58%**.

This is not cosmetic. Any indicator spanning such a date is wrong, which reaches SMA/RSI/ADX,
`volume_surge`, breakout detection, relative strength, the backtest engine, and **Brief
Replay** — the tool FR-SEY-5 requires for validating every trade-logic change.

### Fix

New `src/main/services/split-repair.ts`:

- **`detectDiscontinuities`** (pure) flags consecutive closes where `|close/prev − 1|`
  exceeds `DEFAULT_SPLIT_THRESHOLD` (0.25). Non-positive closes are skipped rather than
  producing an infinite ratio.
- **`detectAndRepairSplits`** re-fetches a flagged ticker's whole stored range (bounded to
  800 days) via the existing `fetchAndStorePrices`, which `INSERT OR REPLACE`s an
  adjusted-to-today series — one pass corrects every bar.
- **Idempotent by construction**: re-fetching a ticker that did not split rewrites
  identical bars, so a false positive costs one API call and changes nothing. The threshold
  is deliberately asymmetric — a false positive is cheap, a false negative silently
  corrupts every indicator spanning that date.
- **Real moves are classified, not re-fetched forever**: a jump that survives the re-fetch
  is genuine (earnings collapse, buyout) and is recorded as `confirmed_real` in the new
  `price_split_repairs` table (migration 068), so the detector skips it on later runs.
  118 of the 153 flagged do not match a simple split ratio and will settle out this way.

Detection reads only stored data, so no new provider API surface was added
(`DataProvider` stays the sole market-data seam).

### Wiring

The repair runs as a second pass inside `daily-price-gap-fill`, which already owns
`historical_prices` freshness — after the gap fill, so it scans the freshest bars. It never
fails the job (a stale-but-present price history beats a halted orchestrator chain), and
outcomes land in the run notes: `Split scan: N repaired, M confirmed real`.

Chain order makes the repair propagate for free: `daily-price-gap-fill` (seq 6) runs before
`daily-technical-signals` (seq 7), so signals are recomputed off repaired prices in the
same run.

`maxRepairs` defaults to 40 per run to bound API usage. With 126 tickers currently flagged
and two orchestrator slots a day, the backlog clears in ~2 days, after which only genuinely
new splits are touched.

### Tests

New `tests/split-repair.test.ts` (8): 4:1 split detected, reverse split detected, ordinary
±17% volatility not flagged, zero-close guarded, split-ratio labelling; then repair
rewrites and records `repaired`, a surviving jump records `confirmed_real` and is **not**
re-fetched on the next run, and a clean series triggers no API call at all. Suite: 981 passed.

### Not fixed here

The corrupt bars still in the DB are repaired by running the job — the Polygon key is
encrypted at rest (`enc:` prefix, Electron `safeStorage`), so the repair can only run inside
the app, not from a script.
