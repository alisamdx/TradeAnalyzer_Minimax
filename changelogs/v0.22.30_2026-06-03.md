# v0.22.30 — 2026-06-03

## Fix: Daily Brief stale data from multiple same-day runs

### Root cause
`persistBrief()` used a plain INSERT. Multiple runs on the same day accumulated
rows in `daily_briefs`. Two symptoms:

1. **UI showed mixed-run data**: `getLatestBrief()` uses `MAX(generated_at) GROUP BY strategy`.
   This correctly returns the latest per strategy, BUT the history view's
   `new Map(displayedBriefs.map(b => [b.strategy, b]))` keeps the *last* array
   element when there are duplicates. Since `getBriefHistory` returns `ORDER BY
   generated_at DESC`, filtering a multi-run day and building the map left the
   *oldest* run's data for each strategy — the opposite of what was intended.

2. **Email vs UI mismatch**: After the v0.22.29 email fix (using `persistedPicks`),
   the email sent the picks just persisted (latest run), while the UI displayed
   a different run's picks.

### Fix
`persistBrief()` now deletes all existing records for the same strategy on the
same ET calendar day before inserting, so only one record per strategy per day
exists. Each run is a clean replacement, not an accumulation.

DST-safe implementation: fetches existing row timestamps, converts each to ET
using `toLocaleDateString('en-CA', { timeZone: 'America/New_York' })`, and
deletes only rows whose ET date matches today. No UTC range math required.

Historical days are preserved — only today's records for the given strategy
are replaced.
