# v1.1.373 — 2026-10-20

## TradeAnalyzer 2: QC-701 back from 72 s to 0.4 s

`core` 0.6.81, `next` 0.4.66.

### What was wrong

v1.1.371 made QC-701's allowance depend on the form and fiscal period of the filer's newest facts. It read them with a correlated subquery (`newest_forms`) over two nested derived tables, `x` (the effective CIK) and `y` (`MAX(period_end)`). SQLite flattened those tables into the outer query, so the subquery's `y.cik` and `y.newest` became the full expressions: the `effectiveCikSql` COALESCE and the MAX subquery over `raw_edgar_fact` (1,009,422 rows). Those were evaluated again in the lookup instead of being read as values. The 2026-10-20 rehearsal timed QC-701 at 72 s, against 0.3 s in the real run, which had used the pre-v1.1.371 query.

### Change

The forms lookup is now its own prepared statement, run once per ticker with the CIK and newest period already computed: `WHERE cik = ? AND period_end = ?`. The ticker/CIK/newest query is the same one as before v1.1.371.

### Verification

On the 2026-10-20 22:44 snapshot, QC-701 took 72,048 ms before and 360 ms after. The old single query and the new two-step version gave the same result on all 344 tickers with facts: the same newest period and the same next-filing cadence, 0 mismatches. Core suite: 790 tests passing. No timing test was added, because a wall-clock bound would be flaky in CI. The existing QC-701 tests in `filing-facts.test.ts` cover the behaviour.
