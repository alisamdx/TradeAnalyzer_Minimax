## The gate closes a `check_error` finding once its check stops throwing

### Problem

A check that throws is recorded as one blocking finding, keyed `check_error`. The gate resolves a stopped finding only on evidence: a successful remediation plus a clean evaluation of the same key, or a key its check can no longer produce (v1.1.273). A recovered check evaluates its real keys and never the key `check_error`, so neither case could apply and the finding stayed open for good. On the 2026-09-18 rehearsal that was QC-604's `check threw: no such column: trade_date`, fixed in v1.1.251 and clean on every run since, and still in the email's BLOCKING section.

### Fix

`runGate` registers a closer for `fingerprint(check, domain, 'check_error')` whenever a check completes without throwing. The existing reconcile step resolves it as `rule_changed`, actor `gate`, with the note *"QC-xxx ran without throwing on this run; the error this finding recorded no longer occurs"*. Whether a check threw is something the gate observes itself, like a retired key shape, so this does not breach the operator-only rule. It applies even when the recovered check evaluates nothing. That case is still reported under "evaluated nothing".

### Tests

`gate.test.ts`: throw then clean resolves the finding (`rule_changed`, gate event); throw then empty also resolves it; throw then throw stays open. The first two fail on v1.1.288.

## Existing app: chains are requested only for expirations the ticker lists

### Problem

`AnalysisService.getNearTermExpirations` guessed a fixed run of Fridays for every ticker and requested a chain for each one inside the DTE window. On 2026-09-18, **5,295** E*Trade `optionchains` calls came back 400 (2,644 for 2026-10-30, 2,643 for 2026-10-23, the rest code 10032 on non-optionable symbols), across 671 tickers that list only monthlies. Nearly all were in `daily-options-snapshot` and `daily-options-premium-history`, and the latter took 38 minutes, which pushed the collector's start to 18:23 ET. The mechanism was diagnosed on 2026-09-05 (NewApp 04 §10) and was still running.

### Fix

New `ListedExpirationFilter`, used by `getNearTermExpirations` whenever an `OptionsProvider` is wired. It fetches the ticker's `optionexpiredate` list once per ET day and keeps only the guessed dates in it.

- It only **removes** dates, so every chain fetched before is still fetched, in the same order, and the chosen contract is unchanged. Nothing about which trades are recommended changes, so FR-SEY-5 does not apply.
- A throw, or an empty list (a transient HTTP 204 looks the same as "none"), falls back to the guesses (the old behaviour) and is not cached.
- Cost: one expirations call per ticker per day, shared by the wheel snapshot, premium history and interactive analyses. Net saving on 2026-09-18's figures: roughly 5,300 − 1,360 ≈ 3,900 calls a day.

### Tests

`tests/listed-expiration-filter.test.ts`: a monthly-only listing drops the weeklies; a weekly-listing ticker keeps every guess and gains none; a listed holiday-Thursday is kept; a throw and an empty list both fall back without caching; one fetch per ticker per ET day, again the next day.
