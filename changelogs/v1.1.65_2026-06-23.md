# v1.1.65 — 2026-06-23

## Capture TWS order-rejection reasons (orders were ending `cancelled` with no reason)

### Symptom
After the v1.1.62 eTradeOnly/firmQuoteOnly fix, the engine's combo orders finally reached TWS — but
every one came back `cancelled` with `reject_reason = NULL` (orders #1/#2/#3, all AVGO bull-put
verticals). No fills, no positions, and **no clue why** TWS was cancelling them.

### Cause
IBKR reports an order's rejection reason on the **error event**, keyed by the order id — *not* on
`orderStatus`. The broker's `EventName.error` handler only routed errors for **data requests**
(`this.pending`); an order-id error fell through and was silently discarded. Separately,
`onIbkrOrderStatus` set `OrderStatusUpdate.rejectReason` only when the status was the literal
`'rejected'` — a `'Cancelled'`/`'Inactive'` order (what TWS actually sends) carried `null`. So the
reason was lost on both paths and `exec_orders.reject_reason` stayed empty.

### Fix
- **`IbkrExecutionBroker`** — the `EventName.error` handler now matches the error's `reqId` against
  `ordersByBrokerId`; if it's a tracked order, it logs `[ibkr] order N (coid) error — IBKR <code>:
  <message>` and emits an `OrderStatusUpdate` carrying `rejectReason = "IBKR <code>: <message>"`.
- **`OrderManager.handleStatus`** — persists `rejectReason` into `exec_orders.reject_reason` via
  `COALESCE(?, reject_reason)`, so the reason is recorded regardless of whether the error or the
  `orderStatus` event arrives last, and a later null never clobbers a captured reason.

### Why this matters
This is the diagnostic that unblocks the live paper bring-up: the *next* rejected order will record
the exact IBKR reason (e.g. a permission/margin/precautionary/combo-routing code) in
`exec_orders.reject_reason` and the app log, so the actual cause can be fixed precisely instead of
guessed.
