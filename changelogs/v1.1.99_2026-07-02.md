# v1.1.99 — 2026-07-02

## Root cause: E*Trade token renewal never worked (wrong endpoint path)

### The bug
`src/main/services/etrade-auth.ts` defined:

```
const RENEW_TOKEN_PATH = '/v1/oauth/renew_access_token';   // WRONG
```

E*Trade's OAuth endpoints (`request_token`, `access_token`, `renew_access_token`,
`revoke_access_token`) all live under **`/oauth/`**. The `/v1/` prefix is only for the
market/accounts REST APIs (e.g. `/v1/market/optionexpiredate`). The correct path is:

```
const RENEW_TOKEN_PATH = '/oauth/renew_access_token';
```

(Confirmed against E*Trade's docs: https://apisb.etrade.com/docs/api/authorization/renew_access_token.html)

### Why it went unnoticed for so long
- **Renew errors are swallowed everywhere.** `ETradeDataProvider.withRenew`, the daily-iv-update
  connectivity probe, and the batch orchestrator pre-wake all catch the renew error and simply
  retry the real call. So a renew that 404s produces no visible error — the retry just fails and
  the caller reports "token expired."
- **The unit tests mock `renewAccessToken`.** `tests/etrade-dormant-token-renew.test.ts` and
  friends stub the function, so the wrong URL was never exercised. Every renew-and-retry test
  passed while the real endpoint was broken.
- The v1.1.92 / v1.1.94 fixes improved **detection** (renew-and-retry on *any* error, not just
  auth-shaped) — correct and still valuable — but they could never succeed because the renewal
  they called was hitting a bad URL.

### Live diagnosis (2026-07-02)
The user reconnected E*Trade in the morning; the Daily Brief succeeded (~11 am → token live).
The afternoon was spent on Wheel filter scans, which go through **Polygon** (`DataProvider`), so
**no E*Trade traffic kept the token warm**. By ~1 pm the token was dormant (idle > 2 h). At 5 pm
the after-close batch failed at Daily IV Update, and an on-demand AAPL CSP in the Payoff screen
returned:

```
E*Trade API error (401) at /v1/market/optionexpiredate: oauth_problem=token_rejected
```

`token_rejected` is E*Trade's **dormant-token** signature — reactivated by renew. But renew was
hitting the wrong URL, so the token was never revived. Hence the recurring "re-authenticate every
day / every evening" pain: auto-revival had, in fact, never happened.

### The fix
- One-line path correction in `etrade-auth.ts` (with an explanatory comment).
- **Regression test** `tests/etrade-renew-endpoint.test.ts` calls the *real* `renewAccessToken`
  against a stubbed global `fetch` and asserts the URL is
  `https://api.etrade.com/oauth/renew_access_token` and contains no `/v1/oauth/`. This is the
  guard the mocked dormancy tests structurally could not provide.

### Expected impact
Dormant tokens (idle > 2 h, same ET calendar day) should now **auto-revive** on the next E*Trade
call — the evening batch, the Strategy Lab, the agent, and the on-demand options paths all route
through renew-and-retry. A token that has crossed **midnight ET** still requires a manual re-auth
(that's expiry, not dormancy — renew cannot revive it).

### How to verify
1. Re-authenticate E*Trade (full verifier flow) to get a fresh token.
2. Use the app normally, then leave it idle (no E*Trade calls) for > 2 h **without** re-authing.
3. Trigger an E*Trade call (Run Now the Daily IV Update job, or open an options chain). It should
   now succeed by auto-renewing, instead of reporting "token expired."

### Follow-up worth considering (not in this change)
- The connection status (`etrade:check-connection`) is a **date-stamp check only** — it never
  probes E*Trade, so a dead/dormant token can still read as "connected." A lightweight live probe
  at connect-time (and/or a periodic heartbeat) would surface a bad token immediately instead of
  at the next batch. Left as a separate decision.
