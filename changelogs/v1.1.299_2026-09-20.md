# v1.1.299 — 2026-09-20

TradeAnalyzer only. Diagnosis fix in the bull put spread shadow report, plus a readability gap closed.

## A label that the next commit made wrong

v1.1.291 gave the shadow report a diagnosis for missing-leg rejections: take the stored chain, re-run the
leg rules over it, and say what stopped the spread. Its last branch — both legs found — was worded
**`legs present (another expiry was chosen)`**, because under the rules in force that was the only way a
rejected chain could still yield legs.

**v1.1.292, the next commit, widened the band** (short 0.20–0.40Δ from 0.25–0.35; long 3–10% of spot from
5–7.5%). `diagnoseLegs` reads `SPREAD_MODE_PROFILE` live, so from that moment it judged last week's
rejections under rules that did not exist when they were made. Every chain the widening rescued came out
as `legs present` and was therefore reported as an expiry choice. Today's report shows 25 of them —
12 under the Δ reason, 13 under the wing reason — which is exactly the population v1.1.292 was written to
fix, described as something else entirely.

This is the project's recurring shape: **a claim in a message goes stale exactly like the code around it,
and is read at the moment nobody can check it.** Same family as `queue-job.mjs` telling the operator to
wait for a loop that had been removed three versions earlier.

## The band is recoverable from the rejection itself

`buildBullPutSpread` formats the live profile into both missing-leg reasons:

- `no two-sided put at 0.25–0.35Δ`
- `no two-sided long put 5–7.5% of spot below the short strike`

So the reason string is the **only surviving record of the band in force that day** — no new column, no
migration, no second source of truth to keep honest.

- **`parseLegBand(reason)`** recovers it, falling back to the current profile for anything it cannot
  parse. A fallback makes the comparison a no-op rather than a wrong answer.
- **`diagnoseLegs(puts, spot, band?)`** takes the band as a parameter, defaulting to today's.
- **`diagnoseStoredRejection(puts, spot, reason)`** judges under today's band and, only when that finds
  legs, under the band that refused it. Both find legs → the expiry really was the choice. Only today's
  → **`the widened rules would now build it`**.

Two notes on the direction of the remaining error. A reason names only *its own* half of the band, so the
other half stays today's — which can only make the "then" evaluation *more* likely to find legs, hence
*less* likely to claim the widening fixed something. The target delta is never in the text and stays
today's: it orders candidates and cannot decide whether any exist. Both leave the guard able to
under-report and not to over-claim.

## What Settings → Strategies actually stored

v1.1.296 made the operator's numbers editable but not readable: `GET /settings` is a fixed allowlist that
does not carry them, so the only way to see what the screen saved was to open the database — which from a
redirected shell is precisely what must never be done. `buildSpreadShadowReport` now returns the settings
whole, and the report script and the view print them with the arithmetic spelled out:

```
  mode shadow · max loss/position $2,500 · max open 10 · max open/sector 3
  fully deployed that is $25,000 at risk
```

That last line is the one 08 S8 flagged and is worth seeing every time the report is read. The same
reasoning is already written into `routes-settings.ts` for `edgarContact`.

## Tests

`tests/spread-mode-settle.test.ts`:

- `parseLegBand` recovers each band, keeps today's value for the half a reason does not name, accepts a
  hyphen as well as the en dash, and falls back to the current profile on unparseable, reversed or
  non-numeric input.
- `diagnoseStoredRejection` separates the two cases on the real first-week shapes: the DVN/EOG/COP/MDT
  Δ-grid case (only strike at 0.38), the CF wing case ($5 strikes at ~$120 → 4.17% and 8.33%), a chain
  with legs under both bands, and two causes that are not about the band at all.

1,420 root tests pass.
