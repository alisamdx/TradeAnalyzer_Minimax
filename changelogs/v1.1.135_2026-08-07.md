# v1.1.135 — 2026-08-07

## `optionLiquidity` weight: swept, found immaterial, disabled as operator config

v1.1.133 concluded liquidity is a gate rather than a ranking signal, and named "reduce or remove
`optionLiquidity`'s composite weight" as the indicated follow-up. This tests that directly.

### The sweep

Section C added to `scripts/fr-income-liquidity-realized-ab.mjs`. Vary the *weight* rather than the
formula — weight 0 is equivalent to `enabled: false`, since `ScoringService` iterates enabled
signals only, so the signal leaves numerator **and** denominator and the rest renormalise to 100.
Legacy liquidity formula throughout (the shipped path). Top-5 per date, 16 dates, outcomes settled
at intrinsic.

| weight | assigned | mean return on capital | total pts | picks changed vs w=13 |
| --- | --- | --- | --- | --- |
| **13** (current) | 60.0% | **−2.92%** | −233.5 | (baseline) |
| 9 | 61.3% | −3.20% | −255.8 | 11/16 dates |
| 6 | 67.5% | −3.56% | −284.5 | 14/16 dates |
| 3 | 62.5% | −3.49% | −279.5 | 15/16 dates |
| **0** (disabled) | 57.5% | **−2.77%** | −221.6 | 16/16 dates |

**Non-monotone ⇒ noise.** Disabling is nominally best, by +0.15 pts against the baseline — but the
middle of the sweep is *worse than both endpoints*, swinging 0.79 pts. A real effect would be
monotone. On ~80 trades per arm from one regime, this cannot distinguish the arms.

### Correction to v1.1.133

That entry named cutting the weight as the indicated fix. It was an **inference** from the signal
being anti-predictive, and the direct test does not support it. Precisely:

- the **mechanism** finding stands — liquidity tracks realized volatility (55% vs 43% top vs bottom
  quartile) and belongs as a gate;
- the **prediction** that acting on it improves outcomes does not.

The reason both can be true: at 13 of 100 the signal is dominated by ivRank 30 + premiumRiskRatio 22
+ recentVolatility 20 = 72. Its weight changes *which* names get picked — 11 to 16 of 16 dates — but
not *how they do*.

### Applied anyway, as operator config, at the operator's direction

`optionLiquidity` is now **`enabled: false` on wheel and income** in this install's
`scoring_strategy_configs`. Enabled weight sums: **91 (wheel) / 87 (income)**, renormalised to 100.

This is a **runtime config change, not a baseline change.** `BASELINE_WHEEL` and `BASELINE_INCOME`
in `scoring-service.ts` are untouched, so fresh installs still ship the signal enabled. Same
precedent as the 2026-06-23 entry-cap change (`max_new_entries_per_day` 1→2 applied to the live DB
while migration defaults stayed conservative).

It is applied on **judgment, not on data** — the reasoning is v1.1.133's mechanism finding, and the
sweep says the effect is unmeasurable either way. That distinction is the point of recording it here.

### Two consequences worth knowing

**1. The live DB and the code baseline now disagree.** This is the same class of trap as the
batch-job `config_json` allowlists, which bit v1.1.121 and v1.1.123: a code constant no longer
describes what this install actually runs. Check the `scoring_strategy_configs` row, not
`BASELINE_*`.

**2. The rows carry `version = 'custom_v1_no_option_liquidity'` deliberately.** `seedBaselines()`
auto-upgrades only rows versioned `baseline_v1`/`baseline_v2`, and its own comment states that
customised configs should carry a different version string so they are left alone. Leaving these on
`baseline_v3` would let a future `baseline_v4` upgrade silently revert the change. **Cost: wheel and
income no longer receive baseline weight updates automatically.**

**Rollback:** ⚖ Trade Scoring → Reset to Baseline, per strategy. Pre-change state:

```
wheel   baseline_v3  ivRank:22 premiumYield:19 fundamentalScore:17 technicalNeutral:11
                     notDowntrend:8 recentVolatility:10 optionLiquidity:9 leverageQuality:4
income  baseline_v3  ivRank:30 premiumRiskRatio:22 recentVolatility:20 trendNeutral:15
                     optionLiquidity:13
```

### Liquidity is still enforced — as a gate

Unchanged and deliberately so: the brief's `hasAdequateLiquidity` structure gate and the v2 engine's
`liquidityScore ≥ 8` in `EntryPolicy`. Only the *ranking* role is removed, which is exactly what
v1.1.133 argued for. An illiquid name still cannot reach a trade.
