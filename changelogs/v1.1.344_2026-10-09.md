# v1.1.344 — 2026-10-09

## Fix: an expired E*Trade token is now reported early and stops the collector's retry storm

### What happened on 2026-10-08

The token from 10-07 expired at midnight ET. Nothing said so until the 10:16 orchestrator refused to start ("E*Trade token invalid — renewal failed"). The 17:01 slot failed the same way. The 17:06 collector ran anyway: Polygon, EDGAR, Finnhub and Treasury were fine, but every E*Trade call returned 401 `token_expired`. That was 1,328 expiration calls, each followed by a renew (713 renews that day, all 401), so the day has no chains, VIX or account data. The operator re-authed at about 22:47 and ran the chain by hand. Its collector (run 66, from 23:52) then lost the new token at midnight, part-way through the run, which produced another ~1,800 401s. At 00:14 the watchdog asked about **2026-10-09**, found no run and halted the chain. It also marked 2026-10-09's domains `not_run` and emailed NO RUN for a day that had not started.

### Changes

1. **The collector stops calling E*Trade once the token is declared expired** (`src/main/services/etrade-token-latch.ts`, `electron-collector-host.ts`). Renew-and-retry on any failure is unchanged: the renew decision still reads only "not 2xx". If the post-renew retry answers 401 `oauth_problem=token_expired`, the token is latched. Every later E*Trade call in that run returns `status: null`, "call not sent", without touching the network, and one `collector-host:etrade-token-expired` ERROR goes to `logs/errors`. `token_rejected` (dormant, renewable) never latches. A re-auth mid-run changes the access token, which clears the latch.
2. **The watchdog asks about the right session** (`watchdogTargetDate` in `jobs/collector-daily.ts`). Before 17:05 ET it checks the most recent trading day before today, because today's collector run cannot exist yet. From 17:05 onward it checks today, so the 19:30 schedule is unchanged. The ET clock comes from a new `etClockHHMM`, which uses `hourCycle: 'h23'` so midnight cannot read as `24:xx` and sort after the cutoff. The NO RUN detail now reads "No daily run exists for this trading day."
3. **Expired-token email before the morning batch** (`src/main/services/etrade-token-alert.ts`, wired in `index.ts`). A 5-minute timer probes E*Trade once per trading day at the first tick inside [07:30, 10:15) ET. That probe, or the 90-minute keep-alive whenever it reports `expired`, sends "⚠ E*Trade token expired — re-authenticate before the 10:15 batch", at most once per ET day. Each alert also logs `etrade-token-alert` (ERROR), including whether the email went out.

### Not changed

- The orchestrator's own token gate (a date-stamp check) is unchanged.
- The `data-collector` job still collects for the calendar date it starts on. A manual chain that reaches the collector after midnight would collect for the new date. That did not happen here, because run 66 started at 23:52.

### Tests

`tests/etrade-token-expiry.test.ts` covers latch trip and clear, `token_rejected` never tripping it, latch ordering in the transport, the watchdog date at 00:14 / 17:04 / 17:05 / 19:30, the midnight clock format, the morning window, and one alert per day. `collector-host.test.ts`'s boot-interval guard now allows exactly the two named E*Trade timers.
