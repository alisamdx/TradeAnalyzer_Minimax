# v1.1.196 — 2026-09-06

## feat — this app now hosts the rebuild's collector (NewApp B3)

Changes #3 and #4 of the seven the existing app receives for stage 1
(`NewApp/requirements/06 §5`). **No view, IPC handler, service, scoring rule,
existing job or existing table is touched**, and the collector writes only into
the new generation, never into this application's database.

### Added

- `src/main/collector-host/electron-collector-host.ts` — the adapter that hands
  `@tradeanalyzer/core` this app's hardened transports, `safeStorage`, and the
  batch progress channel. It owns no collection logic.
- `src/main/collector-host/universe-sources.ts` — which endpoints answer for
  each universe list. Host configuration, not library logic.
- `src/main/services/jobs/collector-daily.ts` — `data-collector` (17:05,
  after-close only) and `collector-watchdog` (19:30).
- `src/main/services/jobs/collector-oneshot.ts` — claims one queued job per
  2-minute tick from the new application.
- `etradeGetRaw()` in `etrade-auth.ts` — same signing, same instrumented
  transport, same single nonce retry as `etradeGet`. It differs only in
  returning the **response bytes as received** (the archive stores those bytes
  and hashes them for provenance) and in returning a non-2xx rather than
  throwing (a failed call is evidence about the day and is archived like any
  other response).

### Decisions worth keeping

**Registered last.** `sequence_order` is seeded from registration order and then
frozen in the DB, so a job inserted in the middle would renumber nothing on this
install and everything on a fresh one. A test asserts the three collector jobs
register after every existing job.

**Renew-and-retry on ANY E*Trade failure**, never on an auth-shaped message. A
dormant token does not reliably fail as a 401 — it can kill or hang the response
stream — and that exact heuristic bit two paths in this app, one of them halting
the evening orchestrator on 8 of 10 trading days. A test asserts the retry
decision contains no message sniffing at all.

**The generation is opened write-capable, never readonly.** On Windows a
readonly connection cannot attach the live WAL index and reads only up to the
last checkpoint; the new exe holds the same file open, so a readonly handle here
would read a stale generation and report it as current.

**Account data is refused rather than written in the clear.** If `safeStorage`
is unavailable, `encryptForArchive` throws. The archive is permanent, so a file
written unencrypted today stays that way forever with no way to tell later which
files those were.

**The shared pointer is never invented.** If it is missing, the new exe has not
been run, and both handlers report `skipped` — creating a path here would make a
second, empty generation indistinguishable from the real one having lost its
data.

**The watchdog reports; it does not re-run.** Quietly re-running would turn "the
collector did not run" into "the collector ran late", and the second is far
harder to notice going wrong repeatedly.
