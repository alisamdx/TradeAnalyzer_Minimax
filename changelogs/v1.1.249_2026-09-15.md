# v1.1.249 — 2026-09-15

## The gate email leads with what changed

**Why.** The gate reports *state*, and state has been RED on every daily run this
generation has had. A signal that is always on carries no information. In the
2026-09-15 email, a check firing for the first time at 92 % (QC-401) looked
exactly like 151 price discontinuities that had been sitting there for weeks —
same verdict, same section, same formatting — and the only way to tell them apart
was to read all 773 rows and remember the previous night's. That is why the
operator was asking for a manual review every evening instead of reading the
alert.

This is the third instance of one shape in this project, after the conviction
band that could never fire and the liquidity gate that always did: **a threshold
is only informative where it can go both ways, and so is a verdict.**

## What it does

`packages/core/src/qa/delta.ts` computes, per check, what this run **added**,
what **stopped**, and what merely persists — from columns the gate already
maintains (`first_seen_run_id`, `last_seen_run_id`, `still_firing`). Nothing new
is stored; a snapshot table would be a second source of truth to keep honest.

The baseline is the **previous gate run**, not the previous calendar day, so a
re-run of the same day compares against the run before it.

Six outcomes per check: `new`, `growing`, `shrinking`, `churned`, `gone`,
`resolved`. Everything else is counted, not listed.

`churned` earns its place: a check that swaps one ticker for another has the same
total on both runs, and reporting that as unchanged would be the same
stable-number-hiding-a-moving-population mistake as the rest of this file's
history.

### The subject line

The subject is what gets read on a phone, and it is what decides whether the
email is opened. It now carries the delta:

```
[TA-Data] 2026-09-15 after_close — RED (572 blocking) · 1 NEW, 2 growing, 1 gone
[TA-Data] 2026-09-16 after_close — RED (572 blocking) · no change
```

Same verdict, same blocking count — different news, and now distinguishable
without opening anything.

### The body

```
CHANGED SINCE RUN #1 (2026-09-14)
  NEW       QC-401 chains  ×1 first seen
      496 of 541 subset tickers returned no expirations (91.68%)
  GROWING   QC-409 chains  267 → 415 (+148)
      PIN267--261016C00280000 is pinned (recommended_by_legacy) but has no snapshot for 2026-09-15
  GONE      QC-601 earnings  ×5 stopped firing (still open)
      E0 (finnhub) moved 2026-09-22 -> 2026-12-07, 76 days later
  GROWING   QC-404 chains  415 → 477 (+62)  [warning]
      W415: ask 72.35 is 3.07x the underlying 23.6
  unchanged: 1 check, 151 findings
```

Blocking first, then by size of move. Each changed check gets one concrete row —
preferring a newly added one, because a count alone is not actionable. Blocking
carries no severity marker (it is the default concern); anything else is
labelled, so a growing warning cannot read as alarming as a growing blocking
check purely because both moved.

## No baseline is not "no change"

On the first run of a generation there is nothing to compare against. That is a
**different fact** from a quiet night and is rendered as one — `first run, no
baseline` in the subject, and an explicit line in the body. An absence reading as
a pass is this project's single most repeated bug (QC-907's zero paired days,
`cleanDayStreak` walking only dates with rows, the overlap check that passed on
zero overlapping days), and the mechanism built to summarise the others was not
going to join them.

A test asserts the first-run body does **not** contain "Nothing changed".

## Tests

`packages/core/test/delta.test.ts`, nine cases: no baseline; new; growing;
shrinking and gone; churned; genuinely unchanged; same-day re-run baselines to
the previous run; the subject distinguishes two RED runs; and the email stays
under 102 KB when a single check contributes 300 new findings.

## Known limitation

`still_firing` is left at 1 for a check that did not run at all, so a check
skipped by `checksFor()` reads as persisting rather than as unknown. That is
pre-existing gate behaviour and unchanged here; it means "unchanged" should be
read as "not contradicted", not as "re-verified".

Also unchanged: `RED (N blocking)` counts every open blocking exception,
including ones that have stopped firing. The delta block is where that
distinction is now visible.
