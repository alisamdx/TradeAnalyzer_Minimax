# v1.1.153 — 2026-09-01

## fix: collapse the duplicate closed positions left by the v1.1.150 import

### How they arose

| version | what happened |
| --- | --- |
| v1.1.150 | the executed-orders import landed and **INSERTED** 25 closed positions; supersede did not exist yet, so each sat beside the estimate it should have replaced |
| v1.1.151 | supersede added — a real fill overwrites the matching estimate in place |
| v1.1.152 | orders made primary, so the import finally ran that path and **superseded 12 estimates** — which the v1.1.150 inserts had already duplicated |

### Verified before writing the migration

All 12 pairs carry **identical `realized_pnl`** — the TSLA 350 assignment reads +$499.48 in
both rows, the TSLA 360 CC +$347.47 in both — so collapsing them cannot move any P&L figure.

Simulated against a copy of the live table first:

```
rows 41 → 29  (removed 12)
realized P&L on closed rows: 5849.32 → 3309.67
remaining estimated: 2      open rows preserved: 2
```

The 5849.32 was double-counting the duplicate pairs; 3309.67 is the true realized total.

### The migration

Keeps the **lowest id** of each group — the original position-sync row, which also carries
`etrade_position_id`, Greeks and `market_value` that the import does not populate. Grouped on
ticker + type + strike + expiry + entry_date + quantity, with `IFNULL` so equities (NULL
strike/expiry) group correctly.

Idempotent, and harmless on an install that never ran v1.1.150 — the subquery simply matches
nothing. No duplicate can arise going forward: `insertClosedPosition` supersedes an estimate in
place and skips a position already imported.
