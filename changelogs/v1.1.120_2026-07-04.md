# v1.1.120 — 2026-07-04

## IV High (Vetted): Wheel (Vetted)'s safety gates, applied to IV High

Follow-up to v1.1.119 (the Filters Prefill summary email). After validating that email, the user asked: does IV High have the same risk protections built into Wheel (Vetted), so the email doesn't hand over anything that's actually a bad trade? A full gate-by-gate comparison showed the answer was no — plain IV High is a bare threshold with zero downstream protections.

### The gap

Re-read `evalWheelVetted` in full to enumerate its complete gate stack:

| # | Gate | Wheel (Vetted) | IV High (before this change) |
|---|------|------|------|
| 1 | Valid quote | ✅ | (implicit) |
| 2 | Fundamentals/suitability ≥ 75 | ✅ (stocks) | ❌ |
| 3 | No earnings before target expiry | ✅ (stocks) | ❌ |
| 4 | Not in a confirmed downtrend | ✅ (all) | ❌ |
| 5 | Live chain must exist | ✅ | ❌ (no chain fetch at all) |
| 6 | Valid target put found | ✅ | ❌ |
| 7 | Liquidity (OI ≥ 250, spread ≤ 15%) | ✅ | ❌ |
| 8 | Real premium floor | ✅ | ❌ |
| 9 | IV ceiling (≤ 80%, no vol-bombs) | ✅ | ❌ |

IV High was designed as a cheap, universe-wide informational scan — zero API cost, fine for browsing ~1,600 names. Wheel (Vetted) is the opposite: expensive per-survivor chain fetches on a pre-shrunk pool. That tradeoff made sense when IV High was purely for browsing. It stopped making sense the moment its top 10 became the content of an actionable email.

### The decision (via AskUserQuestion)

Three real design choices, all resolved toward the recommended option:
1. **New template vs. modify existing** → new `"IV High (Vetted)"` template, mirroring the established Wheel Opportunity / Wheel (Vetted) split. Plain IV High stays untouched for browsing.
2. **Add the live-chain liquidity/IV-ceiling check?** → yes, full parity with Wheel (Vetted) — same OI/spread/IV-ceiling thresholds.
3. **Add the fundamentals/suitability gate too?** → no — IV High serves CSPs, covered calls, and other premium strategies broadly, not just wheel-style ownership; an ownership-worthiness bar doesn't universally apply.

### Implementation

**New pure thresholds** (`filter-templates-service.ts`), reusing `WheelVettedThresholds`' shape:

```ts
export const IV_HIGH_VETTED_DEFAULTS: WheelVettedThresholds = {
  minSuitability: 0, minDte: 25, targetDelta: 0.50, minOi: 250, maxSpreadPct: 15,
  minAnnualizedReturn: 0, minAnnualizedReturnEtf: 0, maxIvPct: 80,
};
export const IV_HIGH_VETTED_CHAIN_FETCH_CAP = 40;
```

`targetDelta: 0.50` (ATM) instead of the wheel's 0.30Δ — this isn't picking a specific CSP strike, it's a general "is this name's options market actually tradeable" check. `minAnnualizedReturn: 0` means the yield-floor check inside the reused `assessWheelPut()` always passes (IV High isn't committed to a specific premium-selling structure the way Wheel is), while still surfacing the computed OI/spread/IV numbers as useful metrics.

**Why a cap is necessary here but not for Wheel (Vetted).** Wheel (Vetted)'s fundamentals gate (suitability ≥ 75) narrows the field dramatically before any chain fetch. IV High (Vetted) has no such gate — without a cap, it could need a live chain fetch for every one of a few hundred IV-Rank survivors, multiplying the batch job's E*Trade call volume for no benefit (the email only ever shows the top 10). So Phase-1 survivors are ranked by IV Rank descending and capped to 40 before Phase 2 spends an API call.

**Why this needed a new code path, not just a new case in the switch.** Every other filter template runs through `runTemplate()`'s uniform per-ticker loop → `evaluateTemplate()` dispatch — each ticker evaluated independently, no cross-ticker ranking. IV High (Vetted) needs the *entire* Phase-1 survivor pool in memory before it can rank and cap it. So `runTemplate()` special-cases `'iv_rank_high_vetted'` and routes it to a dedicated `runIvHighVetted()` method:

```ts
if (templateId === 'iv_rank_high_vetted') {
  return this.runIvHighVetted(tickers, onProgress, signal);
}
```

Phase 1 (cheap, whole universe): same IV-Rank threshold as plain `iv_rank_high` (>70 stock / >30 ETF, per-ticker ETF-calibrated) → downtrend gate (`loadTrendLabel`, reused verbatim from Wheel (Vetted)) → earnings-before-expiry gate (`loadNextEarnings`, stocks only, same target monthly expiry Phase 2 will chain-fetch). Phase 2 (expensive, capped survivors only): live monthly chain → ATM put via `pickWheelPut` → `assessWheelPut` liquidity/IV-ceiling gate.

### Filters Prefill wiring

- Default prefill allowlist grows from 4 to 5 templates: `RSI Oversold, IV High, IV High (Vetted), Price Alert, Wheel (Vetted)`.
- The summary email's IV High section (from v1.1.119) now sources from `iv_rank_high_vetted` instead of the loose `iv_rank_high` — the top 10 shown are "best of the names that already passed downtrend/earnings/liquidity/vol-bomb screening."
- The email table gains **OI** and **Spread** columns so the new liquidity data being vetted is visible, not just implied.

### Tests

`tests/iv-high-vetted.test.ts` (new, 10) — end-to-end coverage of every gate: no options provider → `[]`; confirmed downtrend excluded before any chain fetch; stock with earnings on/before the target expiry excluded, same-date ETF *not* excluded; thin OI excluded; wide spread excluded; vol-bomb IV excluded; a clean candidate passes with correct metrics; ETF IV-Rank calibration (30 vs 70) matches plain IV High; below-threshold tickers never reach the chain at all; Phase-1 ranking + cap verified with 45 seeded candidates (exactly 40 chain-fetched).

`tests/filters-prefill.test.ts` and `tests/filters-prefill-report-builder.test.ts` updated for the new template id and copy changes ("gate survivors" instead of "scanned").
