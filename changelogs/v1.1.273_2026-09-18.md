## The gate retires findings whose key its check can no longer produce

**The problem.** gen-002 held **11,444** QC-410 findings keyed by *contract* (`ADP---260918C00275000`), open with `still_firing = 0` since v1.1.252 re-keyed the check per *ticker*. None could ever fire again, and nothing could close them: the gate resolves a stopped finding only when a remediation succeeded, and there is no remediation for a key that no longer exists. They were most of the open queue (12,963).

**Why not a bulk resolve.** 05 §5 deliberately offers no bulk resolve — a resolution is a claim about one finding, and a bulk version turns it into a claim about a filter — and `operator-workbench.test.ts` pins that. A bulk command was drafted first and withdrawn before commit for exactly that reason; the operator chose instead to make this the gate's job.

**The fix.** A check may declare `keyShape` — the pattern every key it produces now matches. In `reconcileStoppedFiring`, an open finding of that check which has stopped firing and whose key does not match is resolved as `rule_changed`, actor `gate`, one event per finding naming the old key. It is a fact about the check, which the gate knows, so it stays on the right side of P9. QC-410 declares `/^[A-Z][A-Z0-9.]{0,9}$/`; verified on the 2026-09-18 snapshot that all 79 ticker keys and every subset ticker match it and all 11,444 contract keys do not.

**Guards.** A check that throws, or produces a key outside its own declared shape, retires nothing that run, and the stray key is raised as a `key_shape_violation` finding — the declaration is then wrong, and a wrong pattern must never close real findings. A finding that is still firing is never retired. Ticker-keyed findings that merely stopped firing (24 for QC-410 tonight) stay open: their going quiet is a fact about the data, and the operator's call.
