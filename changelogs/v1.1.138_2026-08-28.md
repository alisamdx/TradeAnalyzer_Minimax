# v1.1.138 — 2026-08-28

## fix: the brief's earnings net was inert in both directions

### The problem

The Daily Brief has a last-line-of-defense earnings check for its picks. It did nothing.

Two independent reasons, either one sufficient:

1. **`refreshTickers` skipped any stored future date** as "still valid". The one failure
   that matters is a stored date wrong in the FAR direction — that is what silently
   disables the −20 penalty. NVDA held a bogus `2026-11-17` while its true report was
   `2026-08-26`, so the net skipped it as valid on the day it reported. The Aug-26 run
   proves it: `{"updated":0,"skipped":53,"failed":3}` — 53 skips, zero verifications.
2. **It ran AFTER pick selection** (Stage 5b, line ~512), so even a correct finding could
   not remove a pick. The picks were already chosen 200 lines earlier in Stage 3.

### Fixes

**`EarningsService.refreshTickers` — verify what claims to be safe.** The skip rule is now
asymmetric, mirroring the sweep's write policy:

- A stored date **inside** `TRUST_STORED_WITHIN_DAYS` (60) is trusted and skipped. The gate
  is already engaged; re-checking cannot change the outcome, and an error in that range is
  fail-safe (an earlier date over-penalises).
- Everything else is confirmed against E*Trade: no row, a past row, or — critically — a
  date **beyond** the horizon, which is precisely the value claiming there is no earnings
  risk. 60 is deliberately wider than the 45-day penalty window so every date inside that
  window is trusted and every date outside it is checked.

**Manual entries are now never overwritten, `force` included.** Previously `force=true`
skipped the entire guard block, manual check with it, contradicting the documented
contract.

**The net moved before pick selection.** A new Stage-3 verification pass confirms the
provisional top-`STAGE4_POOL_SIZE` candidates for the penalty-bearing strategies
(income/wheel/bearish) against E*Trade — an independent source from the Finnhub-derived
calendar — then re-applies the penalty to anything newly revealed and re-sorts, before the
Stage-4 pool is locked. Penalty application is now a reusable closure tracking
`(strategy, ticker)` pairs, so the second pass can never double-penalise. Recorded in
`run_meta.earningsVerify` as `{checked, updated, skipped, failed, newlyPenalised}`.

Because `refreshTickers` skips dates already inside the horizon, this is typically ~20
E*Trade calls, against a Stage 4 that already makes one chain call per candidate.

The old Stage-5b call remains for buy/bullish/inflection picks, where it was never a gate —
it exists so the critic and the v2 entry gate see complete calendar data. Its comment now
says so rather than implying it protects anything.

### Had this been in place

NVDA's `2026-11-17` was 83 days out — beyond the 60-day trust horizon — so it would have
been sent to E*Trade, which would have returned `2026-08-26`. The −20 would have applied in
the second pass, taking NVDA from 73.3 to 53.3, below the other wheel picks (63.6–64.3), and
it would not have appeared.

### Validation (FR-SEY-5)

No threshold or rule changed: the 45-day window, the −20 magnitude, and the set of
penalty-bearing strategies are untouched. This restores the gate's *input data* on the path
that selects picks. As established in v1.1.137, a Brief Replay cannot validate an
earnings-gate change — `earnings_calendar` stores one row per ticker, overwritten in place,
so no past calendar state is reconstructable.

The gate becomes strictly **more** conservative here (it can now only add penalties that the
stored calendar missed, never remove one), which is the opposite direction from v1.1.137 and
needs no outcome evidence to justify.

### Tests

New `tests/earnings-refresh-tickers.test.ts` (6): far date verified and hidden near-term
report caught (the NVDA case); near date trusted without a call; no-row and past-date still
fetched; manual never overwritten even under force; force re-fetches an otherwise-trusted
near date. Suite: 973 passed.
