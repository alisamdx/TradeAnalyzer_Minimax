# v1.1.206 — 2026-09-09

## fix — the collector jobs became manual-only, and `enabled` started meaning something

The operator's inbox filled with `[TA-Data] … RED (1095 blocking)` reports, one
per collector run, run #70 and climbing. **Stop the emails** was the whole of the
request; this is what was actually causing them.

### The loop

`gen-001` is malformed, so `finishJob` cannot write a terminal state for a
claimed `meta_job_request`. The row stays `queued`. The 2-minute claim loop in
`index.ts` re-claims the same row, runs it, fails the same way, and the quality
gate emails RED — every two minutes, indefinitely.

Nothing bounded it: no attempt cap, no backoff, no "this already failed" check.
**A retry loop over work that cannot record its own outcome does not converge**,
and it announces that once per iteration to whoever is on the mailing list. The
loop is removed. A queued job is now picked up by running `collector-oneshot`
from the Batch view, which is what the new exe's Jobs UI will do directly once it
owns the queue (05 §7). The claim *path* is unchanged and still exercised — the
trigger was wrong, not the handler.

### The switch that did not switch anything

Turning the three jobs off should have been the obvious first move, and it would
not have worked. **`batch_jobs.enabled` was ignored by the only path that
matters.**

| Trigger | Honoured `enabled`? |
|---|---|
| `runStartupJobs` | yes — `enabled && run_on_startup` |
| the daily schedule tick | yes — `enabled && daily_schedule_enabled` |
| **the orchestrator chain** | **no** |

The orchestrator is what actually runs jobs, twice a trading day. So a job
switched off in the Batch view kept running, and there was no single control that
stopped one. `getSubJobs` now filters on the column like everything else.

Two defaults compounded, and the second is pinned rather than changed: a job
**absent** from the orchestrator's `config_json.jobs` defaults to *enabled*
("handles new jobs added after config was last saved"). That is reasonable on its
own, and it means a newly registered job joins the after-close chain with nobody
opting it in — which is exactly how three collector jobs started running against
a generation that was still being stabilised.

### What "off" means

`enabled = 0` means **does not run on its own**, never **cannot be run**.
`BatchService.runJob` has never consulted the column, so the Batch view's Run
button still works on all three. That distinction is the operator's actual
request — manual is fine, automatic is not — and it is asserted in the tests so a
later tidy-up cannot quietly turn "off" into "unavailable".

### Both halves were needed

`registerJob` seeds with `INSERT OR IGNORE`, so the new `enabled: false` in
`index.ts` only ever applies to a **fresh install**. The existing rows are frozen
— the same trap as `sequence_order`, `config_json` and `after_close_only` before
it (v1.1.121, v1.1.123, migration 067). **Migration 080** does the live install:

```sql
UPDATE batch_jobs
   SET enabled = 0, daily_schedule_enabled = 0, run_on_startup = 0
 WHERE id IN ('data-collector', 'collector-watchdog', 'collector-oneshot');
```

The watchdog is off for a reason worth stating: it exists to email when no daily
run happened. With the daily run deliberately off, leaving it on would send a
`NO RUN` alarm every night for a run nobody scheduled.

### One behaviour change beyond the collector

`getSubJobs` honouring `enabled` applies to **every** job, not just these three.
Any job whose row is already `enabled = 0` will now stop running in the chain.
That is what the column has always claimed to mean and what the other two
triggers already did — but it is a real change, and if some job has been running
on an `enabled = 0` row it will go quiet. The Batch view lists the flag per job.

### Tests

- `tests/collector-jobs-manual-only.test.ts` (7): the chain excludes a disabled
  job and keeps an enabled one (both arms); the config cannot override the
  column; an unlisted job still defaults to enabled; a disabled job still runs
  manually; `registerJob` seeds `enabled` and never overwrites an existing row;
  migration 080 executed **from the file**, not from a copy of its SQL.
- `tests/collector-host.test.ts`: the claim-loop assertions now pin its absence.
  Keyed on `runJob('collector-oneshot'` and a one-`setInterval` count rather than
  on `setInterval` itself — boot has a legitimate one, the ~90-minute E*Trade
  keep-alive, and banning the mechanism instead of the effect would have fired on
  it and taught the wrong lesson.

`1,247` tests pass.
