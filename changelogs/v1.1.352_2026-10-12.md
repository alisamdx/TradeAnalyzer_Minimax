# v1.1.352 — 2026-10-12

## Fix: a late app start ran the collector twice

**What happened.** The app was closed from 02:36 to 19:09 ET on 2026-10-12, so every schedule time of the day had passed when it started. The first scheduler tick:

1. ran the orchestrator's 10:15 slot (19:14–19:41);
2. ran the 17:00 slot, whose chain included `data-collector`: TA2 run 75, 20:18–21:12;
3. reached `data-collector`'s own 17:05 schedule and ran it again at 21:12:01: run 76, until 22:06.

Step 3 used the job row `checkSchedule` had read at 19:09, whose `last_success_date` was still the previous day. The chain had already set it to today (`runJobDirect` → `_writeRunResult`), but the loop never re-read it. The cost was a second full collection (~5,800 E\*Trade calls, ~55 min), a second gate run (QC-405 then counted 996,728 contracts, twice the day's) and a second gate email.

**Why it had not shown before.** On a normal day the app is running. The first tick at or after 17:00 lands before 17:05, so `data-collector`'s own schedule is not yet due when the loop passes it. Every scheduled run from 2026-09-14 to 10-09 was single. Only a start after 17:05 exposes it.

**Fix** (`batch-service.ts`). `checkSchedule` re-reads each job's row immediately before deciding whether to run it.

## Tests

`tests/batch-schedule-stale-row.test.ts`: with the clock at 19:09 ET and an orchestrator 17:00 slot whose chain runs a job that also has its own 17:05 schedule, one tick runs it once. Without the fix it runs twice.
