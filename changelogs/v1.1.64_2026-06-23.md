# v1.1.64 — 2026-06-23

## Engine stopped entering: dropped orders held the daily cap forever + no per-ticker dedup

### Symptom
After the v1.1.62/63 relaunch the engine was healthy (`brokerConnected:true`, cycles running) but
placed nothing new. The day's two AVGO entries — both silently dropped by the pre-v1.1.62 TWS bug,
neither filled — had consumed the entire `max_new_entries_per_day = 2`, so every cycle silently
rejected all picks with `daily_cap`.

### Root causes (three, all in the entry/cap plumbing)

**1. Stuck `submitted` orders were never reconciled.** A combo order the broker silently drops sits
`submitted` forever. For an OPEN order, its `approved` proposal keeps counting against the daily and
weekly caps indefinitely (`countNewEntries` counts `pending`/`approved` proposals). So two dropped
orders = a permanently-consumed daily cap, with no path back.

**2. No per-ticker entry dedup.** AVGO was proposed twice (10:29 and 10:31 ET) because the first
order never filled — no position existed to dedup against, and nothing else stopped the same name
from being re-proposed each cycle. The daily cap was the *only* stacking guard.

**3. A filled entry double-counted against the cap.** On fill, `applyOpenFill` opened the position
but left the proposal `approved`. Since `countNewEntries` counts approved proposals **and** open
positions, a single filled entry counted as 2 — one fill could exhaust `cap=2` on its own.

### Fixes

**`OrderManager.reconcileStaleOrders(now, staleMs)`** — runs at the start of each market cycle
(`STALE_ORDER_MS = 90_000`, generously above IBKR's ~1–2s ack). Any order stuck `pending`/`submitted`
past the cutoff with no broker callback is: best-effort cancelled at the broker, marked `cancelled`
(`stale_no_ack`), and then — only if the order row actually transitioned (guards a fill that landed
during the async cancel) — its entry is freed: OPEN → proposal `expired` (cap slot released, audited
`proposal_expired`); CLOSE → position back to `open` so management retries (audited
`order_stale_cancelled`). This **auto-clears today's two phantom AVGO proposals** on the first cycle
after restart.

**Per-ticker dedup in `EntryPolicy.generateEntries`** — a new `tickersInFlight(now, mode)` set
(live: non-closed positions + `pending`/`approved` entry proposals; dry-run: today's
`exec_dry_run_log` entries). Any pick whose ticker is in the set is rejected `duplicate_ticker`
before the cap check, and a ticker is added to the set once it builds a proposal so the same name
can't repeat within one batch either.

**Retire the proposal on fill** — `applyOpenFill` now sets the proposal to `superseded` (a
non-counting terminal status) when its position opens, so each entry counts exactly once: as a
`pending`/`approved` proposal while in flight, then as an open position once filled. Dedup coverage
is continuous (approved proposal → open position).

### Validation (FR-SEY-5)
Validation-exempt: correctness/safety fixes to engine plumbing (cap accounting, stuck-order cleanup,
concentration dedup). No scoring weight, signal, or entry/exit threshold changed; ticker selection is
unchanged. The dedup is strictly more conservative (it won't stack a name the engine already holds or
has in flight), so it cannot degrade the historical sample.
