# v1.1.262 — 2026-09-17

## A reuse ruling now settles the findings it accounts for

`recordTickerReuse` resolved exactly one exception — the id passed to it. A ruling that
says *everything before this date belongs to a different company* settles every
discontinuity, volume-regime and dormancy finding in that range, and SOLS carries 21
QC-204 findings, JAN 7.

Leaving the rest open is not merely untidy, because of two behaviours that compound:

- **An exception that stops firing stays open on purpose.** `reconcileStoppedFiring` sets
  `still_firing = 0` and nothing else, deliberately — *"it went away" is exactly how the
  earnings-date bug hid for a quarter*.
- **QC-501 reads QC-204's exceptions by `state`, not by whether they still fire.** Its
  whole implementation is `SELECT ... WHERE check_id = 'QC-204' AND state IN ('open',
  'acknowledged')`.

So after v1.1.261 silenced QC-204 on the previous occupant's bars, QC-501 would have gone
on reporting all 28 of them for ever, and the operator's ruling would have looked like it
did nothing.

`resolveSettledBySplice` now resolves, with its own audit event each, every open or
acknowledged finding for that ticker from **QC-204, QC-205, QC-209, QC-210 and QC-501**
whose key date is at or before the splice. Three boundaries, each with a test:

- a dated finding **after** the splice is left alone — that one is about the new entity;
- a **bare-ticker** key is settled (QC-210 is about the whole pre-listing range);
- a check the ruling says nothing about is untouched — QC-603's earnings staleness on the
  same ticker is not answered by a ruling about which company the old bars belonged to,
  which is why the check list is named explicitly rather than "every finding for this
  ticker".

`recordTickerReuse` returns `alsoResolved` so the caller can report it.

## Two smaller things in the same path

**The CLI printed the argument, not the result.** `exception.mjs reuse` reported `the day
before ${spliceDate}` using the optional positional argument, so on the inferred path —
the one where the operator most needs to see which date was chosen — it printed *"the day
before undefined"*. It now prints `r.spliceDate`, and the count of findings the ruling
settled.

**Its closing advice was also out of date**, claiming a reader intersecting bars with
membership sees one entity at a time. That reader only existed from v1.1.261, one version
ago. Fourth instance of the documented shape: a dev script's console output is
documentation and goes stale exactly like the rest of it, and it is read at the moment the
operator is least able to check it.
