# v1.1.151 — 2026-09-01

## fix: `sortOrder` is required by the transactions endpoint; real fills supersede estimates

### `sortOrder=DESC` was the missing parameter all along

The v1.1.149 negotiation found it on the first run:

```
transactions.json  {count:50}                    → timeout (20s)
transactions       {sortOrder:DESC, count:50}    → 200 in 447ms   ← works
transactions       {sortOrder, Jan slice}        → 200 in 204ms
transactions       {sortOrder, Feb slice}        → 401 → retry    → 200 in 411ms
transactions       {sortOrder, Mar slice}        → 401 twice      → fell back to orders
orders             {status:EXECUTED}             → 200 in 376ms
```

Nine hypotheses had been tested and falsified before this — range (8mo/31d/7d/none), path with
and without `.json`, `count` 5/50, a fresh nonce, our signing. The answer was a parameter no
variant had carried until the negotiation tried it.

`sortOrder=DESC` is now tried **first** and defaulted onto **every** sliced request, so a slice
no longer depends on which variant happened to win. The endpoint remains flaky — one slice
failed twice — but v1.1.147's nonce retry recovered another that had failed once, exactly as
designed, and the orders fallback covered the rest.

### Real fills now supersede the estimates

When a position vanishes from the broker, the position sync writes an estimate (`exit_price`
NULL, *"realized P&L estimated from last mark"*). Those are systematically wrong in two ways:

| | estimate | actual fill |
|---|---|---|
| TSLA 350 CSP — **assigned** | −$3,735.53 | **+$499.48** |
| TSLA 360 CC — **expired worthless** | −$463.02 | **+$347.47** |

An assigned CSP reads as a large loss when it was a *conversion into stock*; a position closed
by expiry is booked at its last mark rather than zero. Those two rows alone were a **$4,235
swing**. A real fill must replace the estimate, not sit beside it.

The supersede key is deliberately tight — ticker + type + strike + expiry + entry_date +
quantity, using `IS` rather than `=` so NULL strike/expiry (equities) compare correctly.
Matching on ticker+type alone collapsed an **open 100-share assignment lot** into a **closed
60-share lot from four months earlier**. An estimate with no matching fill is left untouched
rather than dropped or zeroed.

### Measured result on the real book

```
app displayed                        −$2,902
actual fills                       +$4,494.14     (2026-04-09 → 08-28)
  realized wheel  24 CSP/CC        +$3,220.70     16 winners
  realized stock   1 lot             +$599.99
  open, marked to 09-01              +$673.45
```

A **$7,396 error**, none of it from trading — all of it from estimated marks. The import also
surfaced **9 positions that were never in the database at all** (April/May OXY, PFE, NEM,
TSLA), so the book covers 5 months rather than the 84 days previously visible.
