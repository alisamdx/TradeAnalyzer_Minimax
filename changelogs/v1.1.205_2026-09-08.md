# v1.1.205 — 2026-09-08

## fix — a third dev script opened the generation with none of the guards

`@tradeanalyzer/core` 0.3.2. Found while building the Electron arm of the seed
replay, by asking a question that had not been asked out loud: **which code can
open a generation?**

### The defect

`packages/core/scripts/` holds three scripts that open a generation, and the four
refusals were spread across the callers rather than living in the function they
share:

| Refusal | Where it lived |
|---|---|
| Redirected shell | a **copy** in `queue-job.mjs`, a second in `diagnose-generation.mjs` |
| An application has it open (`-shm`) | `openGenerationExclusively` |
| Never create the file | `queue-job.mjs` only |
| Checkpoint before closing | `checkpointAndClose`, called by two of three |

**`exception.mjs` had none of them.** Written later, for the ticker-reuse rulings
B5's gate needs, it resolved the pointer itself — from `homedir()`, a third
spelling of a path the other two each spelled differently — called
`new Database(dbPath)` on the live generation, ran `applyDictionary` against it,
and closed with `db.close()`.

So it would open the generation from a containerised shell (the mechanism that
destroyed a generation on 2026-09-07), while both applications had it open (the
mechanism that corrupted `meta_response` twice), creating the file if it were
missing (which manufactures a generation with no `meta_generation` row), and
could discard its own writes on the way out (a 918,792-byte WAL was lost exactly
that way). Every one of those four has cost this project a day, and every one was
already prevented **somewhere else in the same directory**.

### The shape, for the fourth time

*A capability that must apply to every caller belongs in the function they all
call.* The v1.1.204 write-up says this in as many words — and it says it **about
these scripts**, naming the applications as the gap. The scripts it was
describing were themselves an instance of it.

**A copy in each caller is not a safeguard. It is a list of the callers somebody
remembered, and the next script is written after the list.**

### The fix

- `resolveGenerationPointer()` — probes the pointer's directory for a redirect,
  refuses to invent a missing pointer, and returns the derived paths, so three
  scripts stop spelling the same path three ways.
- `openGenerationExclusively(dbPath, who)` — probes the generation's directory,
  refuses while a `-shm` exists, **refuses to create**, then opens with the
  applications' own SQLite.
- Both delegate to `core`'s `assertNotRedirected`, the same call both
  applications make, so the operator reads the same words rather than a second
  copy that drifts. **Directories are the argument, never `%APPDATA%` globally**
  — the redirect is per file, `dataRoot` is configurable and the pointer is not,
  so each function probes what it resolved and between them both are covered.
- `exception.mjs` now goes through both, and closes with `checkpointAndClose`.
- `queue-job.mjs` drops its local copy of the redirect check;
  `diagnose-generation.mjs` keeps its **reporting** line, because a diagnostic
  should say what it found before it declines to continue.

### The invariant is asserted, not remembered

A scan in `packages/core/test/generation-access.test.ts` fails any script under
`scripts/` that resolves the shared pointer without importing the helper, or that
constructs a `Database` itself. It keys on the **pointer**, not on
`new Database`, so the replay arms and the stress test — which only ever open a
throwaway file in their own temp directory — stay legal.

It strips comments and **keeps strings**, because the module path and the pointer
filename *are* string literals (CLAUDE.md's rule: a rule about a module path
keeps strings; a rule about reaching a global strips them). Three fixtures ship
with it — one that must fire, one that must not, and one of pure prose about the
trap that must not fire either. Four source scans in this project have now fired
on their own documentation.

`293` tests in `core`, `1,239` in the existing app.

## chore — the Electron arm of the seed replay

`packages/core/scripts/replay-seed-in-electron.cjs` runs the `universe_seed`
replay inside a real Electron main process against the Electron-ABI binary.
Both arms now share `scripts/lib/seed-replay.mjs`, so the runtime is the only
difference between them — two copies would drift, and a divergence would then be
indistinguishable from the finding.

**Result: clean.** Electron 32.3.3 main, node 20.18.1, ABI 128, sqlite 3.53.1,
byte-identical row counts and WAL size to the Node control. Clean again with real
`safeStorage` for the archive (`REPLAY_SAFE_STORAGE=1`). That eliminates the
tenth and last suspect on the open corruption bug's list; see
`NewApp/CHANGELOG.md`.

### Electron 32 will not run a `.mjs` entry point, and says nothing

Passed one on the command line it produces **no output, no error and no exit** —
a headless main process that has to be killed. The byte-identical file as `.cjs`
runs and prints normally. The failure mode is a silent hang, which is
indistinguishable from the bug the harness exists to investigate.

Two more the harness has to get right for the same reason: `ELECTRON_RUN_AS_NODE`
is **deleted** from the child's environment (left set, Electron runs as plain
Node and the test arm silently becomes a duplicate of the control —
`process.type` is asserted inside), and every exit path calls `app.exit()`,
because a main process that never created a window never fires
`window-all-closed`.

### And the WAL size is printed now

A clean run peaks at **4,157,112 bytes** before the checkpoint. The previous
write-up recorded `checkpoint {busy:0, log:0, checkpointed:0}` being read as "the
WAL was empty" and carried into a wrong diagnosis; that is simply what a
successful `TRUNCATE` looks like. A number that had to be inferred is now
measured and printed.

## docs — the tooling shell is the redirected one

Verified this session and recorded in CLAUDE.md: **Claude Code's shell inside the
desktop app is MSIX-containerised.** `detectRedirect(process.env.APPDATA)`
reports `%APPDATA%` served from
`AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming`, and full
Electron profiles for **both** applications sit under that path —
`trade-analyzer-next` with its own `data\gen-001\data.sqlite` and two archive
files from the 2026-09-07 seed.

So the redirect quirks are not about a hypothetical packaged terminal. A
directory listing through `%APPDATA%` from such a session is a *merge* of two
views and cannot be trusted to say what exists, and "the shell was verified
clean" is a claim that needs the probe rather than an impression.
