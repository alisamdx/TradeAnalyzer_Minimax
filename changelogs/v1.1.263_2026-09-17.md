# v1.1.263 — 2026-09-17

## QC-210 can launch the reuse ruling it is best at detecting

`REUSE_CHECKS` in the Exceptions workbench was `QC-204, QC-205, QC-209`, so the check with
the strongest reuse evidence — a bar older than the ticker's listing — offered no "Confirm
ticker reuse" panel. It does now.

The rule moved out of `exceptionDetail()` into an exported `reuseCandidateFor(checkId,
key)`, because inline it could only be reached through the app's database and so had never
been tested. Seven tests now pin it, including the two boundaries that matter:

- **QC-210 offers no splice date**, because its key is a bare ticker. That is the honest
  answer: its evidence is *"some bars predate the listing"*, not *"the splice is here"*. An
  empty field asks the operator for the date instead of proposing one the check never
  measured.
- **A pre-splice finding offers the wrong date, and a test pins that it does.** The panel
  pre-fills from the key of the finding being ruled on, so opening `SOLS 2022-07-26` offers
  2022-07-26 — an editable field that looks authoritative and is three years early. The
  test exists so nobody later "improves" the pre-fill by inferring a date from elsewhere;
  the correct fix is to open the finding at the splice.

## And the inference behind it now refuses to guess

That empty field falls through to `core`, which inferred the splice date with
`ORDER BY last_seen_run_id DESC LIMIT 1` over the ticker's QC-204 findings. Every finding
of a reuse ticker shares a run, so the tie was broken **arbitrarily** — and on 2026-09-17
SOLS carried 21 QC-204 findings and JAN 7, six of JAN's dated 2022–2024 inside the
*previous* occupant's history. A wrong splice closes the membership range in the wrong
place, silently, since nothing downstream can tell a mis-dated splice from a correct one.

`recordTickerReuse` now infers only when there is exactly one candidate, and otherwise
refuses with the candidates listed so the operator can pick without going to look them up.
Nothing is written on the way to refusing.

This is the fix belonging in `core` rather than in the form, per this very file's own
header: *a rule enforced by the form is enforced only for the callers who use the form.*
The CLI's documented "omit the date" path keeps working wherever it was ever safe.

## A stale lockfile, surfaced on the way past

`packages/next`'s suite had been red on `workspace-versions.test.ts` for some time —
`package-lock.json` recorded `packages/core` at **0.6.9** and the root at **1.1.245**. It
was already wrong before tonight, and nothing surfaced it because the root `npm test` does
not include the workspace suites. Refreshed with `npm install --package-lock-only`, which
is what the test's own comment says to do. Worth knowing that **`npm test` alone is not
the full suite** — `npm run test:all` is.
