# v1.1.177 — 2026-09-03

## Stage-4 candidates capture the earnings date — the one gate no study could ever test

Migration 077 adds `earnings_date` and `days_to_earnings` to `brief_candidates`.

### The gap this closes

The earnings gate is the only rule in the wheel path that has **never** been testable, in any
study, for a single reason: `earnings_calendar` keeps one row per ticker with **no history**, so a
replay always sees today's next-report date rather than the date that was live on the pick date.
The consequence is on record — a retrospective run still selects NVDA on **2026-08-26**, its actual
earnings day, which is precisely the failure the gate exists to prevent.

v1.1.176 briefly looked like a way out, since `analysis_snapshots` rows carry a `daysToEarnings`
field. It is **NULL on 100% of 23,722 settled rows** — the column exists and is never populated.
That made **four** separate places where the gate could not be evaluated.

Capturing it at pick time is the only fix, and it works in one direction: **from the next brief run
forward, nothing retroactive.**

### What is stored

| column | meaning |
|---|---|
| `earnings_date` | next report date **as known on the pick date** — the ground truth, and auditable |
| `days_to_earnings` | the gap in days, which pairs with the existing `dte` to answer the gate's real question: does the report land inside the hold window? |

Both, deliberately. The date makes the stored value checkable; the day count is what a study
actually filters on, and deriving it later would mean re-deriving the as-of date too. ~14 bytes.

### NULL is not "clear"

**NULL means unknown *or stale* as of the pick date** — either the ticker had no calendar row, or
the stored date had already passed, which per the dice's own rule means the *next* date is unknown.
That is exactly how `roll-the-dice.ts` treats it: fail closed. A study that read NULL as "no
earnings, therefore fine" would reproduce the precise blindness this column exists to remove, so
the semantics are pinned by a test.
