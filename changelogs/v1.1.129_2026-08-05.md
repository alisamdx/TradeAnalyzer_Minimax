# v1.1.129 — 2026-08-05

Two data-lineage cleanups surfaced while investigating the `optionLiquidity` signal
(v1.1.127 / v1.1.128). Neither changes any score or trade.

## 1. Analysis mode result types were declared twice, and had drifted

`BuyResult`, `OptionsIncomeResult`, `WheelResult`, `StrategyResult`, `LizardResult` and the
`AnalysisResult` union existed in **both** `src/shared/types.ts` and
`src/main/services/analysis-service.ts`. Nothing enforced that the copies matched.

Diffing the five pairs found one real drift:

```
WheelResult   shared=14 fields   local=15 fields
  only local : currentIv: number | null
```

(`StrategyResult` looked drifted at first — its `suggestedStrategy` union is multi-line in one
copy and single-line in the other. It is identical.)

**Why it stayed invisible:** `AnalysisAllModesPayload` in `shared/types.ts` is built from the
**shared** copies, and `analysis-service.ts` imports that payload type while returning its own
locals. The local shape has a superset of fields, so the assignment is structurally valid and
TypeScript never complained. The consequence lands on the renderer, which sees the shared shape —
it simply could not see `currentIv` on a wheel row. That is why `AnalysisView` hand-rolls its own
`WheelRow` / `StrategyRow` types rather than importing these.

**Fix:** one declaration, in `src/shared/types.ts` (the documented home for cross-process types).
`analysis-service.ts` imports and re-exports them, so all existing
`from './analysis-service.js'` imports — `scoring-service`, `daily-options-snapshot-job`,
`daily-options-premium-history-job` — resolve unchanged. `currentIv` added to the shared
`WheelResult`. New fields go in `shared/types.ts` only.

## 2. Brief Replay's options blind spot, quantified

Replay has no historical option chains — none were ever stored — so three `TickerSignalData`
fields are unconditionally null for **every** ticker on **every** replay date:
`annualizedReturn`, `optionLiquidityScore`, `suitabilityScore`.

That interacts badly with the FR-SE-03 arithmetic (`scoring-service.ts` `scoreTicker`): a missing
signal contributes 0 to the numerator but its **full weight to the denominator**. So the signals
these fields feed are a permanent zero-at-full-weight:

| strategy | blind weight | composite built from |
| --- | --- | --- |
| **wheel** | `premiumYield` 19 + `optionLiquidity` 9 = **28** | **72%** of live weight |
| **income** | `premiumRiskRatio` 22 + `optionLiquidity` 13 = **35** | **65%** of live weight |
| bullish | 0 | faithful |
| bearish | 0 | faithful |
| buy | 0 | faithful |
| inflection | 0 | faithful |

### What this does and does not mean

- **Ranking within a replay run is unaffected.** The blind signals are zero for every ticker, so
  they scale all composites by the same constant and cannot reorder them.
- **Replay and live are not on the same scale, and their wheel/income rankings genuinely
  differ** — live populates these signals with per-ticker values that vary. **No absolute
  composite threshold may be carried between replay and live for wheel or income.** Bearish's
  ≥70 gate is safe: bearish has no options-derived signal.
- **Replay cannot A/B any of these signals.** Toggling one on or off shows a flat zero, because
  it is already null for everyone. This is what made the v1.1.127 `optionLiquidity` question
  unanswerable by the usual FR-SEY-5 instrument. Use the `analysis_snapshots` panel instead —
  66 wheel snapshots, 2026-05-14 → 2026-08-03, ~1,029 tickers each, carrying the real live values.

### Codified

Exported `REPLAY_BLIND_SIGNAL_KEYS` and pure `replayWeightCoverage(signals)` in
`brief-replay-service.ts`, with the full explanation at the top of the file and a pointer on the
three null assignments themselves. `tests/replay-weight-coverage.test.ts` (7) pins the 28/35
figures against the live `BASELINE_CONFIGS`, so a future weight change cannot silently widen the
blind spot, and asserts the four faithful strategies stay at zero.

No behavior change — replay scored exactly this way before; it just wasn't stated anywhere.
