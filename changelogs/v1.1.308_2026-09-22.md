# v1.1.308 — 2026-09-22

## A re-pulled EDGAR filing discarded every filing beside it

### The finding

One line in the 2026-09-22 day report:

| provider | endpoint | http | parse | error | n |
|---|---|---|---|---|---|
| edgar | `/submissions/CIK{cik}.json` | **200** | failed | `UNIQUE constraint failed: raw_edgar_filing.accession_no` | 1 |

A 200 that parsed to nothing, reported as though the parser had broken.

### What it actually was

`raw_edgar_filing` is `appendOnly: true` and **UNIQUE on `accession_no` alone**,
as a column flag and an index. That is precisely the shape already written up
for `raw_executed_order`: *a constraint enforces an invariant; a check reports a
violation, and if violating the invariant is a thing you want to SEE rather than
prevent, the constraint is in the way.*

Here it is worse than losing the evidence, because **the transaction is the
whole response**. One already-stored filing aborts the insert of every filing
beside it, and `parsed_row_count` comes back `0`.

The trigger is structural. The filers' slice is keyed on the trading date:

```ts
const dayIndex = Math.floor(Date.parse(`${run.tradingDate}T00:00:00Z`) / 86_400_000);
const start = (dayIndex * maxFilers) % Math.max(entries.length, 1);
```

So **two collector runs on one trading date ask the identical twenty filers**,
which is now the normal shape of a day whose scheduled run failed and was
re-run by hand. Measured:

| run | time | HSY | result |
|---|---|---|---|
| 28 | 17:05 | asked | ok, 4 filings stored |
| 30 | 20:47 | asked again | **failed, 0 stored** |

It cost nothing on the day only because HSY filed nothing between 17:05 and
20:47. A new 10-Q in that window would have been thrown away along with the
four duplicates — and QC-701 would then have reported the filer stale, with the
only trace being a parse error that names a constraint rather than a filing.

### The fix

`knownAccessions` — the accession numbers already stored for that CIK — is
passed into the parser, which skips them. A filing is immutable once filed, so
an accession already held is a genuine no-op rather than a fact being dropped.

It is a **recipe argument**, not a database read inside the parser, for the same
reason as v1.1.305's `derivatives` and v1.1.306's `refusedSymbols`: what was
already stored is a fact about capture time, not replay time, and a replay must
re-run the parse that actually happened. `sortedSet` returns `undefined` for an
empty set and `args` drops `undefined`, so a first-ever pull keeps the digest it
had before this argument existed.

### What was NOT fixed, and why it has to wait

**The key itself is wrong.** Every other supersession in the schema is
`(natural_key, observed_at)`; this one is the provider's id alone. But dropping
a unique index is not additive, and inside a generation changes are additive
only (02 §1) — so the correct key is a note for the next generation, recorded in
the spec, not a migration.

That leaves the constraint in place and the parser simply never offering it a
duplicate. Worth being explicit that this is the narrow half: if EDGAR ever
re-issues an accession with different content, the insert will still throw
rather than record the difference, which is the original complaint.

### The two historical failures, which were a different bug

Run 19 (2026-09-17, host 1.1.257) also holds two:

```
{"cik":"0001570585","ticker":"LBTYA"}  ok      4 rows
{"cik":"0001570585","ticker":"LBTYK"}  failed  0 rows
{"cik":"0000920760","ticker":"LEN"}    ok      4 rows
{"cik":"0000920760","ticker":"LEN.B"}  failed  0 rows
```

Share classes behind one CIK, asked twice **in one run**. That is the
per-CIK dedupe that landed in v1.1.275 — these predate it and are already fixed.
Worth recording because the two causes produce an identical error string, and
the run's `host_version` is what separates them.
