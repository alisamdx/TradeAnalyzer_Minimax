# v1.1.193 — 2026-09-06

## fix — the transactions range walk emitted a wasted one-day query on twelve dates a year

### The defect

`syncClosedPositions` walks Jan 1 → today in 30-day windows, stepping 31 days
each time (a 30-day window plus the day that separates it from the next). When
the range length is an **exact multiple of 31**, the walk lands with
`cur === endMs` and emits a final window covering a single day on its own.

That is one extra round trip to `/v1/accounts/{key}/transactions` — an endpoint
this project has already documented as intermittently unresponsive for ~120 s
answering `oauth_problem=nonce_used` (CLAUDE.md). The cost is small; the shape
is not, because it is a **calendar** trigger rather than an odd input. From a
Jan 1 start it lands on about twelve dates a year: in 2026, Feb 1, Mar 4, Apr 4,
May 5, Jun 5, Jul 6, Aug 6, Sep 6, Oct 7, Nov 7, Dec 8, then Jan 8 of 2027.

### Why it survived

`tests/etrade-transactions-slicing.test.ts` asserted exactly the right thing —
every window must have `span > 0`. But it drove the real `syncClosedPositions`,
which builds its range from **today**, so a run only ever exercised one calendar
configuration. The suite could see the fault on roughly twelve days a year and
was green on the other ~353 — and on those twelve it went red for reasons
unrelated to whatever anyone had just changed, which is how a test earns a
reputation for being flaky and stops being read. It was found on one of those
twelve days: 2026-09-06 is day 248 from Jan 1, and 248 = 8 × 31.

### The fix

- `buildDateSlices(startDate, endDate, maxSpanDays = 30)` is now an **exported
  function** rather than an inline block, so it can be tested against dates that
  are not today. That extraction is most of the fix: as an inline loop it was
  only ever reachable through the clock.
- A degenerate tail is **folded into its predecessor**, which grows from 30 days
  to 31 and stays inside the width that keeps a request from stalling. It is
  folded, not dropped — dropping it would leave a one-day hole in the coverage,
  and there is a separate test asserting the walk has no gaps.
- A one-day window is still emitted when the **whole range** is one day. That is
  a real interval, not a degenerate tail, and only a tail with a predecessor to
  fold into is removed.
- An inverted or unparseable range returns `[]` instead of walking.

### Tests

`tests/etrade-date-slices.test.ts` — sweeps **every start-date offset in a full
year** and asserts no multi-window result contains a zero-width window, plus
contiguity, no gap, no window over 31 days, the folded-tail case explicitly, the
genuine one-day range, the inverted range, and a narrower `maxSpanDays`. It
costs milliseconds and does not consult the clock at all.

Full suite: 1211 passing, 2 skipped.
