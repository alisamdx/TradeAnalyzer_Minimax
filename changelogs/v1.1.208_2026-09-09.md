# v1.1.208 — 2026-09-09

`@tradeanalyzer/core` 0.3.3, dictionary version **7**.

## The corruption has a signature

Two independent corrupt generations were read for the first time. They agree.

| | `gen-001-corrupt-20260907` | `gen-001` (2026-09-09) |
|---|---|---|
| dictionary | v5 (51 tables) | v6 (52 tables) |
| damaged | `meta_response` (Tree 5) + `raw_ticker_reference` (Tree 12) | `meta_response` (Tree 7) + `raw_ticker_reference` (Tree 14) |
| damaged pages | 453–469 | 418–432 |
| file | 2,342,912 bytes (572 pages) | 413,073,408 bytes (100,848 pages) |
| contents | 1 run, 1,092 responses, **0 bars** | 71 runs, 78,645 responses, **227,352 bars** |

**The same two tables both times, and only those two.** `raw_daily_bar` holds
227,352 rows in the larger file and is undamaged; `raw_ticker_reference` holds
1,083 and is wrecked. The damage does not track write volume.

Those two tables are precisely what `universe_seed`'s per-ticker loop writes
together in one transaction. And in the 413 MB file the damaged pages are
**418–432 out of 100,848** — inside the first ~570 pages, which is the region
that file's *first* seed allocated. The 2.3 MB file contains exactly one seed and
is damaged at 453–469: the same region.

**Inference, recorded as one:** the damage is inflicted during a `universe_seed`
and nothing afterwards extends it. Today's corruption most likely dates from
gen-001's own first seed on 09-06/07, not from anything in the last two days —
the 71 runs since have been writing into an already-broken file, which is why
QC-001 had been failing for **69 consecutive runs**. Those are consequences, not
69 new events.

Note what this does **not** explain: the offline replay writes exactly this
pattern — same schema, same transaction shape, same two tables, at the real pace
— and is clean in both Node and Electron.

## fix — `meta_open_handle` could not answer the question it exists for

It was keyed on `app_name` alone, so the upsert held only each application's
**latest** open. An earlier redirected open is overwritten by the next healthy
one, and the split becomes unaskable.

Measured on the real corrupt generation: both applications reported the same
`db_path`. That was true of their last opens and evidence of nothing — and it was
read, at first, as "no split". Keyed on **`(app_name, db_path)`**, a path an
application ever resolved survives every later open, so a second row is permanent
evidence of a split file set.

Implemented as a UNIQUE INDEX rather than a composite PRIMARY KEY: the DDL
generator emits `PRIMARY KEY` inline per column, so marking two produces
`table "meta_open_handle" has more than one primary key`. The index gives the
same identity and the same `ON CONFLICT` target.

Dictionary **v6 → v7**. Existing generations have rows in this table, so
`applyDictionary` reports the change as drift rather than rebuilding — by design
(a populated table is never rebuilt on a textual DDL comparison). A fresh
generation gets it outright.

## fix — the new exe stamped `openedAt` in UTC

`packages/next` wrote `new Date().toISOString()` while the collector host built
an ET timestamp from parts. The two look alike and differ only in the evening,
after UTC has rolled over.

In the forensic record of the corruption they sat side by side:

```
TradeAnalyzer 2  2026-09-08T03:02:53.252Z     ← actually 2026-09-07 23:02 ET
TradeAnalyzer    2026-09-08T23:54:19-04:00
```

One of the two rows being compared was a day out, and it reads as the small hours
of the 8th rather than the evening of the 7th.

**`tests/collector-host.test.ts` has pinned the collector host against exactly
this since the day it was written, and the new exe had the bug anyway** — because
the rule lived in a test attached to one implementation instead of in a function
both applications call. `etTimestamp()` now lives in `core`; both call it; the
host's test asserts the delegation, and `packages/core/test/time.test.ts` tests
the behaviour (evening rollover, both DST offsets, the round trip, the ICU
hour-`24` case, and that no `Z` is ever emitted).
