# v1.1.211 — 2026-09-09

`@tradeanalyzer/core` 0.3.5, dictionary version **8** (unchanged).

## The seed ran clean. Twice. And the fix everyone expected is not the reason.

Two consecutive `universe_seed` runs on fresh generations came back
`integrity_check: ok`, after **five** consecutive corruptions.

| | corrupt seeds (×5) | 2026-09-09 19:51 | 2026-09-09 20:09 |
|---|---|---|---|
| responses / references / memberships | 1,092 / 1,083 / 1,587 | identical | identical |
| failures | 6 | 6 | 6 |
| pages | 570 | 573 | 569 |
| `meta_response` + `raw_ticker_reference` | damaged, both, every time | **ok** | **ok** |

The row counts matching exactly is what makes this a result: the same work
happened. It is not clean because it did less.

### The baseline that had been missing every previous round

Before the first seed: 52 tables, `integrity_check: ok`, 1,196,032 bytes, every
row count zero, `meta_generation = 1` — so **TA2 created it**, not the collector
accidentally recreating one. "Was it clean before the seed" is answerable for the
first time.

### And `closed_at` earned itself on its first outing

```
TradeAnalyzer 2  v0.1.2   open 19:40:24  closed 19:40:28
TradeAnalyzer    v1.1.210  open 19:51:04  closed 19:51:38
```

Disjoint, by **reading** rather than by asking the operator what they remembered
having open. That question was put and answered on recollection on 2026-09-09,
which is the day this column was added.

### The checkpoint is struck off — it was measured doing nothing

v1.1.209 fixed `ElectronCollectorHost.close()` to checkpoint explicitly, and that
became the leading suspect. v1.1.210 made it log unconditionally. Both clean runs
say:

```
checkpoint applied — walBytes=4157112 busy=0 log=0 checkpointed=0
checkpoint applied — walBytes=4148872 busy=0 log=0 checkpointed=0
```

**A 4.15 MB WAL file, and zero pending frames.** `wal_autocheckpoint` (every 1000
pages by default) had already flushed everything long before `close()` was
reached. The explicit checkpoint moved no frames on either run, so it cannot be
what stopped the corruption. It remains a correct durability fix for the case
where a WAL *does* hold frames at close; it is not the cure.

**Without the unconditional logging this would have shipped as the presumed
fix.** One version earlier, both runs would have printed nothing at all.

### What is left, stated as candidates rather than as a conclusion

The corrupt seed at 01:08 and the clean seeds at 19:51 / 20:09 differ in at
least: the build (v1.1.208-era → v1.1.210), the dictionary (v7 → v8), the new
`recordCloseHandle` write at close, the checkpoint call itself (now excluded) —
and **the care taken over concurrency**. The last is the live one, because
"concurrent access" sits in the eliminated-suspect table on the strength of
recollection, and at dictionary v7 `meta_open_handle` could not have recorded a
close even if asked. Tonight's runs are the first where disjointness is evidence.

**Two clean runs do not close this.** It is downgraded from *reproducing every
time* to *not reproducing under a protocol where both applications are verified
closed*, and it stays open.

### Then concurrency was eliminated by test — a third seed, run with TA2 open

```
TradeAnalyzer 2  20:34:34 ──────────────────────────── 20:37:55
TradeAnalyzer          20:35:05 ─── seed ─── 20:35:40
```

TA2 held the generation for the whole seed and was actively reading its Data view
throughout. The diagnostic states the overlap outright from the recorded
intervals — *two writers on one write-ahead log* — and the result was
`integrity_check: ok`, with the same 1,092 / 1,083 / 1,587 / 6 and the same
2,347,008 bytes as the first clean run.

The suspect that was live at 20:20 was gone by 20:40, for 35 seconds of runtime.
The checkpoint line was identical under concurrency (`busy=0 log=0
checkpointed=0`), and read **"had nothing to do — the WAL held no pending
frames"** — the new verdict validating itself in the field on the same day it
shipped.

**Nothing left in the difference set explains corrupting `meta_response`**: the
checkpoint is a measured no-op, concurrency is measured clean, and the remainder
is a single-row `recordCloseHandle` write and a nullable column. Intermittency is
genuinely on the table — five corrupt then three clean is unlikely to be chance
(~2% on a naive exact test), but these are not independent draws from one
unchanged process, since the procedure changed too and the pre-seed baseline did
not exist before.

**Operationally**: QC-001 detects this condition on every run. What failed before
was not detection but that 69 consecutive reds arrived faster than they could be
acted on, from a retry loop that has since been removed. With the collector jobs
manual-only, a red gate gets seen — so the bug stays open under a check that
works, rather than blocking the build.

## fix — three instruments, each wrong in the way it was being trusted

Found by using them, in one evening.

- **`applied` folded an empty WAL into a successful checkpoint.** `log === checkpointed` is also true of `0 === 0`. The verdict is now five-way — returned nothing / busy / short / **nothing to do** / applied — because the ambiguity being removed at one level had been reintroduced at the next.
- **`diagnose-generation.mjs` suggested a rename that already existed.** The stamp is a date, so the second corruption in a day collides with the first and the operator gets `Cannot create a file when that file already exists` from the tool whose job is to stop them guessing. It now picks a free name and adds a time suffix — which is also the only thing that says *which* seed produced the file. Its `alreadyRetired` test was widened to match the longer names it now generates.
- **That stamp was built from `toISOString()`.** Any diagnosis run after 20:00 ET would have filed a generation under **tomorrow's** date, permanently, in the directory name that *is* the evidence. Now `etDate()`. `queue-job.mjs` had the same bug writing `meta_job_request.requested_at` — UTC into a column the applications stamp in ET, the exact split that put two time bases into `meta_open_handle` while it was being read as the forensic record of this bug.
- **`queue-job.mjs` told the operator to wait for a loop that no longer exists** ("claims one every ~2 minutes; it must be running"). It was removed in v1.1.206. It now says nothing will pick the job up and gives the Batch-view steps. **A script's closing instructions are documentation and go stale like the rest of it.**
