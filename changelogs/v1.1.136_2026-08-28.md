# v1.1.136 — 2026-08-28

## fix: near-term earnings dates were being truncated away by Finnhub's bulk result cap

### The failure

The 2026-08-26 brief ranked **NVDA the #1 wheel pick** (composite 73.3) and a top-5 income
pick (42.4) on the very day NVDA reported earnings (2026-08-26 AMC). It also appeared as
wheel #2 (66.3) on 2026-08-25. Both `wheel` and `income` are in
`EARNINGS_PENALTY_STRATEGIES`, so both should have carried the −20 earnings-within-45-days
composite penalty. With it applied, NVDA scores 53.3 / 22.4 and drops off both lists — the
other Aug-26 wheel picks scored 63.6–64.3.

Confirmed from local data: NVDA gapped **+6.3%** on 2026-08-27 (209.66 → 227.98) on 294M
shares vs ~100M normal, with ATM IV crushing **41.5% → 33.2%**.

### Root cause — a three-layer failure, all sharing one bad assumption

1. **Finnhub's free-tier bulk calendar caps a response at 1500 entries and truncates from
   the FRONT.** The job issued `from=today&to=+90d`; during earnings season that call
   returns **only the last two weeks of the range**. Verified against the live API: the
   exact call the job made on 2026-08-25 (`from=2026-08-25&to=2026-11-23`) returned 1500
   entries spanning **only 2026-11-09 … 2026-11-23**. Every near-term date was silently
   dropped. So NVDA's row was written as **2026-11-17** — one full quarter late.
2. **The v1.1.75 nearest-wins guard could not help**, because the near date was never in
   the payload to compare against.
3. **Phase 2's per-ticker lookup — which had the right answer — was never asked.** The
   per-ticker endpoint returns every quarter (`NVDA → [2026-11-17, 2026-08-26]`) and picks
   the nearest. But the delta filter only selected tickers with **no row or a past date**;
   the freshly-poisoned row held a *future* date, so the ticker was skipped, permanently,
   until the bogus date itself passed. The bulk write suppressed its own correction.
4. **The brief's own safety net had the identical assumption.** `refreshTickers` skips any
   ticker already holding a future date (`// Skip if we already have a future date`). The
   Aug-26 run proves it did nothing: `{"updated":0,"skipped":53,"failed":3}`. It also runs
   *after* Stage 3 scoring, so it could not have removed a pick in any case.

### Fixes

- **Adaptive bulk sweep (`sweepBulkWindow`)** replaces the two fixed 90-day windows. A
  response at the cap is now treated as *evidence of truncation*, not as data: the window
  is recursively halved until every slice comes back under the cap. Peak season needs
  slices as narrow as ~5 days (measured: `2026-10-27…10-31` = 639 entries, but
  `2026-10-27…11-05` overflows), so a fixed chunk size would not have been enough.
  Guarded by `MAX_BULK_CALLS` (160) and rate-limited to 1 call/s.
- **The sweep is reduced to the nearest future date per ticker in one pass** before any
  write, making the result independent of slice order.
- **Bulk data may only ever move a stored future date NEARER**, never further out.
  Finnhub's bulk calendar has coverage gaps, and a gap that hides a near date while
  returning the following quarter would push the stored date out — reintroducing this very
  bug. Moving a date nearer is fail-safe (the penalty engages earlier) and is also what
  heals poisoned rows, since poison always reads too FAR. A genuinely delayed report is
  picked up by Phase 2 once the stored date goes stale.
- **The Phase 2 delta filter now re-verifies rows dated beyond the swept horizon** (180d) —
  exactly the truncation bug's signature, and dates the sweep cannot see far enough to
  correct.
- **`earnings-refresh` now runs BEFORE `daily-intelligence-brief`** in the batch chain. It
  was registered after it (`index.ts` 636 vs 580), so every brief scored its −20 earnings
  penalty against a calendar refreshed only at the *end* of the previous chain — one cycle
  stale even when the data was right. Migration 067 applies the same ordering to existing
  installs (the 10..12 block becomes earnings-refresh, brief, paper-snapshot);
  `after_close_only` stays 1 — the sweep is too many API calls for the lean intraday slot,
  and a <24h-old calendar is acceptable for slow-moving dates (spec 08 §4).

### Backfill

Every non-manual row dated beyond +120d was re-verified per ticker — **14 of 14 were
poisoned**, each exactly one quarter late, confirming the signature:

```
AFRM 2027-02-04→2026-11-04   AIT  2027-01-25→2026-10-26   CACI 2027-01-19→2026-10-20
CAH  2027-02-03→2026-10-28   CPAY 2027-02-08→2026-11-02   EL   2027-02-03→2026-11-02
FN   2027-02-01→2026-11-02   IREN 2027-02-03→2026-11-04   JKHY 2027-01-25→2026-10-26
MSGS 2027-02-03→2026-10-29   RMD  2027-01-27→2026-10-28   SMCI 2027-02-01→2026-11-02
UI   2027-02-04→2026-11-05   VIAV 2027-01-26→2026-10-27
```

AFRM was an income pick in the 2026-08-27 brief. None were inside the 45-day penalty window
yet, so no *further* brief was mis-scored — but all 14 would have crossed into it over the
following weeks still showing a date one quarter late. Migration 067 deletes any remaining
far-dated non-manual rows so the next run re-verifies them per ticker; on this install the
backfill already corrected all 14, so the migration removes 0 rows here.

### Validation (FR-SEY-5)

Not a scoring-behavior change — no weight, policy parameter, or gate rule is altered. This
restores the −20 earnings penalty's *input data* to correctness so an existing, already-
validated gate fires when it was always supposed to. A replay delta would measure the data
fix, not a rule change.

### Tests

`tests/earnings-refresh-job.test.ts` +2 regression tests: a mocked Finnhub that emulates the

far-future row (asserts it is re-verified rather than trusted). Full suite: 963 passed.
