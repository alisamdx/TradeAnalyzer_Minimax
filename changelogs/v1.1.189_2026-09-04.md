# v1.1.189 — 2026-09-04

## The critic's context was filtered-favourable by construction

Two defects, both pointing the same way: the adversarial reviewer was handed a filtered view of
the pick it was meant to attack.

## 1. The signal list selected for good news

`topSignals` sorted descending on `weight × normalized` and took 4. That is a sort on
**contribution**, so a signal scoring badly has a small product and is pushed out by the
arithmetic — the filter's own mechanism excluded bad news.

Measured over **948 stored picks**:

| | |
|---|---|
| worst-scoring signal reached the critic | **8.3%** of picks |
| a reading below 35/100 reached it | **2.8%** (18 of 653) |
| wheel picks passed clean, no warning flag, carrying a hidden sub-35 reading | **59 of 250 (24%)** |

On DINO — the live pick that surfaced this — here is what the reviewer saw and did not:

```
SHOWN     ivRank           82.2  w22    fundamentalScore  86.0  w17
          premiumYield     45.0  w19    notDowntrend     100.0  w8
HIDDEN    recentVolatility 41.1  w10    leverageQuality   97.0  w4
          technicalNeutral 30.6  w11   <- the app's own "this is extended" read
```

`technicalNeutral` ranked **7th of 7** by contribution. The critic passed DINO clean, and its
rationale cited the "confirmed uptrend" that `notDowntrend` at 100 put in front of it.

## 2. The one measured ownership read was computed after the verdict

`own-at-strike` runs in `roll-the-dice.ts`, downstream of the critic. The reviewer had never seen
it in any form — not as a signal, not as a flag.

On **82 critic-PASSED wheel picks**:

- **57 (70%)** had a cost basis above the ticker's own 200-day average
- **37** were more than 10% above — DELL at **+97.9%**, AMD at **+79.2%**

DELL passed clean with an assignment price 98% above its 200-day. Whether that is *wrong* is a
separate question; the reviewer was not given the chance to have an opinion.

## What shipped

- **`selectCriticSignals()`** — exported and pure, so it is testable without an API call. Keeps the
  4 biggest contributors and appends the pick's **weakest** reading when the contribution sort
  excluded it, **marked** `isWeakestReading`. The mark matters: "the worst thing measured about
  this pick" and "one of the things that drove the score" are different claims to a reviewer.
- **`readOwnership()`** — the two-axis own-at-strike read (basis vs SMA200 + 52-week percentile,
  strike vs the 20-day low) in the context for **wheel** picks. It calls the same
  `readOwnAtStrike` the dice uses, on the same anchors, from the same table — only earlier, so the
  two can never disagree about a pick. Never throws; `null` reads as unknown, never as clear.
- **Prompt** — a SIGNALS paragraph explaining that `normalized` is always oriented higher-is-better
  and that the list is a sample (so absence of a concern is not evidence of none), and an OWNERSHIP
  paragraph defining each field and stating that an absent read is unknown rather than satisfactory.

## What deliberately did NOT change

**The list is still a sample, not full disclosure.** Three of the signals full disclosure would
surface for wheel — `technicalNeutral`, `recentVolatility`, `notDowntrend` — were measured **flat,
mildly inverted and anti-predictive** respectively (T6, v1.1.178). Handing the model every reading
would invite confident cautions built on signals this project has already shown do not predict, on
a critic that already passes only 17% of picks and is the dice's largest rejector. One guaranteed
sight of the worst reading is the smallest change that removes the bias.

**The prompt says nothing new about TREND.** That is T7, still open. `docs/wheel-parameters.md`
records why a prompt tweak there is not justified on current evidence — the same discipline that
stopped `notDowntrend` being acted on at 8 of 91 weight.

## Why this is not validated on outcomes

Stated rather than glossed, because the omission is real. The verdict is a **hard gate** — the dice
rejects anything that is not `pass`, and so does the v2 entry path — so this changes which trades
are taken, which is FR-SEY-5 territory.

But the only available test re-runs the LLM over stored picks and diffs verdicts, and the
intersection of "verdict flipped" with "expiry has settled" across one regime is a handful of
trades. A return figure from that would be a number with no power behind it — precisely the trap
recorded for the own-at-strike study (12 episodes in one 4-week window) and the brief-P&L
experiment before it.

**`scripts/critic-context-ab.mjs` measures the blast radius instead** — how many verdicts move and
in which direction — which is both answerable and what an operator needs before shipping. A change
that flips 2% of verdicts is a different proposition from one that flips 40%. Both arms are the
same code path on the same picks, differing only in the flag. Two API calls per pick; `--limit`
defaults to 10 so an accidental run is cheap.

**It has not been run.** It needs an `ANTHROPIC_API_KEY` and costs real money, so that is the
operator's call.

**`CRITIC_CONTEXT_V2=0` reverts both changes on a live run, with no rebuild.**
