# v1.1.63 — 2026-06-23

## Engine "zombie running" after restart — force-stopped on boot

### Symptom
Immediately after relaunching the packaged app pointed at IBKR paper
(`.\run-ibkr.ps1` → `[execution] broker=ibkr mode=paper @ 127.0.0.1:7497`), the engine reported
itself **running and armed** but placed nothing and connected to nothing:

```
GET /exec/state →
  engineState:"running", armed:true, automationMode:"unattended", executionMode:"paper",
  health:{ brokerConnected:false, lastCycleAt:null, healthy:false,
           degradedReason:"broker_disconnected" }
```

TWS was up and listening on 7497, but the app had **no TCP socket** to it — it never attempted a
connection.

### Cause
`engine_state` is persisted in `exec_risk_state` (so the governor restores `running`/`armed`
across a process restart), but the **broker connection and the cycle loop are process-local** and
are only ever created by `ExecutionEngine.startEngine()` → `ExecutionCore.startEngine()`
(`broker.connect()` + `startLoop()`). Nothing at app boot re-invokes `startEngine()` —
it's only called by the Trading Desk **Start** button (IPC) and the control API.

Result: after any restart (crash, reboot, a repackage-and-relaunch), the persisted state says
`running`/`armed` while the engine is actually inert — no connection, no loop, **no trades** — and
the UI/`/exec/state` give no hint that it's not really working. For an unattended engine that is
dangerous: it looks live but silently does nothing.

### Fix — force-stopped on boot
The operator chose **force-stopped-on-boot** (over auto-resume). On boot, `index.ts` now calls
`ExecutionEngine.reconcileStateOnBoot()`, which resets any persisted `running`/`paused` state to
`stopped` via the new `RiskGovernor.forceStopOnBoot()`:

- Audited distinctly as `engine_state { action: "boot_reset" }` so the audit log shows the restart
  caused it, not an operator Stop.
- A tripped kill switch is **left tripped** (manual-clear only); `stopped` is a no-op.
- Emits an `engine_state` event (UI updates) and refreshes the `armed` flag.

The operator must explicitly **Start** after a restart — which connects the broker and starts the
loop — so the engine never silently looks-armed-but-isn't.

### Why not auto-resume
Auto-reconnecting a trading engine on every boot (especially live) is surprising and risk-bearing;
the operator preferred an explicit, visible Start. Force-stopped-on-boot is strictly the more
conservative choice.

### Files
- `src/main/execution/risk-governor.ts` — `forceStopOnBoot(): boolean` (running/paused → stopped,
  `boot_reset` audit; leaves kill-tripped/stopped untouched).
- `src/main/execution/execution-core.ts` — `emitEngineState()` (re-broadcast persisted state).
- `src/main/execution/execution-engine.ts` — `reconcileStateOnBoot(): boolean` (calls
  `forceStopOnBoot`, emits, refreshes armed).
- `src/main/index.ts` — invoke `reconcileStateOnBoot()` right after engine construction, before the
  control API starts (so `/exec/state` reports the corrected state).
- `tests/risk-governor.test.ts` — 4 new tests for `forceStopOnBoot`.

### Validation (FR-SEY-5)
Validation-exempt: an engine-lifecycle change, not trade logic. No change to which trades are
selected, sized, or exited; strictly more conservative (won't trade after a restart until an
explicit Start).

### Tests
Full suite **651 passing**, 1 skipped. Typecheck clean.
