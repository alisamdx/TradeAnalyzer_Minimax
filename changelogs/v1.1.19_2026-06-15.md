# v1.1.19 — 2026-06-15

## Fix: premium-history mislabels wheel covered-call fallbacks as CSP

### What was wrong

`DailyOptionsPremiumHistoryJob` ran for the first time and wrote 1,830 rows for
`2026-06-15` (937 income + 893 wheel). Live verification was clean on every core check
(no null strike/premium/dte, no implausible values, full-universe coverage) **except one**:
~12% of the wheel rows (110/893) had a strike *above* spot and a *positive* delta — the
shape of a **call**, not a cash-secured put — yet were recorded with `structure = 'CSP'`.

### Root cause

This is not a chain-selection bug. The wheel analysis (`AnalysisService.findSuitableChain`)
deliberately **falls back to a covered call** when no suitable put exists in the
0.20–0.30 delta band with a live bid (see the explicit "try calls for CC" branch). Both
legs are valid parts of the wheel. The genuine bug was downstream: `WheelResult` carries
no put/call indicator, and `wheelResultToRow` **hardcoded `structure: 'CSP'`**, so every
CC fallback was mislabeled. Left unfixed, this would corrupt the CSP-vs-CC
return-on-capital analysis that `options_premium_history` exists to enable once the data
matures.

The CC fallbacks concentrate in lower-priced names (AA, ACGL, ADT, AES, …) where the
coarse strike grid has no put in the *tight* wheel band — note the **income** analyzer
uses a wider 0.20–0.35 band, which is why income caught AA's put (strike 60, δ −0.32)
while wheel fell back to a call (strike 75, δ +0.23).

### The fix (recording fidelity only — no trade-logic change)

`wheelResultToRow` now derives the structure from **delta sign**: a put has delta ≤ 0 →
`CSP`; a call has delta > 0 → `CC`; a null delta defaults to `CSP`. Sign is robust because
it's fixed by option type, not the spot level, so it survives E*Trade's stale-greek drift
(which only skews magnitude); and `findSuitableChain` guarantees a non-null delta on any
real recommendation. The wheel *recommendation* is untouched — only its recorded label —
so no FR-SEY-5 validation is triggered. Because the label is recomputed at capture time,
re-running the job self-heals already-persisted rows (`INSERT OR REPLACE`).
