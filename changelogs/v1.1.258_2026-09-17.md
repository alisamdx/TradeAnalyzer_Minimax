## QC-601 read two windows of one sweep as two observations

The check compared a ticker's newest `raw_earnings_event` row to the row before it,
ranked by `observed_at`. That assumed a sweep writes **one row per ticker**.

It does not. The bulk earnings calendar truncates at its provider row cap, so the sweep
is subdivided into windows (`sweepBulkWindow`, v1.1.136) and one run writes **one row per
window**. A ticker with two reports inside the ~90-day horizon therefore gets two rows
from the same sweep, covering different quarters:

```
MU    nearest 2026-09-30  [sweep window 2026-09-17..10-16]  observed 23:00:12.615Z
MU    nearest 2026-12-15  [sweep window 2026-11-16..12-15]  observed 23:00:13.024Z
```

Both dates are correct — Micron really does report on both. Read as successive
observations it is a 76-day later slip, which is the truncation signature the check
exists for. **Seven of the eight findings on 2026-09-17 were 409 milliseconds apart.**
The eighth (GIS) was a genuine prior-day comparison whose previous date had already
passed, so the roll to the next quarter was the calendar working.

Two consequences, and the second is worse than the noise:

- it fires more as a quarter-end pulls more tickers' second report inside the horizon —
  structural, not data-driven;
- because the last row written for a ticker is always its **farthest** date, a truncation
  that moved the **nearest** one — the fault the check was built for — was masked by
  exactly the same confusion that manufactured the false positives.

**Now:** the tested quantity is the *nearest future* report date per **sweep**, compared
sweep to sweep, and a previous nearest date that has already passed is clamped rather
than read as a slip. On the 2026-09-17 data: **8 fired of 9 evaluated → 0 of 3**, with
the surviving distribution `max 4 days` against a 14-day threshold — the quantity still
moves and the boundary is still reachable, which is the thing a decorative gate cannot
show.

## QC-602 said nothing about its own missing second source

`QC-602` cross-checks Finnhub's report date against E\*Trade's. It self-joins
`raw_earnings_event` on `source = 'etrade'`, and that table has **only ever held finnhub
rows** — 5,739 of them across 983 tickers, one source, for the life of gen-002. The join
returned nothing every run, so the check evaluated 0, fired 0, and looked exactly like a
check with nothing to report.

**This was already known**: `.ai/AI_CONTEXT.md` lists it under known-vacuous checks and
TODO #52 records it, measured 2026-09-16. What was missing is that **the gate's own
output never said it** — the knowledge lived in project notes, while the artefact the
operator actually reads each night rendered a dead check and a clean one identically. It
was dead on the night it was the only corroboration available for eight QC-601 findings,
and nothing in that night's RED report pointed at it.

**Now:** a missing second source is the finding. It reports one evaluation with a
9999-day sentinel — never the threshold's own value, the same device QC-603 uses for a
date never observed — because *"cannot be compared"* must not read as *"compared and
agreed"*. The per-ticker comparison runs unchanged once both sources are present.

Collecting E\*Trade earnings into the generation remains **TODO #52**: a collection
change, not a check change, so it cannot be rehearsed and needs a live run.

## The general form: the email now names checks that evaluated nothing

`EVALUATED NOTHING (4) — QC-303, QC-502, QC-909, QC-951`

The aggregate `Zero-fire checks: N of M` cannot distinguish a check that **found nothing
wrong** from one that **could not look**, and those are opposite pieces of news. The gate
already computed `checksVacuous` and the daily result already carried it — nothing
rendered it, so the only trace of a dead check *in the gate's output* was a zero in a
table nobody reads. Had that line existed, QC-602 would have been on it every night since
gen-002 opened, and the three other names now on it would not have needed looking for.

One line, bounded by the number of registered checks, so it cannot grow into the size
problem v1.1.248 fixed.

## The test that would have caught it, and the one that hid it

Every existing QC-601 fixture inserted **one row per observation** — written from the
check's own assumption about what a sweep looks like. That is the third time in this
project a reader has been tested against a fixture written from the reader (after the
legacy importer and the OSI padding), and it is why the new fixtures span two real runs.

Writing them surfaced a live trap: `beginRun` **resumes** a run that is still running on
the same trading date, slot and kind, so a second `newRun()` hands back the fixture's own
run and the test silently models one sweep where it meant two. It failed loudly, which is
the only reason it is a note here rather than a second bug.
