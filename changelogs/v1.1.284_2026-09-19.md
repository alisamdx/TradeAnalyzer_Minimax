## QC-009's stale findings, and a Form 4 key that could not tell one line from the next

### Problem

QC-009 (the same natural key stored twice from one response) keys its findings by **table** and evaluates every table every run. Run 22 read all 33 tables clean, yet five findings stayed open: a finding that stops firing without a remediation stays open (P9), and today's clean reading of a table says nothing about the runs that fired.

| finding | runs | today's rule over those runs |
|---|---|---|
| raw_analyst_estimate (322) | 8–16 | 0 per-response duplicates |
| raw_earnings_event (330) | 8–16 | 0 |
| raw_edgar_fact (1,641) | 8–16 | raised against v16's key, which lacked `period_start` |
| raw_insider_transaction (39) | 19 | 39, but the key is wrong: see below |

### The Form 4 key

`raw_insider_transaction` was keyed `(accession_no, transaction_date, filer_name, transaction_code)`. A Form 4 routinely lists several lots sold by one filer on one day. Japan Post's AFL filing on 2026-09-14 reports 9,545 @ 116.62 (holding 50,588,645 after) and 4,055 @ 117.02 (holding 50,584,590 after). Those are two facts under one key. Extending the key with `shares, price, shares_owned_after` still leaves one collision in run 19: David Obstler's two identical conversion lines (12,000 at $0, 12,000 after), most likely two different securities, since the parser does not store the title. **Only an ordinal identifies a line.**

**Dictionary v19** adds `line_no INTEGER` (nullable: "ingested before dictionary v19, which did not record the line"). `makeForm4Ingest` numbers each `<nonDerivativeTransaction>` by its position, counted **before** a line is skipped, so the number is the filing's own and never shifts. The natural key is now `(accession_no, line_no)`. Adding a nullable column is permitted growth on a populated table, and the rehearsal applied it in place to gen-002's 299 rows.

### Fix — QC-009 re-judges (`withRejudgedDuplicateFindings`)

For an open finding on a table evaluated **clean** today (a table firing today is live and untouched):

1. read the natural key in force when it last fired: `meta_dictionary` at `meta_run.dictionary_version` of `last_seen_run_id`. If it differs from today's key, close `rule_changed`, naming both keys.
2. otherwise re-count today's per-response rule over `first_seen..last_seen`: zero → `rule_changed`; any → stays open.

### Fix — replay compares what the source could have filled

`runReplay` compared every current fact column. A nullable column added since a run was recorded is null on its rows and filled by today's parser, so any replay of an earlier day would read `different` for growth, and QC-951 blocks on that. `raw_analyst_recommendation.provider_symbol` (v1.1.257) already had this latent problem. Comparison now uses only columns present in `meta_dictionary` at the **oldest replayed run's** `dictionary_version`, falling back to the whole entry when the old dictionary lacks the table. `TableDiff.columns` lists what was compared, so the narrowing is visible.
