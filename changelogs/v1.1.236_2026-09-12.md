`@tradeanalyzer/core` 0.6.6 · dictionary v15 · TradeAnalyzer 2 (`@tradeanalyzer/next`) 0.4.5

## How it was found

Pre-Monday validation, reading TradeAnalyzer 2's Runs view for the three `backfill_bars` runs of gen-001:

| Run | Host | QC-204 evaluated / fired | QC-205 evaluated / fired |
|---|---|---|---|
| 7 | 1.1.233 (1,000 splits) | 1,292,459 / 152 | **0 / 0** |
| 9 | 1.1.235 (6,700 splits, 7 pages) | 1,292,459 / 151 | **0 / 0** |

## Defects

### 1. Fractional volume stored as 0

`makeBarIngest` called `toIntegerStrict(b.v)` and wrote `volume.value ?? 0`. The converter returned `{ value: null, invalid: true }` for a fractional value, so the row got a zero and the `invalid` flag went nowhere — the column had no status. Polygon's daily `v` includes fractional-share trades and is non-integer routinely. The dictionary's premise ("a fractional share volume means the field is not what we think it is") was drafted, never checked against a live response, and every test fixture used whole numbers.

**Fix:** `volumeOrNull()` — the number as sent, or null when absent/non-finite/negative. `raw_daily_bar.volume` becomes `nullable(col.shares(...))`; `raw_eod_quote.day_volume` becomes `col.shares`. New unit `share_quantity` → REAL (first named `shares`; `next`'s AC-13 scan read the unit-label key as the Form 4 `shares` column, and collisions are renamed, never exempted).

The change is deliberately **no column added or removed**: `applyDictionary` treats it as DDL drift, which is *reported* on a populated table and *rebuilt* on an empty one. TradeAnalyzer 2 therefore still opens gen-001 on the new build, so the reset can be done from it.

### 2. The chain subset admitted nobody

`subsetCandidates` computes `advol20` as the mean of `close × volume` and already filtered null volumes. Given zeros it measured $0/day for every ticker.

### 3. QC-205 measured the wrong window

It took the last 40 rows per ticker (`ORDER BY trade_date DESC LIMIT 40`, no version handling) and compared the first 20 with the rest. With three backfills stacked that is ~13 days; and it only looked at the tail, so a reuse anywhere earlier was invisible. Rewritten to 03 §3.3: for each step larger than QC-204's `maxAbsChange`, the median of 20 sessions of volume before vs 20 after, latest observation per `(ticker, trade_date)` by `MAX(row_id)`. Every measured step is an evaluation (fired or not); a step without a full window either side is not measured yet. Keys are `TICKER DATE` with `affects: [stepDate]`.

### 4. One-shot jobs dated to the calendar, not the session

`collector-oneshot` used `deps.todayET()`. Run 9 (01:35 Saturday) recorded trading date 2026-09-12. Now `sessionOnOrBefore(deps.todayET())` — rules-only, no database, unscheduled closures included.

### 5. Refused query drawn as "no rows"

`DataView` set the refusal notice and still rendered `Grid` with `rows = []`. No grid (and no "Load more") under a refusal now.

### 6. Smaller

- Backfill batch note: `N blocking finding(s) awaiting a ruling across the generation`.
- `pilot-exit.ts` comment said QC-204/205 are warnings; both are `blocking`.

### 7. Two type errors shipped behind green tests

Vitest transpiles each file and does not typecheck, so both passed `npm test` while failing `npm run typecheck`:

- `tests/batch-run-notes.test.ts` (v1.1.235) imported `src/renderer/src/views/BatchView.tsx` into `tsconfig.node.json`, which has no `--jsx` (TS6142). `notePreview` / `runNotesText` moved to `src/shared/batch-notes.ts`, in both projects.
- `packages/next` `PilotConditionDto.key` lacked `backfill_queue` (added to core's `ConditionKey` in 0.6.4). `pilot.ts` assigns core's array to the DTO, which is where it failed; `PilotView`'s label map gains the entry.

## Not changed

The collector host stamps provider responses with `toISOString()` (UTC), which becomes `observed_at` on raw rows. Consistent within each table, so ordering by it holds; noted for later.
