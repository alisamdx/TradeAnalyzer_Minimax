# v1.1.145 — 2026-09-01

## fix: E*Trade log masked `/v1/accounts/list` as if it were an account key

v1.1.144's `maskEndpoint` replaced any segment following `/accounts/` with `{acct}`, so the
account-**list** call logged identically to an account-scoped one:

```
/v1/accounts/{acct}            ← actually /v1/accounts/list
/v1/accounts/{acct}/portfolio
```

`list` is a literal endpoint, not an identifier — and that distinction is exactly what tells
you which sync path ran. The very first real use of the new logging needed it and had to infer
it from call pairing instead. Now preserved verbatim; every genuine account key is still masked.

## First diagnosis from the v1.1.144 logging

The instrumentation did its job immediately. 28 E*Trade entries captured on the first run, all
200s — and **no `/transactions` call in any log file, ever**.

That settles the open question from v1.1.144, and it was none of the three candidates
(dormant token, rejected request, transaction matcher). The closed-position import had simply
**never been triggered**:

```jsx
{activeTab === 'closed' && (
  <button onClick={handleSyncClosed}>↓ Import Closed (YTD)</button>
)}
```

The control is labelled **"↓ Import Closed (YTD)"** and renders only on the Portfolio view's
**Closed** tab. There is no button named "Sync Closed Positions" anywhere in the UI — that
phrase is the `exit_notes` text the sync writes into each estimated row, which is what had been
repeated back as if it were a control name.

The calls actually observed (`/v1/accounts/list` + `/v1/accounts/{acct}/portfolio`) are the
regular open-position sync, i.e. the **Sync** button.

**Value of the change**: without logging, "the import produces nothing" and "the import was
never invoked" are indistinguishable, and three plausible code-level fixes were on the table for
a problem that needed none of them.
