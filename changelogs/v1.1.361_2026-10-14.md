# v1.1.361 — 2026-10-14

## QC-006 run completeness and QC-105 calendar coverage (`core` 0.6.74, `next` 0.4.59, dictionary v24)

Two of the 18 checks specified in NewApp 03 but never built (TODO #19). They are the two that most decide whether a GREEN day can be trusted, and they were built before the pilot's 20-day clean streak begins.

**Why QC-006 needed a new table first.** `runDaily` catches a phase that throws so the rest of the run can continue, which is right. But the catch only appended the message to `phaseErrors`, an array the function returned and nothing stored (the host put it in the batch-run note). So the generation, the gate, the email and every later rehearsal saw a crashed chains phase exactly as they saw one that ran and found few contracts. There was nothing for a completeness check to read.

**What changed**
- **`meta_run_phase` (new table, dictionary v24).** One row per daily-run phase and per phase-8 sub-phase (`events/<name>`), written as each ends: `ok`, `failed`, `cancelled`, or `not_reached`. `not_reached` is written after a cancellation for every scheduled phase that never started, so "did not run" is a row rather than an absence. Written through `collector/run-phase.ts` (`DAILY_PHASES`, `recordPhase`, `recordNotReached`). `runEventsPhase` gains `onOutcome`, which reports every sub-phase, successes included. A failed bookkeeping write is added to the phase errors and never stops the run.
- **QC-006 run completeness** (blocking, `cross_cutting`, R1). It fires on every phase row that is not `ok`. It is keyed `<trading date> <phase>` and affects only that date, so a crash breaks that day and no other. A later run that collects the same date and runs the phase cleanly closes it `data_corrected`. A day nobody re-collects stays open, because its hole is real. It evaluates nothing on runs with no phase rows (backfill, one-shot, pre-v1.1.361). Its scope is a phase that *throws*; a phase that ran and got error responses is the per-domain checks' job.
- **QC-105 calendar coverage** (blocking, `cross_cutting`). It counts the calendar days missing from `ref_trading_day` in [trading date − 5 y, trading date + 90 d] against a structural 0, and names the first and last missing day. It uses one key, so a reseeded calendar closes it the next night. Preflight seeds five years back to two years ahead, so it fires only when that seeding has broken. That matters because an unknown date is deliberately read as a trading day: a missing stretch would stop nothing, and would silently turn weekends into sessions.

**Expected noise: none.** In every data-collector run from 2026-09-15 to 2026-10-14 the batch status was `success` or `skipped`, never `failed`, so no phase threw. The quiet bad days (09-22, when E\*Trade answered nothing) were error responses, which QC-301/QC-401 and others report.

## Tests

`packages/core/test/run-completeness.test.ts` (10):
- `runDaily` with E\*Trade and Treasury calls throwing records all 8 phases and every sub-phase, with exactly `account`, `events/index-quotes` and `events/treasury` failed and QC-006 blocking on those dates only;
- a clean re-collection of the same date closes them `data_corrected`;
- a run for a different date leaves them open;
- a cancelled phase and everything after it are reported;
- nothing is evaluated without phase rows;
- a duplicate bookkeeping write is returned, not thrown;
- QC-105 is quiet on the seeded calendar, fires on a three-day hole and on an empty calendar (1,917 days), and opens and then closes through the gate.
