# v1.1.185 — 2026-09-04

## feat — keep both of the day's batch runs in the candidate pool

**No behaviour change to any recommendation.** This changes only what is *recorded*. The gate,
the formula and which trades the dice takes are untouched.

## What prompted it

Yesterday's dice pick was DINO. Today's was AAPL, and DINO had been rejected — `illiquid (6/15)`.
The same contract series had scored **9/15** the evening before. Decomposing the score:

```
Wed 17:36 ET   K=100.0   OI 112 -> 2.5   vol 27 -> 1.5   spread 7.2% -> 5   = 9.0 -> 9   PASS
Thu 10:35 ET   K= 97.5   OI  77 -> 0.5   vol  0 -> 0     spread 9.2% -> 5   = 5.5 -> 6   REJECT
```

**The spread did not move a point.** It is 8 of the 15 points and the only component that sets
what the contract actually costs to trade. The entire −3 came from two step-function counters
crossing their boundaries, plus rounding.

Three separate things were stacked, and none of them is "DINO became less liquid":

1. **A different contract.** Spot went 106.15 → 104.59, so the delta-band walk selected K=97.5.
   OI 112 vs 77 is two strikes, not one strike thinning.
2. **A different time of day.** Same-day volume is a *cumulative* counter. At 10:35 ET it holds
   about an hour of tape; at 17:36 ET, the whole session. Monotonic within a day, by construction.
3. **Rounding at a cliff.** 5.5 → 6.

## Why it was invisible

The brief runs on schedule at both the 10:15 and 17:00 ET slots — confirmed in `batch_runs`, both
`trigger = schedule` — and the dice emails **both**. But only the after-close run survived:
`scoring-service.saveBrief` deletes the same-ET-day rows before inserting, and `brief_candidates`
was unique on `(as_of_date, strategy, ticker)`.

So **248 of 250 stored wheel picks are evening readings**, and the morning pick the operator
actually reads and acts on is produced from data that is destroyed at 17:00 the same day.

That rule — "the after-close slot must overwrite the morning's partial view" — is correct for
every job that refreshes data. It is wrong for instrumentation about a job whose output is *acted
on at both slots*: storing one of them makes the other unauditable.

## How much the sampling matters

Across 250 stored wheel picks with a CSP leg (all evening readings):

| | |
|---|---|
| pass the >=8 gate | 46% |
| score distribution | `4:5 5:32 6:44 `**`7:53`**` 8:21 9:33 10:1 11:19 12:18 14:2 15:22` |
| would flip fail -> pass on the volume component alone | **93 (37%)** |
| spread <=15% (tradable) yet rejected as illiquid | **78 (31%)** |
| legs with `volume` null, scored as zero by `?? 0` | 23 (9%) |

The mode is **exactly 7** — one point below the gate. `MIN_TRADABLE_LIQUIDITY_SCORE = 8` was
inherited from the v2 execution engine's tradability bar, while the volume component was
introduced in v0.32.97 against the brief's **5**/15 gate, with the stated expectation that it
would "rescue or penalize at the margin". At 8/15 it is not marginal.

*(These flip counts are counterfactual arithmetic on stored legs, not an observed flip rate — the
observation is what this release makes possible.)*

## What shipped

**Migration 079** — `brief_candidates` gains:

- `slot` — `intraday` (~10:15 ET) or `after_close` (~17:00 ET), added to the unique index. A
  **phase**, not a clock time, so a re-run of the same phase still REPLACES: at most two rows per
  candidate per day, and repeated manual runs cannot accumulate.
- `volume` — the one score input that varies with *when* the run happened. Nullable on purpose:
  the score reads `leg.volume ?? 0`, so a study must be able to tell "not reported" from
  "did not trade".

Existing rows are backfilled from their own `generated_at`. Storage goes ~20 -> ~40 MB per trading
year, against `daily_briefs`' ~229 MB.

`resolveSlot()` prefers the scheduler's own `slotTime` (`batch_runs.slot_time`) and falls back to
the ET wall clock at a 14:00 boundary for manual, startup and API runs — comfortably clear of both
scheduled slots, so a late-running morning batch is still labelled `intraday` and cannot overwrite
the evening row it exists to be compared against. `DailyIntelligenceBriefJob.run` now accepts the
`slotTime` the handler interface has always passed.

**`scripts/slot-liquidity-drift-study.mjs`** — pairs the two phases of each `(date, ticker)` and
reports the score, volume, OI and spread deltas, how many pairs **cross the 8/15 gate** in each
direction, and how many had a different strike selected. It refuses to editorialise on a thin
sample and says so; it also detects a database the migration has not reached yet.

## What did NOT change, deliberately

- **`daily_briefs` still keeps one row per day.** Every existing replay script groups by date and
  assumes that; making it two rows would silently double-count across all of them. The candidate
  table is the instrument.
- **The gate, the thresholds and the formula.** Changing which trades are taken is FR-SEY-5
  territory and needs a replay — which needs this sample first.
- **`leg.volume ?? 0`.** Fixing the null-vs-zero conflation changes scores, so it waits on the
  same evidence.
