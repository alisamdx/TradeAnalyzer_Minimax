# v1.1.216 — 2026-09-09

Migration **082**. No `core` change.

## The two scheduled collector jobs go back on

`data-collector` (17:05) and `collector-watchdog` (19:30) are enabled again.
**`collector-oneshot` stays manual.**

They were all switched off in v1.1.206 after the collector emailed a RED gate
report 70 times in one day. Both causes are gone: the 2-minute claim loop —
the actual emitter — was deleted in that same version, and the generation has
since survived **four consecutive clean `universe_seed` runs**.

### Why this was necessary rather than merely safe

The pilot's **20-clean-day exit criterion** and the IV bootstrap's
**20-paired-day overlap** both advance only on days the collector actually
runs. Left manual, they advance when somebody remembers — and twenty
*consecutive* days is precisely what intermittent attention cannot produce. The
freeze was correct while the generation was untrustworthy; keeping it would
have quietly meant the pilot could never finish.

### Why the one-shot stays off

It carried the retry loop, and a one-shot is operator-initiated by nature —
there is nothing for it to do on a schedule. Its Run button is unaffected:
`BatchService.runJob` has never consulted `enabled`, so "off" means *does not
start on its own*, not *cannot be run*.

### The two scheduled jobs move together, deliberately

The watchdog exists to email when no daily run happened. With the daily run
off it would alarm every night about a run nobody scheduled; with it on, it is
the thing that notices a swallowed day. Enabling either alone is incoherent,
in both directions.

### Migration 082, because registration only seeds a fresh install

`registerJob` uses `INSERT OR IGNORE`, so the options in `index.ts` never reach
an existing `batch_jobs` row — the same frozen-column trap as `sequence_order`,
`config_json` and `after_close_only`, and the reason migration 080 was needed
to switch them off in the first place. A test now reads that SQL and asserts
the one-shot is **not** in it, checking executable statements rather than the
whole file, since the migration names it in a comment explaining the omission.

**A red gate now emails once a day. That is the interface working.** The
failure being avoided was never "an email" — it was seventy of them arriving
faster than one could be acted on.

## fix — a source-scanning test that went vacuous on line endings

`tests/collector-host.test.ts` slices `src/main/index.ts` on a literal
`"registerJob(\n    'data-collector'"`. With `core.autocrlf` on, a fresh clone
checks that file out as **CRLF**, the pattern matches nothing, and every
assertion in the block then runs against an empty string and passes.

Found because an editing pass rewrote the file as CRLF and the test went red —
which is the lucky version. The unlucky version is a clean checkout on another
machine reporting green over a guard that is examining nothing. Newlines are
now normalised in `stripComments`, before any pattern touches the source.

`1,254` tests.
