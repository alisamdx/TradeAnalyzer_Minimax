# v1.1.0 — 2026-06-14

## v2 execution subsystem — Phase 0 (schema foundation)

First code increment of the v2 automated-execution build. This phase lays the durable
schema and shared types; nothing is wired to a service or UI yet (the tables are
**dormant**). Full design is in `Requirements/v2-execution/` (docs `00`–`05`).

### Migration 045 — `045_execution_engine.sql`

Seven namespaced `exec_*` tables (one cohesive migration, mirroring
`022_scoring_engine.sql`):

- **`exec_config`** — singleton (id=1) governor rules. Seeded with the locked v2.0
  defaults: `execution_mode='paper'`, `capital_ceiling=10000`, `max_risk_per_trade_pct=5`,
  `max_concurrent_positions=5`, `daily_loss_trip_pct=10`, `max_positions_per_ticker=1`,
  `eligible_strategies='inflection'`, `proposal_shelf_life_min=120`.
- **`exec_risk_state`** — singleton (id=1) live risk ledger + engine state. Seeded
  `engine_state='stopped'`, kill switch clear.
- **`exec_proposals`** — candidate orders awaiting approval (semi-auto).
- **`exec_orders`** — the order state machine; `client_order_id` UNIQUE (idempotency key).
- **`exec_fills`** — fills reconciled from broker truth.
- **`exec_positions`** — bot-managed positions (distinct from the v1 E\*Trade portfolio
  mirror).
- **`exec_audit_log`** — append-only forensic record.

Singleton rows seeded in-migration via `INSERT OR IGNORE`; CHECK constraints enforce the
single-row invariant and the enum domains (`execution_mode`, `engine_state`, order/position
status, close reason). Timestamps use the repo idiom `strftime('%Y-%m-%dT%H:%M:%fZ','now')`.

### Types & tests

- `src/shared/types.ts`: added the `Exec*` domain types (`ExecConfig`, `ExecRiskState`,
  `ExecProposal`, `ExecOrder`, `ExecFill`, `ExecPosition`, `ExecGateResult`,
  `ExecAuditEntry`, plus the `EngineState` / `ExecutionMode` / status unions and `ExecLeg`).
- `tests/exec-schema.test.ts` (7 tests): table presence, seeded defaults, single-row +
  enum CHECK enforcement, idempotent re-seeding, and `client_order_id` uniqueness.

### Scope / safety

No behavior change to the running app — the new tables are created and seeded on next
launch but read/written by nothing yet. Next: Phase 1 (the `ExecutionBroker` interface +
`MockExecutionBroker`) and Phase 2 (the risk governor), both buildable/testable with no
IBKR account.
