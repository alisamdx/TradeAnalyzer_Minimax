# v1.1.150 — 2026-09-01

## feat: fall back to executed ORDERS when the transactions endpoint is dead

### Why

`/v1/accounts/{key}/transactions` never responds for this account. Nine hypotheses tested
against the API log, all falsified:

| Dimension | Tried | Result |
|---|---|---|
| Range | 8 months, 31 days, 7 days, none | identical hang |
| Path | with and without `.json` | identical hang |
| Params | `sortOrder=DESC`, `count=5`, `count=50` | identical hang |
| Transport | fresh nonce, fresh signature | same `nonce_used` |
| Our code | 28 other calls, same key + signing | all 200 in ~300 ms |

E*Trade exposes **no dedicated closed-positions endpoint** — Transactions and Orders are the
two documented ways to reconstruct one. Only Transactions was ever wired up.

### Change

When Transactions fails, the import now falls back to `/v1/accounts/{key}/orders` with
`status=EXECUTED`, mapping executed orders into the existing `TxLeg` model so
`matchClosedPositions` and `insertClosedPosition` work unchanged — including writing a real
`exit_price`, which **no row in the database currently has**.

Orders is arguably the better source regardless:

- **`orderAction` states intent outright** (`SELL_OPEN`, `BUY_CLOSE`, `BUY_OPEN`,
  `SELL_CLOSE`). The transactions path had to guess with "a sell must be an open", which
  mislabels a long-option round trip and an assignment.
- **`averageExecutionPrice` is the realised fill**, not a mark — the entire point of this
  import.

The fallback is reported, not silent: the operator sees `Transactions unavailable, falling
back to executed orders: …`.

### Diagnosability

On the first orders page the code logs a **structural summary — key names only, never values**.
Success bodies stay unlogged by design (they carry fills and balances), but if E*Trade's schema
differs from the documented one, this makes the mismatch readable instead of prompting another
blind guess.

### On the research that prompted this

The Orders API lead was correct and useful. Other details in that write-up were not, and are
recorded here so they are not repeated: the base URL was given as `https://etrade.com`
(production is `https://api.etrade.com`, sandbox `https://apisb.etrade.com`), the path omitted
the `/v1/` prefix, and one comment was garbled filler. Its "critical flags" — `MMDDYYYY`,
`count` max 50, `marker` pagination, `.json` — were all already implemented and all already
timed out.

### Tests

New `tests/etrade-orders-fallback.test.ts` (4): transactions timing out routes to orders and a
**real fill lands in `exit_price`**; `orderAction` drives OPEN/CLOSE so a `BUY_OPEN` →
`SELL_CLOSE` long round trip is read correctly; numeric `marker` pagination is followed; and the
reason for the fallback is surfaced. `etrade-transactions-slicing.test.ts` updated — a dead
transactions endpoint is no longer fatal. Suite: 1009 passed.
