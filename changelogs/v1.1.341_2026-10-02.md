# v1.1.341 — 2026-10-02

## Constituent sectors and names are stored as text, not HTML

**Symptom.** The spread shadow report listed open positions under `Oil &amp; Gas Exploration &amp;
Production`, `Fertilizers &amp; Agricultural Chemicals` and `Technology Hardware, Storage &amp;
Peripherals`.

**Cause.** `ConstituentsService.parseWikipediaTable` turned each table cell into text by stripping tags
with a regex and never decoded HTML entities, so `&amp;` (and `&#39;`, `&quot;`, …) reached
`constituents.sector` and `company_name` exactly as the page source had them. Vanguard, the primary
source, carries no sector, and a refresh deliberately keeps the stored one, so an escaped sector
persisted indefinitely. Consequence beyond display: anything grouping by sector — the spread mode's
3-per-sector cap and the shadow report's sector tallies — would treat `Oil &amp; Gas` and `Oil & Gas`
as two sectors if both spellings were ever stored.

**A second fault behind the same escaping.** Column detection accepts a sector cell only if it is under
40 characters, measured on the raw text. An escaped long sub-industry (`Oil &amp; Gas Exploration
&amp; Production` is 42 characters raw, 34 decoded) in the sample row made the parser find no sector
column at all, and the whole table was stored without sectors.

**Change.**
- `decodeHtmlEntities` (named and numeric entities, one pass so `&amp;lt;` becomes `&lt;`, never `<`)
  and `cellText` (strip tags, decode, trim) in `constituents-service.ts`. Company and sector cells, and
  the company/sector column detection, all use decoded text. Vanguard's `longName` is decoded too.
- **Migration 090** decodes the same entities in stored `sector` and `company_name` values, `&amp;`
  last to match the code; a correctly stored value contains none of them, so it is a no-op on re-run.

Tests (`tests/constituents-refresh.test.ts`, +3): a Wikipedia fallback whose first row carries an
escaped sub-industry and `AT&amp;T` stores both decoded (fails without the fix: the sector column is
lost); the decoder on named, numeric, double-escaped, unescaped and unknown input; migration 090
applied twice to escaped and clean rows.
