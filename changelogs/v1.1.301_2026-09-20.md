# v1.1.301 — 2026-09-20

TradeAnalyzer only. Bull put spread: a second candidate pool, run beside the first (BPS-1, 08 S11).

## The question

BPS-1 asked whether the spread's pool should be the wheel screen's output at all. It is worth stating
what that screen is *for*: the wheel composite spends **21% of its weight on fundamentals + leverage
quality**, and that weight exists for exactly one reason — an assigned cash-secured put means you own the
stock, so business quality decides whether assignment is survivable.

A bull put spread never owns anything. Max loss is the width, known at entry, capped. So that 21% is for
this trade at best inert, and at worst a bias toward large, calm, well-capitalised megacaps, which are
precisely the names where a 0.30Δ put pays least. Add `notDowntrend` (weight 8), which the spread's **own**
study measured backwards — closes *below* SMA50 returned +9.4% against +5.7% — and roughly **29 of 100
weight is irrelevant or inverted**.

There is a sharper version of the same point. **Every number in the #43 study was measured on
wheel-selected names.** "+75% at Δ0.30 / 5% wing" is not a statement about bull put spreads; it is a
statement about bull put spreads *on stocks the wheel screen liked*. Nothing in the evidence base speaks
to any other population.

## Both, not either

Operator decision (08 S11): **run both in shadow and decide on the data.** Switching outright would
forfeit the comparison permanently — the same shape as the `iv_history` splice, where two sources were
joined with **zero overlapping ticker-days** and no later analysis could separate source character from
market regime. A paired same-day sample is cheap now and impossible afterwards.

It costs nothing to collect. `spread_chain_capture` already captures income chains
(`SPREAD_CAPTURE.strategies = wheel, income, bullish`) and `brief_candidates` already stores every
strategy's top 15, so the second arm makes **no additional E\*Trade calls** — it is arithmetic over data
already on disk.

## What had to become per-pool, and why each one matters

Adding a second arm is only useful if the two cannot contaminate each other. Four places assumed one:

- **The uniqueness key.** `(as_of_date, slot, ticker)` would have let the second pass *overwrite* the
  first's row for any ticker both screens liked — which is exactly the paired population the comparison
  most needs. Now `(as_of_date, slot, pool, ticker)`.
- **The slot replace.** A re-run deleted the whole slot; it now deletes the slot **for that pool**, or
  each pass would wipe the other.
- **The episode collapse.** Keyed on ticker alone, a name in both pools would have collapsed into one
  position — deleting the pair rather than recording it. Now keyed on `pool|ticker`.
- **The sector-cap simulation.** Run across both books, an `income` position could consume a sector slot
  from the `wheel` book, and the skipped counts would describe a portfolio nobody would ever hold.
  Simulated per pool.

Run grouping in the report is per pool too, or the two funnels merge into one unreadable row.

## The gate stays on one pool

§4 is judged on `wheel` (`SPREAD_GATE_POOL`). Letting the gate follow whichever arm currently looks better
would change what it measures mid-sample — the seam this whole exercise exists to avoid. The challenger is
reported beside it and never folded into it.

The report also prints `overlap`: ticker+expiry pairs **both** pools picked. If that turns out to be most
of the book, the two screens are not really choosing differently and BPS-1 answers itself.

## Also decided

**A defined-risk trade may go into names the wheel would refuse on quality** (08 S11, second half). That
is the point of capped loss, and it follows from using a pool with no fundamental weight rather than from
any new rule. The counter-argument is recorded rather than dismissed: a gap through the long strike *is*
the max loss, and gap risk was tested in this project and falsified as a signal — so the evidence for
going down-quality is exactly what this experiment is meant to produce.

## The comparison refuses to run on unpaired days

The two arms start on different dates: `wheel` has run since 2026-09-14 and holds 10 positions, `income`
begins on the next brief. A lifetime per-pool total would therefore compare a full book against an empty
one and present it as a result — "income is worse" when income has simply not run.

So `pools.books` covers **only the dates every pool ran**, and `pairedDays` is reported as a quantity in
its own right. At zero, the report says so in as many words:

```
## Candidate pools (08 S11 — both run in shadow)

  NO PAIRED DAYS YET — the arms have not both run on any date, so there is nothing to compare.
  This is not a weak result, it is no result. The income arm starts on the next brief run.
```

This is QC-907's lesson applied before it could bite: an overlap check written as "for every day both
series exist, compare them" **passes silently on zero such days**, and "no overlap" then looks exactly
like "clean overlap". Making the paired-day count a first-class number is what keeps them distinguishable.
Pinned by a test that builds a wheel-only book and asserts every pool's book reads empty while the
position is still counted everywhere else.
