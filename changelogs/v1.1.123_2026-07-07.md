# v1.1.123 — 2026-07-07

## Filters Prefill: dual-schedule (lean intraday + after-close)

User request: since Filters Prefill already runs *after* the Daily Intelligence Brief in the
after-close chain (it's registered last — highest `sequence_order` — specifically because it
needs fresh caches/iv_history/technical_signals/earnings), running it *again* in the lean
~10:15 ET intraday slot wouldn't add any time to brief generation, and could surface wheel/IV
opportunities during trading hours instead of only after the close.

### Pushback considered before shipping

The ask was originally framed as "lean instead of after-close" (swap the schedule, don't add
one). Investigated first because the `afterCloseOnly` gate isn't incidental — two real risks:

1. **Replacing loses the reliable EOD scan.** `filter_template_runs` stores latest-only per
   template — whatever ran last is what the Filters view/email show until the next run. A
   straight swap means anyone checking mid-afternoon sees stale 10:15 data.
2. **Two of the four default templates (`rsi_oversold`, `price_alert`) read SMA/RSI off
   `historical_prices`**, which does hold a partial same-day bar by 10:15 in the lean slot
   (the same class of staleness CLAUDE.md documents for breakout/volume_surge scoring) —
   confirmed via `daily-technical-signals-job.ts`, which is *not* `afterCloseOnly` and runs in
   both slots, computing `trend_label`/RSI off whatever `historical_prices` holds at slot time.

A follow-up investigation traced exactly what `wheel_vetted`/`iv_rank_high_vetted`'s gates
read, since those are the two templates that matter for the email:

- **Downtrend gate** — `filter-templates-service.ts`'s `loadTrendLabel()` reads the stored
  `technical_signals.trend_label` column with no freshness check — whatever the *last
  completed* `daily-technical-signals-job` run wrote. Not a same-day-partial-bar read; it's
  effectively the same whether checked at 10:15 or 16:30 (it only changes when that job
  reruns).
- **Wheel-suitability score (≥70 gate)** — `calculateWheelSuitability()` uses only ROE, D/E,
  and market cap from a 24h-TTL fundamentals cache — no price/technical input at all.
- **Liquidity check (OI/spread/IV ceiling)** — always a live E*Trade options-chain call
  (5-min cache) — genuinely live regardless of time of day.

Conclusion: `wheel_vetted` and `iv_rank_high_vetted` are safe (and arguably *better*, since
the liquidity check reflects live intraday quotes) to run at 10:15. `rsi_oversold`/
`price_alert` are the ones with real partial-bar exposure and aren't especially
time-sensitive signals anyway, so they stay after-close-only.

### What shipped: dual schedule, not a swap

`FiltersPrefillJob` now runs in **both** orchestrator slots:

- **After-close (~16:30+)** — unchanged: full `DEFAULT_PREFILL_TEMPLATES` (rsi_oversold,
  iv_rank_high_vetted, price_alert, wheel_vetted), canonical EOD view + email.
- **Lean intraday (~10:15)** — new `DEFAULT_LEAN_PREFILL_TEMPLATES` = `['iv_rank_high_vetted',
  'wheel_vetted']` only, override via `config_json.leanEnabledTemplates`.

`afterCloseOnly: true` is removed from the job's registration in `src/main/index.ts` so the
orchestrator's `!lean || !j.afterCloseOnly` filter (`batch-orchestrator-job.ts`) includes it in
both slots. Inside `FiltersPrefillJob.run()`, a new `isLeanRun(slotTime)` reads the
orchestrator's own `scheduleSlots`/`leanSlots` config (via `batch_jobs` row
`id='batch-orchestrator'`) and calls the existing `isLeanSlot()` helper — the same logic the
orchestrator itself uses to decide which slot is "lean" — so the job picks the right allowlist
key (`enabledTemplates` vs `leanEnabledTemplates`) without hardcoding a slot time. A manual/
startup run (no `slotTime`) is never lean, matching existing orchestrator semantics.

Each slot still **overwrites its own template's stored row wholesale** (unchanged
latest-only behavior) — the after-close run always overwrites whatever the lean run wrote
that morning, so the canonical EOD state is never left showing intraday data.

The lean-slot email is tagged so it isn't mistaken for the EOD version: subject line gets a
`(Intraday)` suffix, and the HTML header gets an "Intraday Preview" badge
(`buildFiltersPrefillEmailHtml()` gained an optional 4th `runLabel` param).

### Live DB patch (same gotcha as v1.1.121)

`BatchService.registerJob()` seeds `batch_jobs` via `INSERT OR IGNORE` — it only writes
defaults on first-ever row creation; every later app start preserves the existing row.
Removing `afterCloseOnly: true` from the code has **zero effect on this install's existing
`filters-prefill` row**, which already has `after_close_only = 1` from a prior version. With
the app confirmed not running (health checks on 7432/7433 both refused), patched the live row
directly:

```
after_close_only: 1 → 0
config_json: added "leanEnabledTemplates":["iv_rank_high_vetted","wheel_vetted"]
```

(The new `leanEnabledTemplates` key would have safely defaulted to
`DEFAULT_LEAN_PREFILL_TEMPLATES` even without this patch — unlike v1.1.121's gap, this is a
wholly new, previously-absent key, not a stale array needing content changes — but adding it
explicitly keeps the DB row self-documenting.) A fresh install seeds both correctly from the
code defaults on first run.

### Tests

`tests/filters-prefill.test.ts` (+8): lean slot runs only the lean allowlist; after-close slot
(last of two configured) runs the full allowlist; an explicit `leanEnabledTemplates` allowlist
is honored independently of `enabledTemplates`; a manual run (no `slotTime`) falls back to the
full after-close set; the email subject/body gets tagged "(Intraday)"/"Intraday Preview" in
the lean slot and not in the after-close slot. Full suite: 915 passed, 1 skipped.
