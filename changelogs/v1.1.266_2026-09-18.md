# v1.1.266 — 2026-09-18

## R6 — the first remediation in the system that actually runs

Spec §6 has listed seven automatic remediations since B5 and described them as current
behaviour: *"The gate may request only these… Every attempt is appended to
`remediations_json` with its outcome."*

None of them existed. Measured on gen-002, 2026-09-17:

```
qa_exception.remediations_json    '[]'  ×12,970   (every row, every value)
resolved via a succeeded remediation:   0
grep runRemediation|applyRemediation|remediate  →  nothing
```

Every check's `remediation:` field was a declaration of intent. And that left a **dead
branch** one level up, which matters more than any single re-fetch:
`reconcileStoppedFiring` may auto-resolve a finding only when *"a remediation in
`remediations_json` succeeded **and** the fingerprint now evaluates clean"* — it read a
field nothing wrote, so the first half was never true and the branch could never fire.
Same shape as a threshold whose tested quantity can never reach it.

`runR6ActionRefetch` re-fetches a ticker's splits and dividends around its unexplained
discontinuities, and records the attempt. Two tests assert the branch now works, and that
it still refuses to resolve when the remediation **failed** — because a finding that goes
quiet without a successful remediation must stay open, which is how the earnings-date bug
hid for a quarter.

## Why this, and not the five-year dividend sweep

The gap it closes is real: QC-204 explains a step with a split **or a special dividend**,
and `raw_split` covered five years while `raw_dividend` covered **ten days** — only the
daily seven-day sweep ever fetched dividends, the backfill never did. For 138 of the 151
findings open on 2026-09-17 the dividend branch could not match at all.

The obvious fix was a five-year market-wide sweep in the backfill. Measured before
writing it: about **845 pages and 845,000 rows**, a 77 % increase on a backfill that makes
~1,100 calls — and of 4,696 dividends in the last eight trading days, **130** were for
universe members. R6 fetches the same evidence only where a step needs explaining:

```
run 19:  61 tickers, 122 calls, covering all 123 open QC-204 findings
```

Which is what §6 specified in the first place. The bulk sweep was the expensive way to do
something the architecture already described as targeted.

## Shape

- **Once per ticker, not per finding.** SOLS carried 21 QC-204 findings; a ticker's splits
  and dividends are one fetch whatever the number of steps. The window spans that ticker's
  first to last step, ±7 days, so a boundary action is inside the range asked for.
- **After the gate, before the email.** Which discontinuities are unexplained is the
  gate's answer, so R6 cannot precede it; and the attempt belongs on the record the
  operator reads.
- **It resolves nothing itself.** Whether the re-fetched action explains the step is
  decided on the *next* run, when QC-204 re-evaluates and the gate weighs this attempt
  against a fingerprint that has gone quiet. Deciding "explained" inside the remediation
  would put the verdict in the thing being judged, which is exactly the separation §6
  draws.
- **One attempt per finding, ever.** A step still unexplained after a re-fetch is an
  operator's question, not something to re-fetch nightly. The collector's removed claim
  loop re-ran one failing job 70 times in a night because nothing capped the attempts.
- **60 tickers per run**, deliberately *not* tuned to today's 61 — fitting a constant to
  the current backlog is how thresholds stop meaning anything. It clears in two runs and
  reports `deferred`.
- **A failure never fails the run.** A remediation that could halt collection would be
  worse than the finding it chases; the outcome is recorded as `failed` and the run
  continues.

## What it will not fix, by design

Some of the 61 are ticker reuse — SPCX and NIQ are on the list, and both were flagged by
QC-210. R6 will fetch, find no action, and leave them open for an operator ruling, which
is correct: their answer is a splice, not a missing dividend. Two wasted calls each,
against the complexity of excluding them.

## Validation

`rehearse-gate` cannot exercise this — a change to what is **fetched** needs a live run.
What was measured beforehand is the candidate selection, which is a pure read: 61 tickers,
122 calls, 123 findings. Tomorrow's run is the first real exercise.
