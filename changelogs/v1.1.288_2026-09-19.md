# v1.1.288 — 2026-09-19

`core` 0.6.43, `next` 0.4.31.

## R3: provisional bars are re-fetched final before the gate

### Why

Spec 03 §6 lists R3, "re-fetch today's bar after the settlement window", as QC-203's remediation, and spec 04 places it at the end of the collection phases. It was never built. Until v1.1.287 that did not show, because every same-day bar was stored provisional whatever the clock said, so no re-fetch could have helped. With v1.1.287 a bar is provisional only when its response arrived before 17:00 ET, which happens when a run starts before the window closes (a manual run, or a scheduled run started early). Without R3, such a bar stays provisional until the next day's five-day fetch supersedes it.

### What it does

`runR3FinalBarRefetch(host, db, run)` in `collector/remediation.ts`, called by `runDaily` after the last collection phase and before the gate:

1. `provisionalBarTickers`: the tickers whose **latest** bar for the run's trading date, among this run's rows, has `is_final = 0`. None → nothing to do.
2. If `barSettled(tradingDate, host.nowET())` is false, the window has not closed. It re-fetches nothing, since another fetch now would only store another provisional bar, and reports `windowOpenAt`.
3. Otherwise it calls `runBarsPhase` for exactly those tickers with `depthDays: 0`, so the request covers the one day. The different `from` also changes the request params, so dedup cannot swallow a body identical to the phase-2 response. The responses arrive settled and are stored final as **new observations**; `raw_daily_bar` is append-only, and the provisional row stays as the record of what was fetched first.
4. Reports `provisional`, `refetched` and `stillProvisional`, the last recounted after the re-fetch.

Placing it just before the gate gives the run the most time to pass 17:00. The chain phase alone takes ~40 minutes.

### QC-203

It now counts the latest observation per ticker in the run. Counting rows would fire on a bar R3 had already fixed, because the superseded provisional row is still there.

### The email

The REMEDIATION block gains an R3 line above R6:

- `REMEDIATION  R3 (final re-fetch of provisional bars): 12 re-fetched, 0 still provisional`
- `… : settlement window still open at 16:50 ET — 1083 bar(s) left provisional`
- `… : nothing provisional` (the normal after-close run)
- `… did not run: <error>`: R3's failure is also in the run's phase errors and never fails the run

### Tests

`bar-settlement.test.ts`: a 16:40 fetch is re-fetched at 17:45 and QC-203 goes from firing to clean, with both rows kept; at 16:50 R3 makes no call and reports the open window; after an after-close fetch there is nothing provisional. `gate.test.ts`: the four email lines.

R3 is collection, so the rehearsal script cannot exercise it; a run starting before 17:00 ET is the live test.
