# v1.1.300 — 2026-09-20

TradeAnalyzer only. Bull put spread shadow mode: the per-position budget stops gating.

## One setting doing two jobs

`maxLossPerPosition` sized a position — `floor(budget ÷ max loss per contract)` — and *also* excluded any
candidate whose single contract cost more than it (08 §3.4.5). The two jobs look like one until the mode is
in shadow, where nothing is traded and the only output is evidence.

It surfaced from the operator's own numbers. v1.1.299 made the stored settings readable and they showed
`maxLossPerPosition = $250`, confirmed deliberate for shadow (S10). At $250 only a spread risking ≤ $250 per
contract survives, so **8 of the 10 positions open on 2026-09-20 would have been excluded** — EOG at $785
a contract, CRWD at $913, CF at $820, with only APA ($198) and DVN ($184) clearing it.

**A budget rejection never becomes a position, and a position is what settles.** So the budget was not
shrinking the book — there is no book — it was shrinking the sample that §4's "≥ 30 settled positions" is
waiting on, by roughly 5×.

## Why an unaffordable spread is still evidence

§4 condition 2 is *mean return on max loss > 0*. That is a per-share ratio: `spread-mode-settle.ts` never
reads `contracts` at all, and the settlement path is entirely in per-share terms. A spread the account
cannot afford tells you exactly as much about whether the *strategy* works as one it can. It tells you
nothing about whether *this account* could have traded it — which is a second, separate question, and the
report now answers both rather than conflating them:

```
## Per-position budget ($250 — shadow records what it cannot afford)

  all positions   10 positions · 0 settled · mean — · win —   ← the §4 sample
  affordable      2 positions · 0 settled · mean — · win —   (8 could not be opened at this budget)
```

A pick the budget cannot afford is stored with `contracts = 0` (and `totalMaxLoss = 0`). That zero **is**
the affordability flag — no new column, no migration — because `on` excludes such a candidate and so can
never write one. A null `contracts` on a row written before this version reads as affordable, since the
budget was a gate then and the row cleared it by definition: the absence of the column is not evidence that
it was unaffordable.

## The `on` branch is a compile-time tripwire, not dead code

The obvious implementation is `if (contracts < 1 && settings.mode === 'on')`. It does not compile, and that
is the useful part: **`SpreadModeSwitch` is `'off' | 'shadow'`** — `on` is deliberately not in the union
until its surfaces exist (§3.9), and `readSpreadModeSettings` coerces a stored `'on'` to the default. So
that comparison would be a guard whose input cannot contain what it looks for, the same shape as
`rebuild-better-sqlite3`'s EBUSY message that could never fire because `stdio: 'inherit'` had already
emptied the string it tested.

`budgetGates()` is an exhaustive switch instead:

```ts
switch (mode) {
  case 'off': return false;
  case 'shadow': return false;   // S10 — sizes, never gates
  default: { const unhandled: never = mode; return Boolean(unhandled); }
}
```

Adding `'on'` to the union stops `default` narrowing to `never` and **breaks the build on this line**,
putting the decision in front of whoever builds that mode. Verified by doing it: adding the member yields
`spread-mode.ts(173,22): error TS2322: Type '"on"' is not assignable to type 'never'`, and nothing else.
A guard is worth having only if it has been seen to fire.

## A seam in the sample, recorded rather than smoothed

Picks from 2026-09-21 onward are drawn from a **wider candidate pool** than those before, and §3.6 ranks
unaffordable spreads alongside affordable ones, so the top-5 cut can differ. The §4 sample has a join at
that date. It is written into 08 §3.5 on the day it was made — an undeclared join between two
differently-selected populations is the `iv_history` splice, whose whole lesson was that the comparison is
only purchasable *before* the stitch.
