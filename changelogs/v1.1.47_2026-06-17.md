# v1.1.47 — 2026-06-17

## Fix: options API endpoint returned empty chains on evening runs (starved the TraderAgent)

### Symptom
The TraderAgent ran its full scout → decide → trade pipeline nightly but produced **zero new trades for ~10 days** (last trade June 8). Scout logged 80–130 surviving candidates each run, yet `decide` selected nothing.

### Root cause
`GET /api/v1/options/:ticker` (`src/main/api/routes-options.ts`), when called without an explicit `expiration`, fetches the next 8 weekly Friday expirations via a local helper `nextFridays()`. That helper mixed two time bases:

- weekday + day arithmetic in **local** time: `now.getDay()`, `now.getDate()`, `setDate()`
- serialization in **UTC**: `toISOString().slice(0, 10)`

When the helper runs after the local clock has crossed UTC midnight — any evening run in a timezone behind UTC (e.g. US Eastern after ~20:00) — the computed local Friday serializes to the **Saturday** UTC calendar date. E\*Trade lists **Friday** expirations only, so `getOptionsChain(ticker, <saturday>)` matched nothing. The route catches per-expiration failures and continues, so the net response was `{ ok: true, data: [] }` — a silent empty chain.

Downstream, the agent's `scout` phase stored **zero option contracts** for every survivor; `decide`'s `pickBestContract` returned null for all of them, so `selectedTrades` was always empty and `trade` wrote nothing.

### Why it looked intermittent
The bug is time-of-day dependent. The June 8 run (which did create trades) happened during the day, before the local→UTC date rollover, so the Fridays were correct. Every subsequent run happened in the evening (agent logs show 18:00–23:00 local), after rollover, so every expiration shifted to a non-existent Saturday.

### Evidence
- Real E\*Trade expirations in the app's own snapshot (`options_premium_history`, 2026-06-17): `2026-07-17`, `2026-07-24` — both Fridays.
- `nextFridays(8)` at the same instant emitted `2026-07-18`, `2026-07-25`, … — all Saturdays.
- Scout payloads: run 22 (Jun 8) had 16 survivors with contracts; runs 23–28 (Jun 9–18) had **0** contracts across 80–130 survivors.
- The app's daily-options-snapshot job was unaffected because it resolves real expirations from E\*Trade rather than guessing.

### Fix
`nextFridays()` now computes entirely in UTC (`getUTCDay()`, `Date.UTC(...)`, `setUTCDate()`), matching the correct pattern already used in `analysis-service.ts` and `filter-templates-service.ts`. The function is exported for testing.

### Scope check
The two other Friday-guessing helpers in the codebase are internally consistent and were **not** affected:
- `ipc-options.ts` `generateNextFridays` — local weekday math **and** local serialization (`getFullYear/getMonth/getDate`).
- `opportunity-service.ts` `nearestFridayAtLeast` — local math **and** `toLocaleDateString('en-CA')`.

### Tests
- New `tests/options-route-fridays.test.ts` (2 tests): pins the helper to UTC Fridays under a faked evening clock (`2026-06-18T01:00:00Z`), and verifies it skips the current day when today is already a Friday.
- Full suite: **595 passing**, typecheck clean.

### Operator note
Full end-to-end live confirmation (real contracts flowing back through the route) needs a run while E\*Trade is serving chains (market hours / shortly after close, token not dormant). The fix itself is proven by the expiration-date data above and the unit test; the next daytime agent run should resume creating trades.
