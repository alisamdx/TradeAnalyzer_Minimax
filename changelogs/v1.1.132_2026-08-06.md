# v1.1.132 — 2026-08-06

## The wheel path was discarding the liquidity inputs it scores from

Found while checking whether `options_premium_history` was mature enough to unblock realized-outcome
validation of the two default-off liquidity flags. The readiness banner says no. The data says
something more interesting.

### What was wrong

`analyzeWheel` computes the recommended contract's bid, ask, open interest and volume, folds them
into `optionLiquidityScore`, and then **throws them away**. `WheelResult` carried none of them, so
`wheelResultToRow` had nothing to write:

```ts
dte: r.dte, delta: r.delta, bid: null, ask: null, premium: r.premium,   // ← hardcoded
annualizedReturn: r.annualizedReturn, iv: r.currentIv, ivRank: r.ivRank,
openInterest: null, breakeven: null,                                    // ← hardcoded
```

Measured against the production database:

| strategy | rows | with `bid` | with `open_interest` |
| --- | --- | --- | --- |
| income | 22,302 | **22,302** | **22,302** |
| wheel | 21,127 | **0** | **0** |

Two months of wheel history — 2026-06-15 → 2026-08-05, ~1,030 tickers a day — recorded the
*verdict* (`optionLiquidityScore`) with none of the *evidence*. `OptionsIncomeResult` carried
bid/ask/openInterest, which is the only reason income rows are complete.

Separately, **`volume` was captured by nothing at all** — no result type had the field — so the
third component of the score (+2 of 10) is unrecoverable for every historical row of either
strategy.

### Why it matters

This is precisely what blocks FR-SEY-5 validation of `WHEEL_GRADED_LIQUIDITY` (v1.1.131). To
re-score a historical recommendation under a different scheme you need the inputs, not the output.
Because income rows kept theirs, a retrospective realized A/B **is** possible there —
**5,797 settled income CSPs across 969 tickers and 12 dates**, each with a close on its expiration
date. The wheel rows cannot be re-scored at all.

The gap is **not backfillable**: those quotes were never persisted anywhere.

### The fix

- `WheelResult` gains `bid`, `ask`, `openInterest`, `volume`; `OptionsIncomeResult` gains `volume`.
- `analyzeWheel` and the options-income path populate them; the empty/unmeasured constructors write
  `null`.
- **Migration 066** adds `options_premium_history.volume` (nullable, no backfill).
- `PremiumHistoryRow`, both mappers and the insert statement carry `volume`; `wheelResultToRow` now
  passes the real bid/ask/OI through.

**Nothing coerces these to 0 when a quote is genuinely absent.** A 0 asserts "measured and
terrible", which is a different claim from "no quote" — the same conflation fixed for
`optionLiquidityScore` in v1.1.127. Pinned by a test.

### The pattern worth naming

Three consecutive fixes to the same code path, all the same shape:

| version | defect |
| --- | --- |
| v1.1.127 | unmeasured liquidity persisted as a fabricated `0` |
| v1.1.131 | the score's own thresholds so miscalibrated it was near-constant |
| **v1.1.132** | the inputs behind the score never persisted at all |

The wheel path kept computing liquidity information and keeping only the conclusion. **When adding
a signal, persist its inputs — a stored verdict cannot be re-validated.**

### Premium-history readiness, for the record

`getPremiumHistoryReadiness()` counts distinct `as_of_date` values older than 45 days and wants 40.
Today: **5**. There are 43,429 rows across 36 capture dates (2026-06-15 → 2026-08-05); the 40th
capture date lands ~2026-08-11 and must then age 45 days, so the banner flips ~**2026-09-25**.

That threshold governs *return-on-capital* analysis. It is not the gate for liquidity validation —
the settled sample needed for that already exists (see above).
