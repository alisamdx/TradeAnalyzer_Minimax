# v1.1.372 — 2026-10-20

## TradeAnalyzer 2: stale blocking findings that nothing could close

`core` 0.6.80, `next` 0.4.65.

### What was wrong

A fresh gen-002 snapshot (2026-10-20 22:44) held 3,202 blocking findings that were `open` or `acknowledged` with `still_firing = 0`. `reconcileStoppedFiring` was behaving as specified (03 §5.1, P9): when a finding stops firing, the gate closes it only on evidence. That evidence is a check's `Evaluation.closesAs`, a successful remediation plus a clean evaluation, or a retired `keyShape`. Every group came down to a check that supplied no such evidence, or to a ruling the operator had already made.

| Group | Count | Cause |
|---|---|---|
| QC-302, 2026-10-16 (run 89) | 687 | **Check bug.** It joined every `raw_eod_quote` version with every `raw_daily_bar` version for the day. The 12:09 ET intraday run (86/87) had stored a snapshot and a partial bar, so the after-close run compared the midday snapshot with the final bar, and the final snapshot with the midday bar. Latest against latest: 0 of 1,081 disagree. The key is a ticker, so a clean reading on a later date is no evidence about 10-16. |
| QC-701 CTSH, D (run 85), LEN (run 53) | 3 | **No closer.** CTSH's and D's 2026-07-24 10-Q facts were read on 10-16; LEN's 2026-08-31 facts on 10-05. The check read them clean every run since, but a clean reading with no remediation does not close a finding. |
| QC-956 `replay` (run 69) | 1 | **No closer.** A replay has passed since (request 10). |
| QC-804 `606:TSLA` (run 8) | 1 | **Not a fault.** Order 606 is an `OPTION_ASSIGNMENT`: BUY_CLOSE TSLA 350C at 0, SELL 100 TSLA at 350. The option leg has no price by nature. The check reads only orders captured in the current run, and an unchanged order is never captured again, so the finding was never looked at a second time. |
| 10-08 token loss: QC-409, QC-402, QC-401, QC-412, QC-801, QC-901 | 2,505 | **By design.** Acknowledged by the operator on 2026-10-13: 10-08's E\*Trade data was never collected and cannot be. 852 of the QC-409s were 2026-09-22 findings that had been resolved and then recurred on 10-08, because a contract key carries no date. |

### Changes

- **QC-302** (`quotes-actions.ts`): `qc302Pairs` compares the latest snapshot with the latest bar (MAX(row_id) on each side). `rejudgeQc302` re-judges each open finding on the latest pair for every date in its `affects_trading_dates_json`. When all of those dates agree, it closes the finding as `rule_changed`. A date with no pair, or one that still disagrees, leaves the finding open.
- **QC-701**: a clean reading of a ticker that has an open finding closes it. The kind is `data_corrected` when the newest fact period has moved past the one in the finding's evidence, and `rule_changed` when it has not (the allowance changed).
- **QC-956**: closes as `data_corrected` once a passing replay is inside the window, naming the request.
- **QC-804**: the option leg of an `OPTION_ASSIGNMENT` order is exempt. `rejudgeQc804` re-judges open findings against the stored order and closes them as `rule_changed`.
- **03 §5.1**: a per-group explanation, what the operator does with a permanently lost day (leave it acknowledged and filter the workbench; resolving or accepting would both be untrue), and a rule for new checks. If a finding can stop firing because the condition ended or the rule changed, the check must supply `closesAs`. If its key carries no date, it must re-judge on the finding's own dates.

### Rehearsal

`rehearse-gate.mjs --date 2026-10-20` on the 22:44 snapshot closed 691 QC-302 findings (687 blocking), 12 QC-701 (8 `data_corrected` including CTSH, D and LEN; 4 `rule_changed`), QC-804 `606:TSLA`, and QC-956 `replay`. Open, non-firing blocking findings went from 3,202 to 2,505, all of them the acknowledged 10-08 group.

### Not fixed here

QC-701 took 72 s in the rehearsal, against 0.3 s in the real run. The cause is the `newest_forms` subquery that v1.1.371 added; this change's own query takes 1 ms. It probably needs an index on `raw_edgar_fact (cik, period_end)`.
