# v1.1.118 — 2026-07-03

## Brief pipeline audit, round 3: B1–B4

Final round of the brief-pipeline audit (following v1.1.116's earnings/VIX/trend fixes and v1.1.117's score-concentration fix). Unlike the first three items, B1–B4 were mostly design questions rather than clean logic bugs, so this round leaned on **empirical investigation against the production database** before deciding what (if anything) to change — consistent with this project's FR-SEY-5 rule that trade-logic changes must be validated, not guessed at.

### B2 — ETF wheel handicap (confirmed real; implemented, shipped disabled)

**Investigation.** Queried the live production DB directly:

```
ETF constituents: 60
ETFs with a fundamentals_cache row: 4 / 60
Last 5 wheel briefs — ETF picks: 0, 0, 0, 0, 0
```

Wheel's `fundamentalScore` (weight 17) and `leverageQuality` (weight 4) derive from data (P/E, ROE, debt) that structurally doesn't exist for an ETF wrapper. Under the existing missing-signal rule (`FR-SE-03`: a missing signal's weight still counts toward the composite's denominator, contributing 0 to the numerator), these two signals are *always* null for an ETF — deflating every ETF's wheel composite by 21% of the total weight, for reasons unrelated to trade quality. The result, confirmed above: ETFs never surface in the live wheel brief, even though `FiltersView`'s wheel templates already work around exactly this problem with an ETF-specific branch.

**The fix (implemented, off by default).** `ETF_AWARE_WHEEL_SCORING` in `scoring-service.ts`:

```ts
const ETF_AWARE_WHEEL_SCORING = false;
export function etfAwareWheelScoringEnabled(): boolean {
  return ETF_AWARE_WHEEL_SCORING || process.env['SCORING_ETF_AWARE_WHEEL'] === '1';
}
const ETF_NA_WHEEL_SIGNAL_KEYS = new Set(['fundamentalScore', 'leverageQuality']);
```

When enabled, `scoreTicker`'s accumulation loop `continue`s past these two signal keys entirely for an ETF ticker — excluding their weight from **both** numerator and denominator, rather than zero-contributing — so the remaining signals renormalize to 100%. Verified by hand-computed test cases: a synthetic ETF with realistic values for every applicable signal scores **58.3** with the flag off (current, unfixed behavior) and **73.8** with it on — a 15.5-point swing purely from not penalizing the fund wrapper for lacking P/E data it was never going to have.

The env-var override (`SCORING_ETF_AWARE_WHEEL=1`) mirrors the existing `REPLAY_WITH_ADX` pattern used for the ADX scoring A/B, and is checked live (not cached at module import), so a future validation run — or a test — can exercise the "on" arm without touching the shipped default. `TickerSignalData.isEtf` now flows through both the live scoring path (`ScoringService.loadEtfFlags`, new) and Brief Replay (`BriefReplayService.loadEtfSet`, new), so a Brief Replay run with the env var set will faithfully measure the effect on ETF wheel outcomes.

**Why it ships disabled.** This changes wheel composite scores for ETF tickers, which changes Stage-4 pool selection and final picks — the live wheel brief feeds the v2 execution engine. Per FR-SEY-5, that requires showing a Brief Replay improvement (or at least neutrality) before shipping enabled, matching the precedent set by the ADX A/B and the SPY-regime-gate/overbought-guard rejections. **Next step, not done here:** run Brief Replay with `SCORING_ETF_AWARE_WHEEL=1` over a representative window and compare ETF wheel win-rate/return against the current baseline before flipping the default.

### B1 — Morning-vs-evening liquidity bias (investigated; insufficient data, no action)

The hypothesis (from the original audit): the Strategy Lab's liquidity score includes a same-day-volume component, and at the ~10:15 intraday brief slot volume is structurally lower than after close, so borderline structures could pass the evening gate but fail the morning one.

This turned out to be a **pre-existing tracked question**, not a new one — `scripts/fr-liquidity-slot-comparison.mjs` already exists specifically to measure it, and the `project_expiry_selection_followup` memory already scheduled a re-run once `structure_liquidity_log` (migration 064, v1.1.93) accumulates enough days. Ran it fresh against production:

```
Distinct ET dates with a morning run: 1, evening run: 1
Structure observations paired across both slots: 1072
liquidityScore  morning mean 4.60 | evening mean 4.55 | paired delta (eve−morn) mean -0.05
bar flips (≥8): morning-pass → evening-fail 34 | morning-fail → evening-pass 53
```

Only **one ET date** has been logged — the instrumentation is new. The means are nearly identical, and at the tradability bar (≥8) the **evening slot clears it more often than morning** (53 vs 34) — the opposite direction of the hypothesis. This is exactly what single-day noise looks like, not a systematic bias. **No code change** — acting on a plausible-sounding hypothesis off one day of (contrary-direction) data would be exactly the kind of unvalidated guess this project's process is designed to avoid. Updated the `project_expiry_selection_followup` memory with today's numbers; still waiting on the originally-scheduled ~2–3 week re-run (mid-to-late July 2026).

### B4 — Unvalidated-pick gate asymmetry (reviewed; already correct, no action)

Re-examined `hasAdequateLiquidity()` returning `true` on a failed lab call but `false` on a successful call that found no valid structure. Traced both consumers precisely:
- **Human brief**: shows the unvalidated pick (`validated:false`) with the critic's `low_liquidity` info flag ("not validated against a live options chain") — a clear signal to the reader.
- **v2 execution engine**: `chosenScore()` in `brief-entry-source.ts` returns `null` whenever `pick.strategyLabResult` is absent (there's no structure to build), so `briefPickToPickInput` excludes the pick before the engine ever evaluates the liquidity gate.

The two layers are independently consistent; the "asymmetry" only existed in how the gate function's two branches were named, not in what actually happens downstream. **No code change** — documented in spec §14 and `.ai/AI_CONTEXT.md §10` so it isn't re-flagged as an open bug later.

### B3 — Thin-`iv_history` "double penalty" (reviewed; already appropriately conservative, no action)

Re-verified the interaction: a missing top-2-weight signal (e.g. wheel/income `ivRank`) deflates the composite (by design, FR-SE-03) and raises the critic's `critical_signal_missing` warning. Traced the actual gating impact: this warning alone does not force an automatic reject — the LLM critic's system prompt explicitly forbids defaulting to `caution`, so a normally-functioning critic weighs it qualitatively. It only forces a hard `flag` (→ engine rejection) when the **critic itself degrades** (the LLM call fails), which is the deliberately conservative fallback: don't trade blind on both incomplete data and a skipped adversarial review in the same cycle. **No code change.**
