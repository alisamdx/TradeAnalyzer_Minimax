# v0.32.80 — 2026-06-11

## Fix: EDGAR 5Y CAGR computed from FY-2 instead of FY-5

### The bug

Found during the post-batch deep-dive of the daily brief data. Every 10-K re-reports
the two prior fiscal years as comparatives, so the raw 10-K entry list for any concept
contains each fiscal year 2–3 times:

```
[0] FY2025 (from FY25 10-K)
[1] FY2024 (from FY24 10-K)
[2] FY2024 (from FY25 10-K)   ← duplicate
[3] FY2023 (from FY23 10-K)
[4] FY2023 (from FY24 10-K)   ← duplicate
[5] FY2023 (from FY25 10-K)   ← duplicate — this was the "5 years ago" slot!
```

`getEdgarFundamentals()` indexed this list as if entry N were N years back. Index 5
always lands on FY-2, so the "5Y CAGR" was a 2-year change annualized over 5.

**Verified impact (AAPL):** true 5Y revenue CAGR 8.68% → computed 1.66%.
YoY growth (index 1) was structurally correct by luck — the newest year only appears
once, so index 1 is always the true prior year.

**Blast radius:** `revenueGrowth5Y`, `epsGrowth5Y` in fundamentals_cache for the whole
universe → `earningsGrowth` (blends 1Y+5Y), `revenueGrowth5Y`, `epsGrowth5Y` signals in
the bullish/buy scoring strategies → valueScore / growthScore / stockGrade.

### The fix

New exported `annualSeries(entries)` in `sec-edgar-provider.ts`:

1. Keep only `form === '10-K'` entries
2. Drop duration facts whose period is < 300 or > 400 days (some filers tag quarterly
   comparatives inside 10-Ks; 52/53-week fiscal calendars produce 363/370-day years,
   both inside the window). Instant facts (balance sheet, no `start`) pass through.
3. Dedupe by period `end` — most recently `filed` entry wins (restatements honored)
4. Sort newest-first

`EdgarEntry` gains optional `start` (present on duration facts, absent on instants).
`pickBestConcept` and the slot-building `annuals()` both use the deduped series.
`latestEntry` ties on `end` now break by latest `filed`.

Also removed the 5Y CAGR fallback to 3–4 year bases: fewer than 6 deduped annuals → null,
which the scoring engine treats as a missing signal and reweights (matches the existing
behavior for recent IPOs like ALAB/MRVL).

### Data note

Cached values remain wrong until rows pass the 24 h TTL. Handled separately by purging
the stale cohort and rewinding `fetched_at` so the next batch refreshes everything.
