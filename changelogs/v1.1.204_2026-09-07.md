# v1.1.204 — 2026-09-07

## fix — the dev scripts were corrupting the generation they inspected

**This supersedes the root cause given at v1.1.202.** The MSIX redirect was real,
the guard was worth shipping, and it was **not** what corrupted `meta_response` —
the second corruption happened *after* that guard shipped, on a shell verified
clean, with both applications on the fixed builds.

### What it actually was

`queue-job.mjs` and `diagnose-generation.mjs` used **`node:sqlite`**, which
bundles **SQLite 3.51.3**. Both applications use **`better-sqlite3`**, which
bundles **3.53.1**. The wal-index (`-shm`) format carries no cross-version
compatibility guarantee, so running a script against a generation the collector
was writing put two SQLite libraries on one wal-index.

It showed up two ways:

- **Corruption**, both times in the table being actively written.
- **Silently lost writes** — `queue-job` reported `request 1` on two successive
  runs, because the first insert never reached the file. Same root, quieter.

`node:sqlite` was chosen deliberately, on the grounds that "a built-in has no ABI
to be wrong." That is true and it is reasoning about the wrong risk.

### The identification that settled it

`sqlite_master.rootpage` on a **freshly built** schema. The two events reported
`Tree 5` and `Tree 7`, which read as different objects and are the same table:
adding `meta_open_handle` to the dictionary shifted every later root page by two.
**A tree number is only meaningful against the schema version that produced it**,
and reading the two as different tables is what kept the earlier diagnosis
pointing the wrong way.

### The fix

`packages/core/scripts/lib/generation-access.mjs` is now the only way a script
opens a generation:

- **Refuses while a `-shm` exists**, which is exactly when some process holds the
  database. Recovering a stale one is the application's job — starting the new
  exe replays and checkpoints it.
- **Opens with `better-sqlite3`**, one SQLite per generation, always. The ABI
  swap is the price; the script names `npm run rebuild:node` and **refuses rather
  than falling back**, because a fallback reintroduces the mixing at the moment
  nobody is watching. The require and the `new Database(...)` are in one `try`:
  the binding loads lazily, so `require` succeeds against the wrong ABI and the
  construction is what throws.
- **Checkpoints `TRUNCATE` before closing**, reporting a `busy` or short
  checkpoint rather than discarding work silently.

### Tests

`packages/core/test/generation-access.test.ts` — four, run in a child process
because both refusals are `process.exit`. Both directions are asserted: it must
refuse with a `-shm` present **and** open without one, since a guard that refuses
everything is an outage that looks identical in a suite testing only the refusal.

### What this cost, and the general lesson

**A diagnostic that damages what it inspects is worse than no diagnostic** — and
this one was the instrument being used to decide whether the damage was
happening. A directory holding two `data.sqlite` files was strong evidence of *a*
fault and no evidence at all about *which* fault.
