# v1.1.149 — 2026-09-01

## feat: negotiate a working transactions request shape instead of guessing one per release

### Four hypotheses, all falsified against the API log

| # | Theory | Test | Verdict |
|---|---|---|---|
| 1 | Range width (v1.1.146) | 31-day slice | Stalled like 8 months |
| 2 | Transport replay (v1.1.147) | Fresh-nonce retry | Same `nonce_used` — a fresh nonce cannot be reused |
| 3 | Date parameters (v1.1.148) | `{count}` only, no dates | Still hung, aborted at 45,016 ms |
| 4 | Our OAuth/signing | 28 other calls, same key + code | All 200 in ~300 ms |

`/v1/accounts/{key}/transactions` hangs for this account and reports it as
`oauth_problem=nonce_used` after ~120 s. The OAuth message is a mask over a server-side
timeout.

### Change

Guessing one variant per release costs a package-and-click cycle each time. This tries the
remaining plausible request **shapes** in a single pass, 20 s each, and uses whichever answers:

| variant | rationale |
|---|---|
| `.json` suffix | E*Trade honours a format suffix on many endpoints; `Accept: application/json` alone may not be enough here — note its error envelopes come back as XML regardless |
| `sortOrder=DESC` | documented for this endpoint, and may be required for `count` to bound the result set — an unbounded scan would explain a fixed ~120 s server timeout |
| `.json` + `sortOrder` | both together |
| `count=5` | if the endpoint is merely slow per row, five rows should return |
| 7-day window | narrower than any range tried so far |

The winning shape is then reused for every sliced request — including any extra params it
needed (`sortOrder` carries through; `startDate`/`endDate` are replaced per slice). Every
attempt is logged, so a total failure stays fully diagnostic and the error names each shape
tried.

Worst case is ~100 s to establish the endpoint is dead, versus ~18 minutes before v1.1.148.

### Reading the result

- **A variant answers** → that shape is used for the import and you get real fills.
- **None answer** → the endpoint is unusable from any client, which points at E*Trade
  server-side or an account entitlement rather than a client bug. Next step is E*Trade support
  or a CSV import of their transaction history, not more code guessing.

### Tests

`tests/etrade-transactions-slicing.test.ts` +3, −2 (7 total): when only `.json` answers, every
sliced request carries the suffix; when only `sortOrder` answers, every slice keeps it while
dates are still replaced per slice; and when nothing answers, no sliced requests are issued and
the error names each shape tried. Suite: 1005 passed.
