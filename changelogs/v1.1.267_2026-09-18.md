# v1.1.267 — 2026-09-18

## The liquidity study reads through the app, not the SQLite file

`scripts/fr-income-liquidity-realized-ab.mjs` opened
`%APPDATA%\trade-analyzer\trade-analyzer.sqlite` itself, write-capable. That path is
MSIX-redirected in the container a Claude Code session runs in — probed 2026-09-18:

```
AppData\Roaming\trade-analyzer  →  AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\trade-analyzer
```

So the scheduled 2026-09-28 re-run would have read the container's **stale shadow copy**.
That task exists to measure a settled panel that has roughly doubled since the last run;
reading an old copy would have reported the old panel and returned *"sweep unchanged"* for
a reason entirely unrelated to the question. And it would not have prompted: the existing
`Bash(node *)` allow rule lets any `node scripts/*.mjs` run unattended. The task was paused
the same morning pending this fix.

It now calls **`GET /api/v1/diagnostics/settled-csp-panel?strategy=income|wheel`**, which the
running app answers on its own connection — the same fix the wheel A/B got in v1.1.220. The
script has no database access left; it exits with *"the app must be RUNNING"* if the API is
unreachable, and names the version it needs on a 404.

## Its realized volatility never matched live scoring — now it does

The study re-scores every recommendation with the income composite, whose
`recentVolatility` signal carries weight 20. The script computed it with its own copy of the
formula, and that copy was looser than the engine's:

| | live `ScoringService` | old script copy |
|---|---|---|
| closes considered | newest ≤ 22 | newest 21 |
| minimum to produce a value | 16 closes, ≥ 15 returns | **10 closes** (9 returns) |
| a zero close | skipped | `log(0)` → `-Infinity` → `NaN` |

For any thin-history ticker the study therefore scored a signal the engine never computed —
a replay signal measured differently from the live one is a different signal.

`services/settled-csp-panel.ts` exports `recentVolatility()`, which mirrors
`loadRecentVolatility` exactly, and its test does not restate the formula: it inserts bars and
compares against **`ScoringService.gatherSignalData` on the same data**, agreeing to 10
decimal places, and asserts both return `null` on a 12-close history. A replica tested
against its own copy of a formula only proves it matches itself — the third time this project
has met that shape.

Live scoring is untouched. There are now four realized-vol implementations (live, Brief
Replay, the backtest's `rollingVol`, and this one); consolidating them touches the scoring
path and is FR-SEY-5-gated, so it is not done here.

## One bar load per ticker

The script queried bars once per `(ticker, as_of_date)` — thousands of round trips, which
would each have become an HTTP call if moved naively across the API. The service loads each
ticker's history once and binary-searches the as-of date, and a test asserts the vol is
computed **strictly as of the recommendation date**: rewriting every later bar into a
violent path changes nothing.

## Consequence for the numbers

The next run of the study is not directly comparable with the 2026-08-07 one: rows whose
ticker had 10–15 closes before the as-of date now carry `realizedVol = null` (contributing 0
to the composite, at full weight in the denominator — the engine's own rule) instead of a
value the engine never saw. That is the study moving *towards* what it claims to measure, but
a comparison across the two runs should say so.
