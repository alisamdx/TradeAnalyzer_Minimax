# v1.1.268 — 2026-09-18

`core` 0.6.23, `next` 0.4.11 (TradeAnalyzer 2 has no code change; it is rebuilt to bundle core 0.6.23 and bumped so `meta_open_handle.app_version` distinguishes that build from the 0.4.10 one bundling 0.6.22). Two faults found validating the 2026-09-18 collector run (run 22).

## 1. A day with no insider data was indistinguishable from a quiet day

**What happened.** The EDGAR daily form index answered **HTTP 503** for 2026-09-18. The insider sweep falls back to the previous session only on 404 or 403 (the two ways "not published yet" had been seen: 404 on 09-10/11, a 215-byte AccessDenied 403 on 09-14..16), so it captured the 503 as a failed index and stopped. `events_insider` stored **0** rows against **299** the night before.

**It was worse than one empty night.** The sweep reads today's index, or yesterday's when today's is not up yet — which, at 18:00-19:30 ET, is every normal night. So each run in practice sweeps the *previous* session. The 09-17 run had swept 09-16, the 09-18 run failed, and the next run (09-21) would fall back to 09-18: **09-17's Form 4s could never have been asked for again.**

**And nothing noticed.** QC-906 compares fetched Form 4s against parsed rows, and returns nothing on a day with none fetched (deliberately — most days the universe filter leaves few). In the delta it showed as *gone*. Same shape as `cleanDayStreak` walking only dates with rows and QC-907's zero paired days: absence read as a pass.

**Fix — collection.** `runInsiderSweep` now walks every session after the last index that parsed (`insiderIndexDates`), oldest first, capped at five past sessions:

- today's index answering anything but 2xx is skipped **uncaptured** — it is the normal evening case, whatever status SEC uses, and the next run asks again;
- a past session answering 404/403 has no index and never will (SEC publishes none on federal holidays the NYSE trades through — Columbus Day, Veterans Day) and is stepped over, or the walk would stall on it for ever;
- any other failure on a past session is captured and **stops** the walk, so later sessions cannot advance the "last parsed" mark past it;
- a re-run of the same evening asks for nothing it already has.

**Fix — gate.** **QC-910 insider index coverage** (warning, sentiment): the number of sessions before the trading date with no parsed index. Fires above **1** (working threshold) — one behind is recovered by the next run's catch-up and is not a finding; two means the catch-up itself is failing. Also fires when a sweep ran and no index has ever parsed; evaluates nothing where no sweep has ever run. The detail names the status that stopped it.

On the next run (09-21), expected: the sweep asks for 09-17, 09-18 and 09-21, stores 09-17 and 09-18, and skips 09-21 until it is published. Not rehearsable — a collection change needs a live run.

## 2. HTTP 204 was recorded as a parse failure

E\*Trade's `/v1/market/optionexpiredate` answers **204 with a 0-byte body** for a symbol with no listed options — NVR, YUM, DDS, the same symbols whose chain call says "No options are available for this symbol". `logs/api` shows 10-26 a day since 2026-09-10. The empty body went to `JSON.parse` and was indexed `parse_status = failed` ("Unexpected end of JSON input"), so the day report listed parse failures that were really "zero expirations".

`indexAndIngest` now indexes any 204 as `parse_status = ok` with zero rows and never hands it to the ingestion module. It lives there, not in the expirations parser, because No Content means the same thing from every provider — and because replay runs the same function.
