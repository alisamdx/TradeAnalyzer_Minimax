# v1.1.209 — 2026-09-09

`@tradeanalyzer/core` 0.3.4, dictionary version **8**.

## The collector path is exonerated

A screening arm was built to close every remaining difference between the replay
and the live seed at once. It ran in Electron, in the generation's own directory,
at the live pace, through the real job-queue wrapper, with varying response
bodies and injected failures.

| | live seed (corrupted) | screening replay (clean) |
|---|---|---|
| runtime | Electron 32.3.3, ABI 128 | Electron 32.3.3, ABI 128 |
| directory | `…\trade-analyzer-next\data` | same |
| references / failures | 1,083 / **6** | 1,083 / **6** |
| pace | ~30 ms | 30 ms |
| result | 2,334,720 bytes, 570 pages, **corrupt** | 2,408,448 bytes, 588 pages, **ok** |

Three things had never been exercised and are now covered:

- **Failure responses.** The corrupting seed had 6 failed tickers; every previous
  replay had zero, so the row shape a failure produces — a `meta_response` with
  no status and no `raw_ticker_reference` beside it — had never been written.
  `REPLAY_FAIL_EVERY` injects both shapes: a provider 500 with a body, and a
  transport fault with no status (a killed response stream).
- **Body size.** Every canned response was byte-identical, so every row was the
  same length and the btree packed in a way no real run does. Bodies now vary
  deterministically between 0 and 8 KB.
- **The job wrapper.** `collector-oneshot` does not call `runUniverseSeed` bare —
  it claims a `meta_job_request` row, marks it running, and writes the report back
  as JSON when it finishes. **Those writes land at the very end of the sequence,
  which is exactly where all three corrupt files have their damaged pages**, and
  the replay had skipped every one of them. `REPLAY_QUEUE=1` goes through it.

Plus the untested cell of the earlier 2×2: Electron *in that directory* (Node had
been tested there, Electron only in temp).

**Everything reproducible outside the app is now clean.** What remains is the real
application around the collector.

## fix — `meta_open_handle` recorded opens and not closes

The table exists so that "are two applications holding this file at once" is
answerable by **reading**. It could not answer it: two open timestamps are
consistent with any amount of overlap or none.

So on 2026-09-09, at the exact point where concurrency was the live hypothesis in
a corruption investigation, the question had to be put to the operator and taken
on recollection. (The answer was no, and it stands — but recollection is not what
this table was built to replace.)

Dictionary **v7 → v8** adds a nullable `closed_at`, which is additive growth and
so applies inside an existing generation. Both applications stamp it before
closing, `recordOpenHandle` clears a stale value on re-open, and
`recordCloseHandle` never throws — a close is a best-effort annotation on the way
out, and turning "could not record the close" into "the application could not
shut down" would be strictly worse.

`diagnose-generation.mjs` now prints each interval and **states an overlap
outright** when two applications' recorded intervals intersect. Where a close is
missing it says so, and says explicitly that overlap *cannot be ruled out* from
those rows — which is not the same as ruling it in. That distinction is the one
this whole investigation keeps turning on.

## fix — the collector host never checkpointed

`ElectronCollectorHost.close()` was `this.db?.close()`, leaving a multi-megabyte
WAL to SQLite's close-time behaviour. The new exe was fixed for this on
2026-09-07 after a measured **918,792-byte WAL was discarded with the base file
byte-for-byte unchanged**; the collector host — which writes far more — still
trusted close. It now checkpoints `TRUNCATE` explicitly and logs a `WARNING` when
the checkpoint does not fully apply, so a checkpoint that does nothing is no
longer indistinguishable from one that worked.

## Known defect, deliberately NOT fixed in this version

`ElectronCollectorHost.polygonGet` calls `fetch` directly and **bypasses the rate
limiter**, contrary to spec 06 §5 change #3 and CLAUDE.md's standing rule. It is
real and it should be fixed.

It is being left alone for now on purpose: routing it through the limiter changes
the collector's write pace, and the write pace is currently an experimental
variable in an open corruption investigation. Fixing it mid-bisect would confound
the next run. Recorded here so it is deferred rather than forgotten.
