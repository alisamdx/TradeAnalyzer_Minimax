# v1.1.231 — 2026-09-11

## Reviewing the IV bootstrap before paying for it

`bootstrap_iv` is the one-shot that loads a year of external IV history. It has never run, because it
waits on an IVolatility subscription. Examining it ahead of that spend found two faults and settled a
scope question.

### 1. It had no API key, and its comment said otherwise

```ts
// The API key is the host's business, not `core`'s …
// `httpGet` signs and logs it; this module never sees it.
const url = `${IVOLATILITY_BASE}${IVX_ENDPOINT}?symbol=…&from=…&to=…`;
```

The host's `httpGet` had one auth branch — Finnhub — and `providerForHost` did not know
`restapi.ivolatility.com`. So the comment described an intention, and the first real run would have
sent ~500 unauthenticated requests.

This is the third instance of the same shape in eight days: **Finnhub (v1.1.223) had the key missing
entirely; EDGAR (v1.1.230) had three of four callers unlogged; this one had a comment asserting a
capability that was never built.** A comment is not a mechanism.

Fixed: `getIvolatilityApiKey` on the host, appended as `?apiKey=` — a query parameter, because
IVolatility **rejects** `Authorization: Bearer` (`ivolatility-provider.ts` line 8, learned the hard way
by the existing app). An unset key refuses the call rather than sending it bare.

### 2. The credential in the URL forced a logging change

`logHttp` built `requestParams` from `URL.searchParams`, so signing the URL would have written the key
into `logs/api/` — plaintext, 30-day retention — on every one of ~500 calls. `loggableParams()` now
redacts `apiKey` / `token` / `key` / `secret`. `polygonGet` already avoided this by rebuilding params
from the caller's object rather than reading them back off the URL; this brings the generic transport
to the same standard.

### 3. No pacing — and the precedent that sets the rate

`runBootstrapIv` looped tickers with no delay. Each call now waits on a dedicated 55/min limiter
(burst 2, so it trickles rather than starting with a head of tokens).

**55/min ≈ 1,100 ms, which is exactly what the existing app used** in `iv-history-service.ts` to pull
S&P 500 + Russell 1000 + ETFs — a year of daily IVX each, roughly 1,000–1,500 calls — to completion,
with a 15 s back-off on 429 and no incident. That is a *larger* run than the bootstrap plans.

**This retracts earlier advice.** The plan had said to contact IVolatility support before running,
citing their warning that retail subscriptions are not for bulk downloading. The operator pointed out
that the old app had already done a bigger pull without asking. They were right: the thing that
differed was never the notification, it was the throttle — and the old app had one while
`runBootstrapIv` did not. The vendor warning is real but the empirical precedent at greater scale
outweighs it, so the notification is dropped and the pacing is mandatory.

Open, and worth one check against the account's own plan page before the run: the
`1 req/sec sustained (burst 5), 20k req/month` figure is an **uncited code comment**. It is the basis
for the rate chosen here, and no source for it exists in the repository.

### 4. Scope: the chain subset, not the full universe

`bootstrapTickers()` reads `ref_chain_subset_membership` — the tickers IV rank is actually computed
for (~500 at steady state). Buying the full list would be worse than wasteful:

`QC907_BOOTSTRAP_OVERLAP` evaluates every ticker with an unaccepted external series and requires **20
paired days per ticker**. A paired day needs an `ok` row in `derived_iv30_daily`, which is derived from
our own chain snapshots — captured only for subset members and pinned contracts. A bootstrap row for a
non-subset ticker therefore **can never pair, never be accepted, and fires a blocking finding
permanently**.

The old app pulled everything because it stored IV for everything and had no pairing gate. This design
demands the two series be comparable before either is trusted — which exists precisely because the old
app's `iv_history` splices IVolatility to E\*Trade values with **zero** overlapping ticker-days across
1,055 shared tickers, a comparison that can never now be made.

The real cost of the narrow buy is churn: a ticker joining the subset later has no history until its
own series matures. That is an argument about **when** the subscription month starts — once the subset
has filled — not about widening the list.

### Tests

`tests/collector-host.test.ts` — the key is read, appended as a query parameter, redacted in the log,
refused when unset, and paced by its own limiter. The Finnhub single-limiter assertion was rewritten:
it had counted every `requestsPerMinute: 55` occurrence and required exactly one, which broke as soon
as a second provider legitimately needed the same rate. It now counts each **named** limiter.
