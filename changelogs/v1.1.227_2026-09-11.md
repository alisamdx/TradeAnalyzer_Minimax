# v1.1.227 — 2026-09-11

## The EDGAR contact address: one module, and it lives in settings

The SEC asks automated clients to "declare your user agent in request headers", with a sample of
`Sample Company Name AdminContact@<domain>.com`. Their **enforcement** is on rate — 10 requests per
second, "further requests from the IP address(es) may be limited for a brief period", resuming after
10 minutes below the threshold. There is also a clause that unclassified bots are not allowed to crawl
the site, which is what a declared contact answers.

So this is a courtesy and a small insurance policy, not a gate. Nothing was being blocked: the one
EDGAR failure on the 2026-09-10 run was the daily form index, and that file serves fine — the run
simply asked for the day's index before it had posted.

### Two callers, two different wrong answers

| Caller | What it sent | Reaches |
|---|---|---|
| `sec-edgar-provider.ts` | `TradeAnalyzer/1.0 trader@local` | XBRL fundamentals, `company_tickers.json`, Test API screen |
| `ElectronCollectorHost.httpGet` | `TradeAnalyzer/<version> (collector)` — no contact | collector filings, company facts, Form 4 sweeps |

`trader@local` is not an address anyone can reach, so declaring it is worse than declaring nothing: it
looks like compliance and delivers none. Both now call `edgarUserAgent()` from
`services/edgar-identity.ts`. **A rule that must hold for every caller belongs in the function they all
call** — the fourth time this shape has been written up here (the portfolio cash snapshot, the E*Trade
OAuth transport, the dev scripts' redirect guard).

`core` still sends no user agent at all, which spec 04 §11 requires: the library does not know who is
running it, and a contact address in a checked-in library is exactly what this change avoids.

### Why a setting and not a constant

This repository has a GitHub remote (`github.com/alisamdx/TradeAnalyzer_Minimax`). An address written
into source is in that history permanently, and no later edit removes it. The operator sets it once in
**Settings → SEC EDGAR Contact**; it is stored in the `settings` table under `edgarContact`.

It is a **plain** setting, deliberately not `secureSet`. The encrypted path can fail closed and blank
every key at once (v1.1.200), and a courtesy header is not worth that failure mode — nor is an address
the SEC is meant to read a secret.

### Degradation

No contact configured → `TradeAnalyzer/1.1.227`, with no parentheses. `TradeAnalyzer/1.1.227 ()` reads
as a bug at the receiving end and tells the SEC less than saying nothing at all. Blank and
whitespace-only values count as unset. A failed settings read returns null rather than throwing: the
identity must never be why a provider call cannot be made.

### Tests

`tests/edgar-identity.test.ts`

- the setting round-trips and shapes the agent;
- unset gives a name-only agent, asserted not to contain `()`;
- whitespace counts as unset;
- both callers are proven, by source assertion, to route through the one module, and
  `sec-edgar-provider.ts` is asserted to no longer contain `trader@local`;
- a scan over all of `src/` fails any email-shaped literal in a user-agent context, so the address
  cannot be committed later by accident. `example.com` is exempt (RFC 2606 reserves it for exactly
  this), which is what the Settings placeholder uses.

### Operator step

The address is not in the build. Open **Settings → SEC EDGAR Contact**, enter it, and press
**Save Settings**.
