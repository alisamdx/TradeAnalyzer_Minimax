# v1.1.304 — 2026-09-22

## QC-602 compared the farthest earnings date, not the nearest

### What happened

The 2026-09-21 gate report carried a new QC-602 finding:

> ACN: finnhub 2026-12-16 vs etrade 2026-09-27 (80 days apart)

Eighty days between two sources on the same ticker's next report is the
signature of a feed that has lost a quarter — the exact failure the Finnhub
bulk-cap truncation caused in the existing app, where NVDA's 2026-08-26 report
was stored as 2026-11-17 and the brief ranked it wheel #1 on the day it printed.
So the finding invited an investigation of Finnhub's calendar.

Finnhub's calendar was right. The stored rows for ACN on 2026-09-21 are:

| source | report_date | fiscal | observed_at |
|---|---|---|---|
| finnhub | 2026-10-01 | FY2026 Q4 | 22:40:26.126Z |
| finnhub | 2026-12-16 | FY2027 Q1 | 22:40:26.330Z |
| etrade  | 2026-09-27 | — | 22:40:43.739Z |

Both Finnhub rows are correct and both are from **one sweep**. The earnings
sweep is subdivided into windows because the bulk calendar truncates at its row
cap, so one run writes one row per window per ticker — here 204 ms apart. The
check ranked with

```sql
ROW_NUMBER() OVER (PARTITION BY ticker, source ORDER BY observed_at DESC, row_id DESC)
```

and **the last row written for a ticker is always its FARTHEST date**, so it
picked December against E*Trade's September. The true disagreement is
2026-10-01 vs 2026-09-27 — **four days**.

### The fix

`QC602_EARNINGS_SOURCE_DISAGREEMENT` now takes `MIN(report_date)` per
`(ticker, source, run_id)` and ranks those by `run_id DESC`, which is precisely
what QC-601 does. On today's data the finding reads
`ACN: finnhub 2026-10-01 vs etrade 2026-09-27 (4 days apart)`; the other three
paired tickers (AAPL 2d, ABBV 7d, ABT 2d) are unchanged, and the fired count
stays 4 of 4.

### Why it survived

**This is QC-601's artefact in the sibling that reads the same table, and the
fix that killed it there (v1.1.285) changed only QC-601's query.** QC-601's own
comment describes the mechanism in full — *"MU's 2026-09-30 and its 2026-12-15
are two real reports in two windows of the SAME sweep, written 409 ms apart"*,
and *"the last row written for a ticker is always its FARTHEST date"* — and
QC-602, twenty lines away in the same file, reading the same table for the same
purpose, kept the ordering that comment exists to warn about.

Nothing caught it because **every QC-602 test inserted one row per ticker per
source**, so the multi-window shape the check meets in production had no fixture.
The check also could not have failed on it before 2026-09-21: E*Trade earnings
only became a second source in v1.1.270, and 09-21 was the first run with any
ticker dated by both. The new regression builds the real three-row ACN shape and
fails on the old code with `expected 80 to be 4`.

### The part worth keeping

A finding can be **true and still carry a fictional number**, and that is worse
than either a false positive or a missed one: it is a real problem wearing the
signature of a different, much more serious problem, and it spends the
operator's attention on the wrong feed. QC-602's job is to make one source's
drift visible; an 80-day reading pointed at Finnhub, which was correct, and away
from E*Trade's 2026-09-27 — a **Sunday**, which QC-604 flagged independently the
same night.

Rule: when two checks read one table for related questions, a fix to how one of
them selects rows is a fix the other one needs. Grep the table, not the check.
