# v1.1.213 — 2026-09-09

`@tradeanalyzer/core` 0.3.5, dictionary version **8** (unchanged).

## fix — every `acquire()` spent TWO tokens, so the rate limiter ran at half its setting

Found by asking whether the previous version's change needed a live seed to
validate. It did not; it needed a unit test of the class it had just made
load-bearing.

`processNextInQueue()` shifted the queue's **head** to wake the next waiter. But
a callback that has just succeeded is still sitting at the head — nothing removed
it — so it shifted **itself**, re-ran through `setImmediate`, and took a second
token.

Measured: a bucket with a burst of **10** granted exactly **5** acquires.

```
requestsPerMinute: 100   ->  effective  50
requestsPerMinute: 500   ->  effective 250
```

**This has been true for as long as the class has existed**, so every Polygon
path in the app — screener, analysis, validate-all, briefing, LEAPS, news — has
been running at half its configured rate, and the Settings screen has been
reporting a number the app never used.

Now: the succeeding callback splices *itself* out before waking anyone, and
`processNextInQueue` **peeks** rather than shifts. Peeking matters — a waiter
that still cannot get its tokens re-arms on a timer, and a shifted one would be
re-armed while no longer in the queue, losing its place in the FIFO and becoming
invisible to `drain()`.

### Why twelve existing tests missed it

Two reasons, and both are the interesting part:

1. **Every assertion was "did it resolve"**, with slack in the budget. None
   asked *how many tokens did that cost*. A double-spend satisfies all of them.
2. **The re-entry does not happen under fake timers at all.** `setImmediate` is
   faked, the deferred callback never fires, and the whole path is absent. My
   own first attempt at a regression test passed for exactly this reason —
   before the fix — which made it worthless: it could not distinguish the two
   behaviours it was written to distinguish.

The test that settles it uses **real timers**, yields after each acquire so the
deferred callback actually runs, and **counts grants rather than awaiting them**,
so a failure reports `expected 5 to be 10` instead of hanging for ten seconds.
A hang says something is wrong; a count says what.

## Net effect on the Polygon rate

The two fixes compound, and the change is larger than either:

| | before v1.1.212 | now |
|---|---|---|
| configured | 100 | 500 |
| actually applied at startup | no — always the default | yes |
| effective | **50 rpm** | **500 rpm** |

Still roughly **a quarter** of the ~1,900 rpm the collector was measured
sustaining unthrottled without a single 429, so the headroom argument for 500
holds — it was made against the real peak, not against the halved figure.

## Confirmed on a live seed, by arithmetic rather than by impression

A fourth `universe_seed`, 1,092 Polygon calls, immediately after this fix:

```
500 granted instantly from the full burst   (burstSize defaults to rpm)
592 paced at 500/min = 8.33/s               = 71.0 s
                                              ─────
predicted 71.0 s   observed 70 s   (handle held 20:58:29–20:59:40)
```

Zero 429s, `integrity_check: ok`, same 1,092 / 1,083 / 1,587 / 6 as every other
run. The measurement separates all three live hypotheses rather than merely
being consistent with the preferred one: **unthrottled** would be ~34 s, **still
double-spending** ~3.4 min, **correct** ~71 s.

**The burst is why the prediction going in was wrong** (~2.2 min): `burstSize`
defaults to `requestsPerMinute`, so a run begins with 500 tokens in hand and
only the remainder is paced. Spec 04 §3's elapsed figures are corrected to carry
the burst term — a phase of *n* calls costs `max(0, n − tokensInHand) ÷ 8.33/s`,
which is a range, not a number, because it depends on what ran before it.
