# v1.1.116 — 2026-07-03

## Daily Brief / Critic — three real-money accuracy fixes

Follow-up to an independent, code-first audit of the daily brief pipeline (scoring → Stage 4 validation → AI critic → execution-engine entry gate), looking specifically for defects that could produce a wrong recommendation or silently drop a good one. Three findings were prioritized as highest-impact and fixed here; the rest are tracked for a later pass.

### 1. Same-day earnings were invisible to the brief

**The bug.** Both earnings guards compared `report_date` with a strict `>` against today's ET date:
- Stage-3 penalty (`daily-intelligence-brief-job.ts` `loadEarningsPenalty`): `WHERE report_date > ? AND report_date <= ?`
- Critic warning (`critic-service.ts` `getEarningsBeforeExpiry` / `hasFutureEarningsRow`): same `>` comparison, plus the same defect made `hasFutureEarningsRow` read a same-day report as "no data at all" (`earningsKnown: false` to the LLM).

A ticker reporting **today after the close (`amc`)** — or with an unrecorded report time — evaluated as having no earnings risk at all. Concretely: the ~10:15 intraday brief could hand you a wheel/income/bearish pick with no `-20` composite penalty and no `earnings_in_window` warning, on a name that reports at 4:05pm that same day. You could sell premium off that brief mid-morning and take the full gap that afternoon.

Note: the v2 execution engine's own earnings resolver (`brief-entry-source.ts`) already used `>=`, so the automated live-trading path was not exposed — only the human-facing brief (and its critic commentary) had the gap. That's exactly the surface you read from for your personal book.

**The fix.** New shared pure helper in `earnings-service.ts`:

```ts
export function isEarningsPending(reportDate: string, reportTime: 'bmo' | 'amc' | null, todayET: string): boolean {
  if (reportDate > todayET) return true;
  if (reportDate < todayET) return false;
  return reportTime !== 'bmo'; // same day: amc or unknown time hasn't happened yet
}
```

A same-day `bmo` (before-open) report has already happened by the time any batch job runs and is excluded (falling back to "next earnings unverified" until the calendar's smart-cache refreshes to the following quarter). A same-day `amc` or unknown-time report is still pending and is penalized/flagged exactly like any other in-window date.

Both consumers now widen their SQL bound to `>=` and filter precisely with `isEarningsPending`:
- `loadEarningsPenalty` (Stage 3)
- `getEarningsBeforeExpiry` and `hasFutureEarningsRow` (critic)

### 2. The critic could run on a stale VIX with no age check

**The bug.** `refreshVixQuote()` only overwrites `quote_cache`'s VIX row on success; on any failure the previous value is left in place with no re-validation. `CriticService.getMarketContext()` read that row unconditionally — there was no staleness check at all. If E*Trade failed for a stretch (a multi-day outage, a token dormancy over a weekend), the critic kept reasoning off a VIX number that no longer described the market: a cached "calm" 14 silently surviving into an actual fear spike (or vice versa) would flip the wheel/income (`VIX > 30`) and bearish (`VIX < 14`) rules in the wrong direction on the day they matter most.

**The fix.** `getMarketContext()` now reads `fetched_at` alongside `last` and treats anything older than 24 hours as unknown:

```ts
const vixFresh = vixRow !== undefined
  && (Date.now() - new Date(vixRow.fetched_at).getTime()) <= VIX_MAX_AGE_MS; // 24h
const vix = vixFresh ? vixRow!.last : null;
```

24h was chosen because `refreshVixQuote` runs at the top of every brief — both daily slots, ~18h apart on a normal trading day — so a successful refresh is never more than ~18h old; anything past 24h means the refresh has actually been failing. A stale VIX now falls back to the pre-existing `null` fail-safe (macro context becomes SPY-trend-only; the two VIX rules simply skip) rather than confidently using an outdated number.

### 3. Two of the critic's five trend-conflict checks were silently dead

**The bug.** `checkTrendAlignment` branches on strategy and reads a specific scoring signal to detect a trend/strategy mismatch:

```ts
if (strategy === 'wheel') {
  const trend = s['trendStrength'];   // wheel's config has no such key!
  ...
}
...
if (strategy === 'buy') {
  const trend = s['trendStrength'];   // buy's config has no such key either!
  ...
}
```

`pick.signals` only ever contains the keys present in that strategy's own scoring config (`scoring-service.ts`). `trendStrength` exists only in the **bullish** config. Wheel's actual trend signal is `notDowntrend`; buy's is `trendAlignment`. So `s['trendStrength']` was `undefined` for every wheel and buy pick, and the `if (trend && ...)` guard silently never entered — these two safety checks have never fired since they were written. A wheel pick sitting in a confirmed downtrend (assignment-at-the-top-of-a-decline, the wheel's core risk) got the composite penalty from `notDowntrend` scoring but never the designed `trend_strategy_conflict` critic warning; same for a buy pick lagging on both trend and relative strength.

**The fix.** Read each strategy's real signal:
- wheel → `notDowntrend` (scoring's `computeTrendDirectionScore('wheel')`: bullish=100, sideways=75, confirmed-downtrend=10 — threshold `<35` isolates the real falling-knife case)
- buy → `trendAlignment` (scoring's `computeTrendDirectionScore('directional')`: bullish=100, sideways=25, bearish=0)

Bullish and bearish were unaffected (their existing keys, `trendStrength`/`downtrendScore`, are correct) and are unchanged.

**Left alone, on purpose:** income's `trendNeutral` branch reads `trendStrengthAdx`, which has been permanently `null` since ADX was excluded from scoring (`USE_ADX_IN_SCORING = false` in `scoring-service.ts`, validated on a full-year Brief Replay A/B — enabling ADX was net-negative). No live substitute signal exists for "trending too hard for range-bound income" without reintroducing ADX, which would need its own replay validation per the project's FR-SEY-5 rule (trade-logic changes must be validate-before-ship). This is documented in-code rather than silently left looking active.
