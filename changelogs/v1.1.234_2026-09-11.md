# v1.1.234 — 2026-09-11

## Exactly 1,000 splits is not a number of splits

`core` 0.6.5.

The first real `backfill_bars` finished and reported:

> `backfill_bars: 1293548 bars for 1089/1089 tickers, 1000 splits; RED 512 finding(s) awaiting a ruling.`

The bars are good. **1,000 splits is the `limit` parameter read back to us.**

```ts
const splitResponse = await host.polygonGet('/v3/reference/splits', {
  'execution_date.gte': from, 'execution_date.lte': args.tradingDate, limit: '1000'
});
```

No `next_url`. No `atProviderCap`. Polygon's splits endpoint paginates, and documents a
maximum limit of 5,000.

### 1. Why a short list became 512 bad findings

QC-204 marks a price discontinuity `explained` only when a matching corporate action sits
inside the gap:

> a `raw_split` / `raw_dividend` row between `prev.trade_date` and `cur.trade_date`

So a truncated split list does not merely lose rows — it **converts real corporate actions
into unexplained price breaks**, each one landing in the operator's review queue as a
possible ticker reuse. An unknown share of the 512 are artifacts of splits never fetched.

**They must not be ruled on until the sweep is re-run.** Ruling on them is precisely the
wasted work the review queue exists to avoid, and an acceptance carries a 30-day expiry, so
a wrong ruling is a decision that comes back.

### 2. The check that exists for this could not fire

QC-008 is **blocking**, reads `meta_response WHERE at_provider_cap = 1`, and says:

> returned exactly the provider cap — treat as truncated and subdivide

It was written after Finnhub's 1,500-row bulk calendar stored NVDA's August report as
November and put it in the brief on the day it printed. It has been correct and idle: none
of the four Polygon list call sites ever passed `atProviderCap`.

**A cap detector only works on the call sites that tell it a cap was hit.** That is why the
paging and the flag ship in one change rather than two.

### 3. Four call sites, one shape

| site | window | was | now |
|---|---|---|---|
| `backfill.ts` splits | 5 years | `limit: '1000'`, one page | swept to the cursor's end |
| `phases/market.ts` splits | 7 days | `limit: '1000'`, one page | swept |
| `phases/market.ts` dividends | 7 days | `limit: '1000'`, one page | swept |
| `phases/events.ts` short interest | 45 days, whole market | `limit: '50000'`, one page | swept |

The daily window is seven days and nowhere near 1,000 rows today — which is exactly why it
would have gone unnoticed there. The five-year window is what made it visible. The window
only has to grow, or a busy ex-dividend week only has to arrive.

Short interest keeps its `limit: '50000'`. It is the largest list this collector asks for
(every ticker FINRA publishes, across ~3 settlement dates) and 50,000 very probably does not
bind. It was also very probably true that EDGAR's 1,000-filing cap and Finnhub's 1,500-row
calendar did not bind, right up until they did — and this path has **never yet returned a
live 200**, so the first response that clears the short-interest verify note must not be one
we trusted without checking.

### 4. How the sweep is built, and two things it deliberately does not do

`collector/paged.ts` — `sweepPolygonPages(host, { path, params, onPage })`.

**It does not stitch pages into one synthetic body.** Each page is captured separately, so
`meta_response` holds exactly what Polygon sent, the archive stays byte-faithful, and a
replay re-ingests each page through the same recipe. `ingestSplits`/`ingestDividends` read
only `results` and needed **no change at all** — the paging is invisible to them.

**It does not follow a URL.** `polygonGet` builds `https://api.polygon.io${path}` itself, so
only the path and query of a `next_url` are used and the origin is discarded: a response
body is data, never a destination. A `next_url` naming a different host is refused outright
(its *path* was meant for another service), and an `apiKey` echoed back inside a cursor URL
is stripped before it can reach `params_json`, which is stored and printed by the Runs view.

Stopping early is still allowed and is now **recorded**: page budget spent, cursor not
advancing, or cursor off-provider each set `atProviderCap` on the final page, where QC-008
will find it.

`BackfillReport` gains `splitPages` and `splitsTruncated`, and the batch note now reads
`N splits over M page(s)` — because `splitsStored` alone cannot distinguish a complete list
from a truncated one, which is the whole reason this took a live run to notice.

### 5. The rule, rather than the four instances

`packages/core/test/polygon-paging.test.ts` fails any file under `src/collector` that calls
`polygonGet` with a `limit` and does not use the sweep.

It carries **`fires` and `clean` fixtures** instead of leaning on a count. A count is a
number that can be quietly tuned until the suite goes green — and the first draft of this
very test asserted `examined >= 3`, went red at 2, and the honest fix was to discover *why*
(routing `events.ts` through the sweep removed its last direct `polygonGet`, so it correctly
left the scan) rather than to lower the number. Comments are stripped first, for the reason
they always are here.

This is the **fourth** instance of one shape: Finnhub's 1,500-row calendar, the universe
seed's 2,000 alphabetical tickers with MSFT absent, and now splits/dividends/short interest.
Every one of them was HTTP 200.
